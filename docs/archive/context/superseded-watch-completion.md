# 历史规则：已被取代

不可用于当前实现。当前规则见 [播放合同](../../context/playback.md)。

- **「算看完」的统一口径（2026-09-13 裁决；判定式已被 2026-09-29/30 产品完善度批次推翻，见下一条）:** 用户看到列表里「看到 00:28 / 00:28」却没标已看，裁定这就是已播完，且已播完的下次要从头播。判定收在 `VideoService.UpdateVideoWatchProgress` 一处：位置离片尾不到 `watchedCompletionToleranceSeconds`（1 秒）即视为看完。裁决要求**严格**，所以用绝对容差而非 5 秒 / 95% 这类宽松阈值；容差再取 `min(1, duration*0.05)` 并要求位置 >0：固定 1 秒在亚秒片段上会让「位置 0」满足 `position >= duration-1`，而取时长一半又等于「看过一半就算看完」——比被否决的 95% 还松。20 秒是比例与绝对值的交接点。判定成立就标已看**并把断点清零**——这一条同时兑现三件事：下次从头播、列表不再显示「看到 X / Y」、与 Jellyfin 自身语义（`Played=true` 配 `PlaybackPositionTicks=0`）一致。`watched_at` 只记第一次看完的时间。三条上报路径都收敛到这个口径：内嵌播放器（ended 仍可显式传 `completed`，时长元数据不准时它可能远离片尾）、Jellyfin `/Sessions/Playing/*`（此前自己要求 `seconds >= duration`，比应用内严，同一部片在两个客户端结论不同）、**IINA 断点同步**（桌面「播放」按钮走的就是它，此前完全不动 `is_watched`，不改这条的话用户报的现象在主力路径上根本没修掉）。IINA 同步另加三条：已看的视频直接跳过（位置清零后「只前进不后退」挡不住陈旧 `watch_later` 记录把它拉回「在看」）；断点文件**消失**仍不据此判已看（可能是用户自己清了记录）；**完成判定必须排在「只前进不后退」守卫之前**——两者幅度同为 1 秒会形成死区，既吞掉正常完成（库里存 26.6、这次到 27.3 就被跳过），也让历史遗留行恒满足 `seconds <= position+1` 而永不自愈。`IINAProgressUpdate` 带 `Watched` 字段，前端就地补「已看」徽标，不必等整页重载。手动 `SetVideoWatched(true)` **有意不动断点**：误点一下就把两小时电影的断点抹了且撤不回来。已看视频被上报中途位置时也照常记录（重看场景）。对外自洽改在一处解决——`jellyfinUserData` 在 `Played` 时把 `PlaybackPositionTicks` 报成 0，与 `IsResumable` 的筛选口径（`is_watched=false AND position>0`）对齐；桌面端本来就不显示也不续播。前端 `resumePositionFor` 的容差同步收到 1 秒（原为 `max(duration-5, duration*0.98)`，长片上反而更宽松），行组件 `watchProgressPercent` 在 `is_watched` 时返回 0。
