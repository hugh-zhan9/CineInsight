### 2.4 稳定分页机制 (Cursor-based Pagination)
针对大规模视频列表设计了基于游标的稳定分页：
- **排序规则:** `score ASC, size DESC, id DESC`。
- **最近播放:** 使用 `(last_played_at DESC, id DESC)` 键集游标，播放时间变化时不依赖 `OFFSET`。
- **继续观看（2026-09-29/30，D-PC42，PLAY-09）:** 条件改为 `resumableSQL`（断点可续，见 2.5），排序改为 `(watch_progress_updated_at DESC, id DESC)` 的键集游标（`ListContinueWatchingWithFilter`），进度时间为空的老数据排在最后；此前按均衡分数排序，最近看的会沉底。

### 2.7 视频扫描与路径管理
- **手动目录扫描进度（2026-09-10）：** `ScanDialog` 通过 `SyncDirectoryWithProgress(dir, requestID)` 与 `directory-scan-progress` 事件显示检查目录、读取设置、读取目录、核对片库、处理文件和保存目录阶段。发现数量与已检查文件数在遍历途中更新（文件事件约 250ms 合并，进入目录前立即上报），附当前目录和已用时间；8 秒无新进度明确提示仍在等待，不把初始 0 当最终结果。事件按请求 ID 隔离，遍历结束后的迟到事件不回退阶段；运行中禁换目录、重复启动，关闭按钮标为「后台继续」，重开保留任务。手动路径分批读取目录名（128 条/批、不全量排序），复用既有过滤；读取错误返回失败、禁止用不完整结果进入增删对账。自动扫描仍沿用原遍历策略。
- **TS 文件头检测上限（2026-09-10）：** `.ts` 与 TypeScript 源码扩展名冲突，`isKnownNonVideoSourcePath` 原先误用 `os.ReadFile`，扫描一个 5.6 GB 的 TS 视频就会完整读入内存，在 SMB 上造成持续大流量和长时间无进展。现由 `isTypeScriptSource` 只读取前 64 KiB（`io.LimitReader`），含 NUL 的二进制样本不按源码排除；`.d.ts` / `node_modules` 路径排除保留。此修复同时覆盖手动/自动扫描与 `AddVideo`；不可回退成整文件读取。本机真机日志已确认共享目录发现完成（1072 个视频），不代表另一台机器上所有文件可见性问题都已验收。
- **扫描机制:** 递归遍历目录，基于 `Settings` 中的 `VideoExtensions` 过滤。
- **附带大小:** `ScanDirectoryWithInfo` 返回 `[]ScannedFile`（含 path+size），用于迁移检测。
- **唯一性:** 在数据库层面通过 `idx_videos_path_active` 唯一索引（结合 `deleted_at IS NULL`）保证路径唯一。
- **手动增量扫描:** 视频列表工具栏可手动扫描全部已配置目录，复用启动时同步逻辑并展示新增、迁移、移除记录、元数据补全、跳过和失败数量；发现新视频后立即唤醒 AI 打标任务。
- **扫描回报（2026-09-29/30，D-PC09，LIB-08 / LIB-14）:** `ScanSyncResult` 与 `LibraryReconcileSummary` 带 `skip_breakdown`，键为 `existing`、`blocked_user_delete`、`recently_modified`、`temp_file`、`not_video`、`read_error`、`legacy_trash`，旧的 `skipped` 等于各项之和。`SyncScanDirectories(trigger)` 由前端启动时传 `startup`、扫描条传 `manual`（为空或不认识按 `manual`），完成后与改目录触发的扫描一样发 `library-scan-summary {trigger, result}`，`IncrementalScanBar` 展示，有增删恢复时重载列表与头部计数——启动扫描与改目录扫描不再静默。`ScanDialog` 加入扫描根之前先调 `ValidateScanDirectory`（`{exists, duplicate_of, nested_in, contains}`），有嵌套时提示并可「仅扫描不加入」；`ScanDirectoriesSection` 不再吞掉错误。
- **扫描目录黑名单:** 设置页按目录维护扫描排除列表；黑名单目录及其全部子目录会在启动扫描、手动目录扫描、增量扫描和迁移候选扫描中跳过。加入黑名单停止后续收录，并在查询时隐藏已有视频；不删除记录，取消排除后恢复可见。
- **扫描恢复与候选过滤（2026-09-10）:** 全量扫描找到 `is_stale` 旧记录时也清标记并计入 `Restored`，与窄对账一致。两条路径的未命中候选必须经 `os.Stat` 明确不存在才能进入迁移/删除/标失效，近期活跃、隐藏或排除规则不等于磁盘丢失。目录遍历错误向上传，阻止失败根参与缺失对账；已明确排除、隐藏或回收站目录仍优先跳过（`filepath.Walk` 在回调前尝试读取目录，不能让不可读的 `.Spotlight-V100` 挡住全盘扫描）。「回收站目录」自 2026-09-29/30 起只指路径某一段为 `.Trash` / `.Trashes`，或登记过的旧版 `trash/` 目录（带回收站条目的目录；或基名恰为 `trash`、且父目录下有软删媒体的目录），计入跳过分项 `legacy_trash`；用户自己名为 `Trash` 的普通目录不再被一概跳过（LIB-14 / IMG-13）。跨目录旧失效记录只在真正匹配新文件后检查存在性，避免无关挂载盘错误污染本地实时同步。手动增量扫描摘要增加「恢复显示」，复用 `TaskFailureList` 展示失败路径和原因。用户手动删除与来源未知的历史删除不自动复活；明确由扫描删除的记录按下述 2026-09-11 规则恢复；同路径出现新文件时是否收录按文件身份判定（2026-09-29/30，见下文「删除归因与自动恢复」）。另一台 Mac「手动扫描 0、无报错」及本地 / SMB 文件不可见仍待现场验证，不能由上述回归推定已解决；跟踪见 `docs/issues/2026-09-10-scan-zero-on-second-mac.md`。
- **删除扫描目录 = 标失效，不删记录（D-S01..D-S03）:** `App.DeleteDirectory` 在删配置行**之前**调 `VideoService.MarkVideosStaleUnderRemovedRoot`，把只属于该根的活跃视频置 `is_stale=true`；标记失败就不删配置行（先删配置又没标上，那批记录会掉进"扫描看不见、列表看得见"的夹缝——这正是本次修的毛病，因为两条对账都只在**当前**扫描根之下取候选）。有意不走软删：`deleteVideoRecord` 每条都会建 `VideoTrashEntry`，删一个目录就往回收站灌上千条。嵌套根按"属于被移除根且不属于任何剩余根"判定，`/media` 与 `/media/movies` 同时配着时删前者不牵连后者。这批记录的失效原因记为 `removed_root`，在「路径失效」视图里可见（此前被扫描根裁剪挡住、确认框的承诺落空，LIB-01，2026-09-29/30 修复），行菜单「加回目录…」经 `ReaddRemovedRoot` 预填原根路径。
- **失效记录不进默认列表（D-S02）:** `applyLibraryFilter` 在智能视图不是 `stale` 时一律追加 `is_stale = false`。这条边界是主片库与随机播放共用的，因此随机也不会再抽中指不到文件的记录。连带变化：因播放失败或文件丢失而失效的记录此前显示在主列表里，现在也只在「路径失效」视图里出现。
- **失效原因与「路径失效」视图（2026-09-29/30，D-PC06，LIB-01 / LIB-10）:** 所有写 `is_stale=true` 的地方同时写 `videos.stale_reason`（`offline_root` / `missing_file` / `removed_root` / `outside_roots` / `play_failed` / `read_error` / `watcher_missing`），清失效时一并清空；历史失效行原因为空，显示「原因未记录」；守卫测试从源码扫出所有写入点逐一断言。`stale` 视图**跳过扫描根裁剪**（黑名单仍排除），可按原因筛选（`stale_reason`，`unknown` 表示空原因），`ListStaleReasonCounts` 给出分组计数；行菜单提供「重新定位文件…」（原生文件选择 → `RelocateVideo`）、「重新检查」（`RecheckVideos`：取这些视频的目录去重后窄对账）与「删除」。`GetLibraryCounts` 与洞察页的视频总数都套用默认视图的可见条件（扫描根 + 黑名单 + 非失效），三处总数一致（PLAY-07）。
- **编辑扫描目录路径 = 重映射（2026-09-29/30，D-PC07，LIB-02）:** 设置页改扫描目录路径时二选一：`remap`（新路径必须存在、不能与其他根相同或嵌套；经 `rewriteLibraryPathPrefixTx` 在一个事务里改写视频含软删行、回收站条目原路径、扫描黑名单、字幕索引与扫描目录，再窄对账并重配监听；旧路径已不存在时默认选中）或 `replace`（沿用原行为，旧根下的记录标 `removed_root`）。此前改路径等于静默重建记录，元数据全挂在看不见的旧记录上。`RenameDirectory`、`MoveDirectory` 与重映射共用 `rewriteLibraryPathPrefixTx`。
- **离线与重连（2026-09-29/30，D-PC08，LIB-07）:** 监听把某根判为不可用（卸载或根被移除）时，`MarkRootOffline` 把该根下只属于它的活跃视频标 `offline_root`；根从不可用回到监听中时排队窄对账，文件还在的 `offline_root` 行自动恢复。触发来源：`RetryRoot` 成功、监听自行恢复、每分钟一次的巡检（对不可用的根做目录存在与卷挂载检查，可用即 `RetryRoot`）。启动与全量扫描时的离线判定同样写 `offline_root`。外置盘运行中拔插的真机行为待真机验证。
- **对账收拾孤儿记录（D-S01/D-S04 的历史遗留补充）:** 只在删目录那一刻处理是不够的——旧版本删目录只删配置行，那批记录已经掉进夹缝。`SyncScanDirectories` / `SyncImageDirectories` 末尾各跑一次 `reconcileOrphanedVideos` / `reconcileOrphanedImages`：不属于任何**已配置**目录的记录，视频与图片都只标失效、由查询过滤，不软删。判据用配置目录而非本轮扫到的 `roots`——盘没插时根扫不了但仍配置着，底下的记录只按离线标失效，不软删；目录清单读失败时直接返回错误、绝不走到这一步，否则会把整库藏起来。
- **加回目录即恢复（D-S03）:** `App.AddDirectory` 之后后台跑一次 `SyncAffectedDirectories`（窄对账，文件重新出现时清 `is_stale`），完成后复用 `library-watcher-reconciled` 事件通知前端。`ScanSyncResult.Restored` / `LibraryReconcileSummary.Restored` 是为此新增的计数——只做恢复的那一轮在其余计数上全是 0，漏掉它前端不会刷新列表。只恢复真的扫得到的文件，盘没插或路径写错时不会复活任何记录。
- **删除语义（2026-07-30 起的「移到同目录 `trash/` 文件夹、不覆盖移动、复制回退校验内容摘要」已被 2026-09-29/30 产品完善度批次推翻，R1–R3 / D-PC01–D-PC05；以下为现行语义，字段级契约见 `docs/loopx/design/2026-09-29-product-completeness/需求设计文档.md` §2 与 §1.2b）:** 视频与图片记录仍用 GORM 软删除，每次删除都建回收站条目（`video_trash_entries` / `image_trash_entries`，`mode ∈ {trash, legacy_trash, record_only, missing}`，同一次操作共享 `delete_batch_id`）。
  - **同时删除原文件 = 移到系统废纸篓**：先持久化 `pending_move`，再经 `services/system_trash_darwin.go`（cgo，`NSFileManager trashItemAtURL:resultingItemURL:error:`）移入所在卷的废纸篓，成功后在同一事务里软删记录、写 `mode=trash` 与废纸篓里的实际路径。删除流程不再做整文件 SHA-256，只记大小、mtime 与文件身份。所在卷不支持废纸篓（或非 macOS / 无 cgo 构建）时返回 `trash_unsupported`，记录不动，由用户在「永久删除（二次确认，`PermanentlyDeleteVideos` / `PermanentlyDeleteImages`）」与「只从片库移除」之间选择，不做降级（D-PC02）；根离线返回 `volume_offline`，无权限返回 `permission_denied`。手机端与 Jellyfin 删除走同一条路，但都不提供永久删除（手机端遇到 `trash_unsupported` 返回 409，提示去桌面端处理）。
  - **仅删除记录 = 按文件身份屏蔽**：写 `mode=record_only` 并记录身份；之后扫描遇到同一身份的文件跳过（计入 `blocked_user_delete`），直到在回收站点「允许重新收录」。视频与图片都进回收站、都可恢复（此前图片「仅删除记录」不可恢复，IMG-02）。
  - **恢复**：核对废纸篓一侧的 inode、大小与 mtime（不比较设备号——外置盘重插后设备号会变），不一致返回身份不符；原位置已被新收录的文件占用返回 `path_occupied`（「原位置已收录了新文件」）；`record_only` 只做数据库还原。用户在访达里「放回原处」、原路径上的文件身份与条目一致时，扫描与列表对账会直接恢复原记录。卷离线时列表对账、崩溃恢复与迁移残留都保持原状态。
  - **回收站中心**（`TrashCenterDialog.vue`，管理菜单「回收站」或命令面板打开）：视频 / 图片 / 扫描隐藏 / 迁移残留四个页签，多选「恢复所选」「永久删除所选」「移除已清除记录」，按模式与删除人筛选、搜索、加载更多；顶部显示占用并说明「在访达中清空废纸篓才会释放空间」（废纸篓里的文件被外部清掉后条目标 `file_gone`）。离线或无权限而无法处理的条目另有「仍然移除记录（不动文件）」（`ForceRemoveTrashRecords`；2026-10-13 起按钮叫「从回收站移除」，要输入「从回收站移除」，发给后端的协议常量仍是「移除记录」）。批量删除后出全局撤销提示并记进任务中心「最近操作」（`RestoreTrashBatch`；2026-10-13 前是页内「撤销本次删除（N 项）」条，见 2.38）。批量删除可带 `requestID` 报进度并可取消（`CancelBatchDelete`），已处理的项保留（D-PC51）。
  - **旧版回收站兼容**：2026-09-29 之前移进同目录 `trash/` 的历史条目回填为 `legacy_trash`，恢复与清除继续可用（记有 `file_sha256` 的行，按原路径恢复原记录前先核对哈希，读不出哈希时既不恢复也不新建）；这些目录在扫描中跳过，计入 `legacy_trash`。
  - 字幕索引、`restoring` / `rollback` 状态与启动对账沿用原有事务语义：事务返回错误时先确认数据库终态再决定是否补偿，应用启动会对账中断状态；`pending_move` 停在文件已移走、事务未提交的，启动时按原路径文件身份回滚，或在卷的废纸篓顶层按文件身份找回，都找不到置 `deleted` 并记「文件位置未知」。增量扫描发现文件缺失且无法判定为迁移时，仍只软删除数据库记录（`mode=missing`）。
  - 真机待办：废纸篓在 SMB、exFAT 与未授予「完全磁盘访问」时的错误码与恢复 / 清除行为只有单测，尚待真机验证。

- **扫描删除边界与删除人（2026-09-11，用户最终裁决）：** 磁盘退出或加入黑名单只隐藏；只有成功扫描的根仍在线、路径未被排除且 `os.Stat` 确认文件不存在时，全量扫描才软删除。`scanRemovalGuard` 保留遍历前根目录身份，缺失候选进入迁移前、删除前和扫描结束都核对在线状态；macOS 对 `/Volumes/<盘名>` 额外核对实际挂载点，防止退出后残留空目录伪装成在线。权限/遍历错误不得当作文件丢失。图片移除扫描范围也改为只标失效，默认图库/语义搜索/清理/手机候选过滤失效项；图片黑名单沿用独立配置为空时回退通用黑名单的语义。
- **统一手动扫描对账：** 手动目录弹窗原先在前端按扫描列表求差，再调用 `DeleteVideo`，会把程序操作混入用户删除，且漏掉后端文件存在性保护。现由 `SyncDirectoryWithProgress` 共用 `syncScanDirectories`，只处理选中目录，不对其他根运行孤儿对账；保留发现/处理事件和请求隔离，并展示恢复、删除、暂不可用与失败结果。
- **删除归因与自动恢复：** `videos`、`images` 和两类回收站条目新增 `deleted_by`，`user`=用户操作、`scanner`=程序扫描，旧行默认空值表示「历史未知」，不猜测回填。归因与软删除同事务落库，视频中断删除续跑从回收站条目继承；回收站显示删除人。启动/全量/窄范围/手动目录扫描找到 `scanner` 删除的视频时，用原回收站条目恢复原 ID、标签与字幕索引；只有确认是扫描删除且删除时文件已缺失、没有内容指纹的条目，才允许按原路径与记录大小恢复。~~用户/历史未知删除不自动恢复~~——2026-09-29/30 起改为按文件身份判定（R3 / D-PC03，推翻 2026-09-11 这一句；LIB-04）：同路径遇到软删行时依次判断——有扫描删除的 `missing` 条目 → 沿用上面的自动恢复；有 `record_only` 条目且大小与 mtime 一致 → 跳过（`blocked_user_delete`）；有 `trash` / `legacy_trash` 条目 → 原文件在废纸篓里，这是新文件，新建记录；没有条目的历史软删行且大小一致 → 跳过；其余 → 新建记录。启动时把「与软删行同路径」的活跃视频静默软删的 `cleanupReimportedSoftDeletedVideos` 已退役（它会把新收录的文件下次启动就删掉）。图片旧扫描已有 `is_stale` 来源标记继续兼容，但明确 `user` 永不自动恢复。回收站恢复同时清 `is_stale`，避免恢复成功仍不可见。扫描新增来源记录后沿用备份与迁移。

### 2.8 文件迁移检测
- **应用场景:** 自动扫描时区分“文件移走”和“文件删除”，移走的文件更新路径而非删除重建。
- **匹配算法:** 用 name + size 指纹对 stale 记录和新文件配对，配对成功调用 `RelocateVideo` 保留标签等元数据。
- **匹配范围:** 全库匹配，不限于当前目录。
- **主动文件迁移:** 单个或批量视频可迁移到已存在的目标目录，同名 SRT 会随视频移动；采用排他目标创建避免覆盖，同文件系统使用硬链接切换，跨文件系统完整复制并落盘；为避免外部进程持有旧文件句柄继续写入造成数据丢失，跨盘源文件会保留在隐藏暂存路径并向前端返回警告，数据库更新失败会回滚磁盘路径。2026-09-29/30 起（D-PC05，LIB-11）暂存源文件同一事务登记到 `migration_staged_sources`，回收站中心「迁移残留」页签可列出（逐行对账，文件已不在即标 `cleaned`）、移到废纸篓（`TrashStagedSources`）或直接删除（`DeleteStagedSources`），不再只提示一次就无从管理。
- **主动文件夹迁移:** 可把整个文件夹迁移到目标父目录，保留内部相对结构，并同步更新包含的视频记录、字幕索引和扫描目录路径（2026-09-29/30 起与重命名、重映射共用 `rewriteLibraryPathPrefixTx`，回收站条目原路径与扫描黑名单也一并改写，成功后重配监听，D-PC10，LIB-06）；迁移目标不在任何扫描根下时，确认框先警告并可勾选「同时把目标加入扫描目录」（`CheckMoveTarget`，LIB-09）；采用内容哈希校验、数据库切换、最后清理源目录的顺序，支持跨磁盘迁移，跨盘源文件夹同样保留并警告；禁止迁移到源文件夹自身或其真实路径子目录，拒绝源根符号链接。
- **文件夹重命名:** 可选择包含已收录视频或已配置扫描根的实际文件夹，在同一父目录内原子改名；目标已存在、根目录、符号链接和带路径分隔符的名称会被拒绝。改名同步更新活跃/软删除视频路径、扫描目录、回收站恢复路径、位于该树内的扫描黑名单路径和字幕索引，数据库更新失败时回滚磁盘名称。

### 2.9 视频重命名
- **功能:** `RenameVideo` 同时重命名磁盘文件和数据库记录（name/path）。
- **安全:** 保留原扩展名，目标文件已存在时拒绝操作，数据库更新失败时回滚文件名。扩展名规则（2026-09-29/30，D-PC12，LIB-03）：新名的扩展名为空、或不是已配置的视频扩展名时补上原扩展名（`The.Matrix.1999.1080p` 不再被当成扩展名 `.1080p`），显式改成另一个视频扩展名则照改；规范化后与当前文件名相同时直接返回、不动文件。

### 2.11 片库智能视图与统一清理

- **清理审阅决定与缓存（2026-09-20）：** 「不是同片」「不是同源」「截取片段忽略」原本已有持久记录，但重开面板直接回传分析缓存会让已处理项复现。`cleanup_review.go` 统一在 `CleanupService.Status` 回读与完整分析结束前按数据库决定过滤，读取失败明确报错、不回传未经核对的候选；过滤创建新切片，不修改共享缓存。近似重复组内有已否决配对时拆成互不重叠、两两相容的组。「不是同片/同源」同时排除截取候选，避免换类别复现；只忽略截取仍不等于否认同源。截取缓存保留计算时的私有源指纹，与 `ClipDismissal` 按原有文件版本规则匹配，重编码后的新分析仍可重新评估。前端保存成功提示「已记录」并回读过滤后的状态，按 ID 移除已处理项及失效选择，请求序号阻止保存前发出的迟到响应恢复旧行。既有决定直接复用，无需用户重做。

### 2.14 片库实时监听
- **开关:** 全局 `library_watch_enabled`。新安装默认开启；已有安装升级后默认关闭，避免大型片库未经确认就持续监听。
- **事件源（2026-09-23）：** macOS 改用原生 **FSEvents**（`library_watcher_backend_darwin.go` + `library_fsevents_darwin.h`，CGO / CoreServices），每个扫描根仅注册一个递归事件流，不枚举子目录、不逐文件持有句柄；其他平台保留 `fsnotify` 逐目录注册。macOS 无 CGO 构建明确返回不可用，不回退到 kqueue。添加、修改、删除扫描根时动态重配，无需重启。`watch_count` 表示实际注册数，前端统一显示「实时同步中（含子目录）」。
- **FSEvents 生命周期与恢复：** 原生回调只复制并投递事件，不做磁盘 IO；通道有界、不阻塞，拥塞或系统丢事件时通知服务对当前有效扫描根补扫，`MustScanSubDirs` 对指定子树补扫。每根启用 `WatchRoot`，根改名/卸载报告不可用；路径从系统真实路径映射回用户配置路径（如 `/private/var` → `/var`）。关闭先停止并排空原生 dispatch 队列，再释放 Go handle，避免回调悬空或关机死锁。FSEvents 接收整树事件，黑名单/隐藏路径在应用层过滤，补扫与稳定探测继续跳过这些子树。
- **监听黑名单（2026-09-23）：** App 将已保存的 `scan_exclude_paths` 传给 watcher，初始注册、新子树注册、事件入队和稳定探测都复用扫描排除规则。保存黑名单后重建监听范围，撤销已排除子树的监听及待处理批次，解除排除则重新注册；根本身被排除显示 `disabled/excluded`，在访问文件系统前跳过。此前监听未读取黑名单，会进入排除目录；本机 G-DRIVE 的 `hugh_` 内有指向 Docker 容器路径的失效符号链接，macOS fsnotify 注册父目录时触发 ENOENT，导致整根注册回滚。回归包含真实 fsnotify + 失效链接、嵌套扫描根、动态排除/恢复与设置保存接线。
- **合并与稳定探测:** 同一根目录 750 ms 窗口内合并事件，最多启动一个稳定探测；任何稳定探测最长 30 秒，可取消。
- **窄范围对账:** 只遍历受影响子树，不做全根目录枚举；复用现有导入、迁移检测、元数据探测和字幕索引逻辑。对账只按根目录范围查询视频记录，不加载全库。
- **迁移匹配:** 第一趟沿用全量扫描的 (文件名, 大小) 唯一身份规则，候选可覆盖全部可恢复记录；第二趟为支持改名而只按大小匹配，因规则过宽，候选被限制在本批次实际对账过的目录内，避免把无关记录的标签、评分和 AI 数据串到同大小的新文件上。
- **删除语义:** watcher 事件绝不直接永久删除文件或数据库记录；暂时消失只标记 `is_stale`。手工全量扫描的既有软删除语义保持不变。
- **状态:** 每个根目录展示 `watching / unavailable / error / disabled` 与原因码，并提供显式重试；网络盘等不支持的卷明确报错而不是假装在监听。根变为不可用时把其下记录标 `offline_root`，恢复监听后自动窄对账，另有每分钟一次的巡检（2026-09-29/30，D-PC08，见 2.7「离线与重连」）。
- **兜底:** watcher 是加速层，启动扫描和手工扫描始终是最终恢复路径。

### 2.35 存储体检（2026-10-12）
- **入口与裁决（2026-10-12 用户裁决）:** 洞察页新增「概览 / 存储体检」页签（`InsightsPage.vue` + `components/insights/StorageHealthPanel.vue`），不另开顶栏页面。四块内容：可回收空间、久未观看的大文件、转码可省空间估算、按编码/分辨率/目录的占用；顶部四张回顾页风格统计卡（总占用、可回收、久未观看、转码可省）。
- **后端:** `StorageReportService.GetStorageReport({unwatched_min_bytes, unwatched_months, unwatched_limit, transcode_limit})`（`services/storage_report.go`，App `GetStorageReport`），只读。视频口径走 `visibleVideoQuery`、图片走 `applyImageVisibility`，失效与黑名单里的不计。编码取每个视频主视频流（`media_streams` 里 `stream_type='video'` 且非封面图、流序号最小）的 `codec_name`；技术信息没探测成功过（`video_technical_metadata.probed_at` 为空，且没有视频流记录——老数据可能有流记录却没写 `probed_at`）的记「未探测」并计入 `probe` 覆盖率，探测成功但没有视频流（纯音频）的记「无视频流」；分辨率与目录分布复用洞察页的 `libraryStorageByResolution` / `libraryStorageByDirectory`。两个清单各自截断（默认 50、上限 500，列满 500 后页面不再给「显示更多」），`count`/`bytes` 按全部命中项。
- **久未观看:** 大小 ≥ 门槛（默认 2 GiB）且最后一次观看活动早于「现在 − N 个月」（默认 12）；从没看过的看入库时间（`videos.created_at`）。按大小从大到小。最后一次观看活动取四处里最晚的：`last_played_at`（桌面启动播放）、`watch_progress_updated_at`（内嵌与 Jellyfin 进度）、`watched_at`（标已看）与 `play_events.played_at`（内嵌与 Jellyfin 的有效观看只记在账本里，D-PC42）；只看 `last_played_at` 会把刚在内嵌或 Jellyfin 里看过的片列成「从未播放」（2026-10-12 独立审查 I-1）。账本只对粗筛出的候选逐行读、分批 500（SQLite 不按日期解析 `MAX()` 结果）。
- **转码估算（只估算，不做转码）:** 只看老编码（h264、mpeg4、mpeg2video、vc1、wmv、msmpeg4、h263、flv1、rv、theora、vp8、mjpeg）；HEVC、AV1、VP9 与 ProRes/DNxHD 不估。估算大小 = max(原大小 / 2, 该高度的 HEVC 常用码率 × 时长 / 8)，常用码率 SD 1.5、720p 3、1080p 6、2K 9、4K 18 Mbps；可省不足 100 MiB、时长或高度未知的不列。按可省从大到小。
- **可回收空间:** 不另算，前端（`utils/storageReclaim.js`）读视频与图片清理分析的缓存结果（`GetCleanupStatus` / `GetImageCleanupStatus`）：每组保留推荐项（original / preferred / full），其余成员算可回收；极短、极低分辨率整条算。精确重复算「确定」，其余「待确认」；同一文件落在几类时各类各算、总数只算一次。结果过期照算并标「结果可能已过期」；没分析过时给「打开视频清理中心 / 打开图片清理审阅」（命令 `library.openCleanup` / `photos.openCleanup`，后者 2026-10-12 新增，宿主页 photos），进去会自动开始分析。
- **删除:** 只有久未观看清单能勾选，勾选只保留当前列出的行（换门槛、重取后看不到的自动放掉；重取期间勾选与删除锁住，确认后再核对一遍名单，变了就中止不删）；「移到废纸篓」先弹汇总确认（条数、总大小、其中收藏或评过分的条数），再走片库同一个删除宿主 `TrashUndoBanner`（kind=video、deleteFile=true，可整批撤销）。删除或撤销后面板发 `videos-changed`，App 重取顶栏计数并调 `VideoListPage.handleVideosChangedElsewhere(removedIDs)` 按当前条件重载片库，洞察页概览也重取。删除或撤销条整批撤销进行中，洞察页页签与面板里的跳转锁住，`InsightsPage` 发 `busy-change`，App 的 `navigateTo` 拦下切页（原因是当时撤销条挂在本页上，切走会丢；2026-10-13 起撤销改为全局提示 + 「最近操作」，宿主刷新回调声明成 prop，切走后撤销也能通知片库，这把锁保留为保险，见 2.38）。部分没移到废纸篓时，失败原因在随后的重取之后补回提示（撤销条只报成功部分）。刚删掉的视频在清理分析重跑前先从「可回收」里扣掉；删掉的是某组保留项时，这一组整组先不算。清理分析结果只在打开、刷新和删除/撤销后重取（`markRaw`，带序号丢弃晚到响应），换门槛只重取体检数据；概览正在取数时被要求重取，会在这一轮结束后再取一次。转码清单只提供打开详情与打开目录。

#### 2.36.1 失联数据治理（D-LD-01..05）
- 入口：数据维护页「失联」页签（`LostMediaPanel` + `LostRelinkDialog` / `LostPurgeDialog` / `OrphanFilesSection`）；服务 `services/lost_media*.go`（`LostMediaService`），App 接线 `app_lost_media.go`。
- 失联 = 视频活跃失效行（is_stale）+ 扫描器软删且回收站条目仍是 missing 的行；图片 = is_stale 且未软删或 deleted_by=scanner。用户删除的不算。归类：卷未挂载 / 读取出错只展示；文件不见 / 目录已移除 / 不在扫描目录 / 原因未知可找回、可清除。图片原因按 hiddenImageReason 现算。按「扫描根（含已移除的根，路径前缀推断；否则其他位置）→ 目录」分组，明细按 id 键集分页。
- 找回保持记录 id：目录搬家（相对路径 + 大小，exact / size_mismatch）、在文件夹里找（name_size 默认勾 / size_only 默认不勾 / ambiguous；一个文件被多条命中都降为 ambiguous）；outside_roots / occupied 不可执行。执行在路径写锁内逐条复核；失效行走 relocateVideoFrom / relocateImage（后者已同步改 name），扫描器回收站行一个事务里取消软删 + 改路径 + 删 missing 条目（不能用 retireTrashEntryTx，它会连记录一起硬删），提交后补探测。
- 清除（确认文本「清除记录」，lost_purge_unconfirmed）：逐条复核（仍可清除、mediaPathUnavailable 为空、os.Stat 不存在、无进行中超分；事务内再确认仍失联），跳过原因 no_longer_lost / volume_offline / file_present / enhancement_active。事务内：版本组 bump 后移出、不足两人解散；删无外键引用（near_duplicate/clip/version_suggestion dismissals、face_observations+重算簇、face_relation_writes、playback_queue_entries（当前条目被删则队列回空闲、revision+1）、automation_rule_writes、同类批次的 metadata_batch_edit_items）；日记 source_play_event_id 置空；扫描器行先 retireTrashEntryTx；最后 hardDeleteVideoTx/ImageTx。提交后删派生文件（thumbnails/<id>.jpg 与 .seek.*、media-details/videos/<id>/、subtitle-backups/<id>/、faces/<crop>、image-thumbnails/<id>(.view).jpg）与播放代理，删不掉留给孤儿回收。书签与日记文本保留。
- 孤儿文件：thumbnails、image-thumbnails、media-details/{videos,people,collections,watchlist}/<id>/、subtitle-backups/<id>/、faces/<id>.jpg，按 Unscoped 判定归属（回收站中的不算孤儿），文件名解析不出 id 的不动；播放代理沿用 orphanProxyFiles（RemoveOrphanPlaybackProxies 跳过 inFlight）。壁纸副本未纳入（无当前壁纸记录可对照）。体检用 `OrphanFileTotals(ctx)`。
- 找回 / 清除 / 回收在 lost_media 任务键下同一时刻一个（lost_media_busy），可取消（CancelLostMediaTask），stopLostMedia 停止并等待。卷未挂载、读取出错的条目不给批量找回（换盘符场景需先移除旧根，使其变为 removed_root）。
- **评审修订（同日）：** 找回执行在路径写锁内复核并只做数据库改写（失效行 `relocateVideoRecord` / `relocateImage`；扫描器回收站行一个事务里取消软删、改路径、删 missing 条目并按新路径 `rebuildSubtitleIndexTx`），放开锁之后视频再补探测；探测失败或被取消不算失败。清除预览与执行共用 `purgeCheckRow` 复核：预览返回通过的 `ids` 与按原因的 `skipped`，确认框只执行这些 `ids`（执行时再复核一次）。清除删掉待播队列条目时经 `SetPlaybackQueueEmitter` 发 `playback-queue-state`。逐条等锁可取消：视频用 `lockLibraryPathsContext`（`lockLibraryPaths` 的可取消版本，已列入写锁守卫），图片用 `acquireLibraryPathContext` 包 `imagePathMutationMu`；被取消或进入维护打断的条目报 `cancelled`（未处理），不计失败，整批就此停下。播放代理孤儿回收删除前逐个复核（先看 inFlight，再看 ready 行是否正指向该文件）。找回 / 清除后发 `videos-changed`，载荷带 `kind`：视频 `{kind:'video', removedIDs}`，图片 `{kind:'image'}`。

#### 2.36.2 元数据完整度、年份与缺失筛选（D-MC-01..03）

#### 2.36.3 元数据批量编辑与撤销（D-MC-04/05）
- **入口:** 片库批量栏与图片库选择条的「批量编辑…」（所选 + 可选当前筛选），以及片库「管理 → 整理」与图片库「管理」菜单的「批量编辑当前筛选…」（不用先选中；语义检索、随机批次、相似视频、图片文件夹总览时不给），都打开共用的 `MetadataBatchEditDialog.vue`（文案与字段表在 `utils/metadataBatchEdit.js`）：范围「所选 N 项 / 当前筛选的全部结果」（语义检索、随机批次、相似视频时只给所选），逐行加操作——视频：年份设为/清空、评分设为/清空、标签/人物加去、作品集加入/移出；图片：标签、人物、评分。先试运行（2026-10-13 前叫「预览」；目标数与每项「会改变几项」），改了范围或操作试运行结果作废，再执行；结果页可撤销，执行成功也出带「撤销」的全局提示并记进「最近操作」（见 2.38）。片库折叠版本时筛选范围仍含全部版本，预览写「共 X 项（含折叠起来的其他版本）」。视频提示已知限制：清空的年份等字段会被 NFO 补全按「空就补」填回（不加逐字段锁）；有「移出作品集」时提示撤销会把视频加回作品集末尾（不记原位置）。数据维护「完整度」页签下方「最近的批量编辑」列出最近 20 次并可撤销。
- **后端:** `MetadataBatchEditService`（`services/metadata_batch_edit*.go`），App `PreviewMetadataBatchEdit` / `ApplyMetadataBatchEdit` / `ListMetadataBatchEdits` / `UndoMetadataBatchEdit`。请求 `{kind, target:{ids | filter(LibraryFilter) | image_filter(ImageFilter)}, ops:[{field, action, value, ids}]}`；校验失败 `invalid_batch_edit: 原因`（空操作、同字段多次设为/清空、同 id 既加又去、引用不存在、自动标签、年份 1870–2100 整数、评分 0–10 步长 0.5）。预览与执行共用 `computeBatchChanges`，只计/只写真正改变的（条目，字段）。筛选在执行时重新解析（片库/图片库列表同一套条件）。每 500 个目标一个事务：标量条件更新、关联 `INSERT … ON CONFLICT DO NOTHING` / 按行删除；加标签作废同条目同标签的待审 AI 候选；加人物释放这批目标上的人脸写入记录（同 AddPersonVideos）；去人物不删人物；作品集加入接末位、移出后压紧。同一事务写 `metadata_batch_edit_items`（标量记前后值；关联 before=本批去掉的 id、after=本批加上的 id）。有改变才建批次记录，只留最近 20 次（明细随外键级联删除）。
- **运行:** 执行与撤销共用任务键 `metadata_batch_edit` 与运行位，第二个请求 `batch_edit_busy`；批与批之间检查取消（只由恢复维护与退出的 `StopAndWait` 触发），已提交的批次保留并报告 processed。撤销逐行比较当前值与 after，一致才恢复，否则计入 changed_since（关联只看本批的 id；条目已永久删除或要加回的对象已不在也算）；恢复了的明细行在同一事务里删掉（item_count 与摘要不变），所以撤销被取消后再撤销只处理剩下的行；跑完才写 undone_at，再撤销 `batch_already_undone`，记录已被淘汰 `batch_edit_not_found`。
- **刷新:** 无后端事件。片库页执行/撤销后原地重载；图片库亮「图片库有更新」提示条；面板发 `videos-changed`（带 kind），App 对 image 调 `PhotoLibraryPage.markImagesChanged()`，对 video 走既有 `handleVideosChangedElsewhere`。

#### 2.36.4 本地规则自动化（D-RA-01..05）
- **裁决（D-RA-01，用户 2026-10-12）:** 规则只做「加标签」「加入作品集（仅视频）」，只加不撤；用户手动去掉的不再加回；新入库自动跑，现有内容先预览再执行；不移动、不改名、不删除。条件只看文件与技术属性（目录按路径段、文件名包含/通配/正则≤200、扩展名、大小、时长、高度、视频编码、图片有无地理位置），AND 组合、Go 侧求值；时长/高度为 0、没有视频流、EXIF 未解析视为未知 → 不满足且不写账本，补探测/补解析后再评估。自动标签不能作规则目标。

#### 2.36.5 数据体检与备份校验（D-DH-01..05）
- **备份三件套：** 每份备份 = 快照（格式不变）+ `cineinsight-<ts>.files.tar`（不压缩，收 media-details/{people,collections,videos,watchlist}、wallpapers、subtitle-backups；包内路径相对数据目录、不跟随符号链接、跳过点开头临时文件；不含 `.env` 与缓存）+ `cineinsight-<ts>.manifest.json`（format=1、backend、created_at、两个文件的 size/sha256、包内条目、schema 表→列；SQLite 另记各表行数与 quick_check）。流程：快照 → SQLite 只读 quick_check（不 ok 不发布、记失败；恢复前安全备份例外，问题写进清单）→ 空间检查（文件包预计 + 快照，不够报 `backup_insufficient_space`）→ 写包与清单 → 依次发布快照、包、清单（清单最后）。轮转按快照成组删，有包无清单的半成品与失去快照的包/清单先清掉。`ListBackups` 读清单不再全量哈希；无清单的标 `legacy`、仍可恢复。代码：`services/backup_{manifest,files_pack,publish,schema,verify,restore_files}.go`。
- **校验与恢复：** `VerifyDatabaseBackup`（backup 任务键）分 full / archive（PG：哈希 + `pg_restore --list`）/ legacy 三档，结果按备份名存 `<dataDir>/backup-verifications.json`，列表与体检读它。恢复前清单表结构有当前版本不认识的表/列 → `backup_from_newer_version`，不进维护；已知结构 = AllModels + 连接表 + PG 语义表 + 迁移标记表 ∪ 当前库实际表列（AutoMigrate 不删列，老库遗留列不能让自家备份被拒）；PG 只比表名。库替换成功后在围栏内还原文件包：解到 `<dataDir>/.cineinsight-restore-files-*` 逐条校验 → 每个目录「原目录改名 `.pre-restore-<ts>`、新目录就位」→ 删旧目录；失败不回滚库，返回 `restore_committed:` + 「数据库已恢复，整理过的文件未能还原，可从恢复前的安全备份中取回」，保留 `.pre-restore-*`。

- **评审修订（同日）：** 清单另记 `models`（做备份的版本的模型结构：AllModels + 连接表，GORM 解析，不看库里的实际列），`schema.tables` 只作参考；兼容判定 = 备份 `models` 的表与列都在当前模型结构或 `retiredSchemaColumns` 里（删除模型字段或模型时必须登记到这里）；没有 `models` 的清单按兼容处理（取代上文「∪ 当前库实际表列」）。恢复前（进入维护之前）先核对文件包：存在、大小与 SHA-256 与清单一致、每个条目可读且在清单里，否则 `backup_files_invalid`；各暂存落点空间不足报 `backup_insufficient_space`。暂存目录建在各收录目录同级 `.cineinsight-restore-<目录>-<时间>`；就位失败把原目录改回；启动时与每次还原前 `RecoverInterruptedFilesRestore` 把「目录缺失 + 有 .pre-restore-*」的最新一份改回。managed_paths 对不可用（不存在或链接失效）的 media-details 子目录只报告不判不清；face_clusters 计数修复走 `recomputeFaceClustersTx`。
- **评审修订二（同日）：** 清单另记 `unavailable_roots`：备份时存在却进不去（失效链接、没挂载的盘、`media-details` 本身失效）的收录目录不当空目录打包；设置页备份状态（`files_warning`）与列表提示。恢复时这些目录原样不动；文件包要还原的目录现在不可用时，进入维护前以 `backup_files_target_unavailable` 拒绝。有效的符号链接目录照常跟进去打包。恢复前按卷合计空间（设备号；测试注入 `volumeOf`）：备份目录要放临时副本 + 安全备份（库文件含 WAL 或最近一份转储 + 当前整理文件），库目录要放 SQLite 临时库，各收录目录的同级要放解出的条目（每个按 4 KiB 取整）；任一卷不够即 `backup_insufficient_space`，旧格式与空文件包同样检查。还原整理文件前写 `<dataDir>/.cineinsight-restore-in-progress.json`（各目录的 `.pre-restore` 名与暂存目录名），成功或改回后删除；`RecoverInterruptedFilesRestore`（启动时与每次还原前）只按标记改回，并发一次桌面通知、备份状态显示 `notice`。兼容判定用的模型结构含 Postgres 语义索引模型与两张裸 DDL 向量表；`services/testdata/model_schema_golden.json` 由 `TestModelSchemaGolden` 守住：模型新增表或列要更新快照（`UPDATE_MODEL_SCHEMA_GOLDEN=1 go test ./services -run TestModelSchemaGolden`），删掉的必须登记进 `retiredSchemaColumns`。
- **评审修订三（同日）：** 还原整理文件时先把收录目录解析到真实位置（`filepath.EvalSymlinks`）：动的是链接指向的目录，暂存目录与 `.pre-restore-*` 建在真实目录同级，链接本身保留；还原过程中目录变得不可用或位置变了就不动它、这次还原记为不完整。进行中标记 `<dataDir>/.cineinsight-restore-in-progress.json` 在建暂存目录之前写下（`staging`），开始改名前改成 `swapping`，记下真实上级、真实目录名、暂存目录名与旧目录名；恢复（启动时与每次恢复开始前）：`staging` 只删暂存目录、原目录保持原样并说明一次，`swapping` 按记下的名字把缺失目录改回；只认 `.cineinsight-restore-<名字>-` 与 `<名字>.pre-restore-` 前缀；标记收拾不完时新的恢复以 `backup_restore_recovery_pending` 拒绝。恢复前的空间检查按卷合计，解出的文件与每个目录按该卷的分配块（Statfs；Windows 4 KiB）取整；卷按设备号分组（APFS 容器、btrfs 子卷、Windows 文件夹挂载点可能偏松）。备份自身的空间检查只算还没写的文件包。列不出的收录目录也记进 `unavailable_roots`。`backup_last_error` 落库前去掉绝对路径。`TestModelSchemaGolden` 先查删除：快照里有、模型里没有又没登记 `retiredSchemaColumns` 的，连重新生成快照也会被拒绝；语义向量表的列是手工维护的，改 DDL 时要同步。已知限制：恢复前安全备份之后写入的文件不在其中；校验期间占着备份锁。
- **评审修订四（同日，取代修订三里符号链接目录整目录换入与标记的说法）：** 整理文件的还原分两种：收录目录的真实位置在数据目录里时整目录换入（同级暂存目录 → 原目录改名 `.pre-restore-*` → 暂存就位）；收录目录本身或上级是符号链接、真实位置在数据目录之外时按合并还原——文件先解到数据目录里的 `.cineinsight-restore-merge-*` 暂存目录并校验，再逐个用「同目录 `.cineinsight-restore-tmp-*` 临时文件 + 改名覆盖」写进链接指向的目录；那里不建暂存目录、不改名、不删任何东西，已有文件、点文件与子目录链接不动，路径经过子目录链接的文件跳过（记为不完整）。恢复前对这类目录做一次写入探测，写不进去即 `backup_files_target_unavailable`；空间同时记在链接所在盘与数据目录盘上。进行中标记只记数据目录里的位置（上级必须是数据目录内的规整路径），每个目录带状态（pending / swapped / aside_deleted / merged），每完成一步就重写。恢复（启动时与每次恢复前，都持有备份服务的锁）：上级目录不在、读不到、原目录与 `.pre-restore` 同时都在或都不在时留着标记与现场并说明，新的恢复以 `backup_restore_recovery_pending` 拒绝；swapping 状态一律给一次说明；已换好目录的 `.pre-restore` 只有在整个换入阶段走完时才删；还原不完整时已换好目录的 `.pre-restore-*` 保留；合并中断留下的临时文件由下次恢复清掉。
- **评审修订五（2026-10-13，取代修订四里两种还原方式与恢复收拾的说法）：** 只有真实位置在数据目录里、且里面任何一层都没有符号链接的收录目录才整目录换入（同级暂存目录 → 原目录改名 `.pre-restore-*` → 暂存就位；目录里不在备份中的文件，包括系统或应用留下的隐藏文件，会随旧目录换掉，恢复确认里写明）；其余（收录目录或上级是链接、或目录里有链接）一律合并：先解到数据目录里的 `.cineinsight-restore-merge-*` 并校验，再逐个用同目录 `.cineinsight-restore-tmp-*` 临时文件改名覆盖写进真实目录，不建暂存、不改名、不删任何东西，经过链接（目录或文件）的条目跳过并记为不完整；写入探测失败即 `backup_files_target_unavailable`；空间记在真实目录本身所在的卷与数据目录卷上。恢复收拾（持备份服务的锁）先推断再动手：pending 的换入目录暂存已不在、原目录与旧目录都在 → 按已换好处理；没有要撤回的目录不看上级在不在；判断不了的连暂存目录一起留着、留着标记。所有换入与合并都完成时才删已换好目录的 `.pre-restore`；合并目标够不着时照样删标记并在说明里提到可能残留的临时文件；清扫只在数据目录里进行。标记收拾不完时备份状态给出 `recovery_pending` 与留下副本的目录（叫法 + 相对位置），设置页「数据库备份」提供危险确认的「放弃收拾，允许恢复」（`DiscardInterruptedFilesRestore`：只删标记、不碰任何文件夹），`backup_restore_recovery_pending` 的拒绝文案指向它。已知边角（终审 Minor，内容都还在恢复前的安全备份里）：部分失败的还原在收尾清理途中被强杀，或最后一个目录改回失败后又被应用重建，下次启动的收拾可能把 `.pre-restore-*` 当成可删。放弃收拾后，`.cineinsight-restore-` 开头的临时副本会在下次启动时清掉（`.pre-restore-` 保留）。

### BT 托管文件的扫描与入库（2026-10-31）

`BTPathPolicy` 接入全量/窄扫描、直接添加、恢复、搬家匹配及刷新。托管 namespace 中尚未通过资格的文件记为 `withheld`（摘要 `bt_pending`），不能按缺失文件软删，也不能通过普通扫描提前收录。旧备份没有任务行、取消/缺失或连接离线时，目录保护仍保留。

只对已选择、客户端完成且不在校验/移动/错误状态的实际视频原位入库；导入前后核实归属、真实路径、扫描根/黑名单与文件指纹。不移动、重命名或改写做种文件。下载完成与入库完成分别显示；普通已有记录复用，用户仅删除记录后不自动复活，显式恢复沿用既有资格。新建或恢复的记录在最终核实前隔离，首次发布可恢复；查重只显示结果，不自动清理文件。完整资格、取消与安全解除规则见[设计 D-PT-06](../loopx/design/2026-10-30-prowlarr-download/需求设计文档.md#D-PT-06)。
