> 当前领域合同，属于 [AI-CONTEXT](../../AI-CONTEXT.md)。保留原节号；明确被取代的历史规则不再生效。

### 2.1 智能随机播放 (Smart Random Play)
采用自研加权随机算法 (`ALGORITHM.md`)，旨在平衡视频库的播放频率：
- **公式:** `播放分数 = 普通播放次数 * PlayWeight + 随机播放次数`。
- **逻辑（2026-10-22，D-F03）:** 随机播放、随机 N 部服务接口、今晚看什么及首页同源选片按作品抽样：已确认版本组一票，未分组视频各一票。对可访问且未删除成员（含离线历史）取最大时间衰减播放分数，再用既有低分高权重算法；增加版本不增加抽签次数。文件计数、断点、收藏与评分仍分别保存。
- **权重:** `PlayWeight` 可配置（默认 2.0）。
- **作品候选:** 收藏、时长、LibraryFilter先限制可播放成员，代表取其中position/id最前的一版；已看判断使用同作品可访问未删除成员，任一看过即算看过。排除一个版本会排除当前整部作品；硬条件与smart_view矛盾时返回空，不放宽。不依赖collapse_versions展示开关。
- **推荐反馈（D-F07）:** 「7天内不推荐」按当前作品硬排除；用户明确选择的标签权重乘0.5，命中多个只乘一次，长期有效直到撤销。`recommendation_feedbacks`持久化，创建只认唯一目标，续期/撤销带行id与revision；管理active和候选共用目标可访问性，软删/越界/黑名单目标不影响存活组。组暂避随成员变化、解散失效；单文件反馈入组时扩展到当前作品。反馈只影响选片，入口在今晚看什么，不写观看事实。
- **筛选内随机:** 主片库可在当前关键词、标签、人物、体积、分辨率和智能视图范围内随机，并排除最近 12 次随机结果；当前范围无候选时明确失败，不回退全库。语义搜索模式下随机按钮禁用（语义结果不支持随机）。
- **随机条件（2026-10-11 与「今晚看什么」合并）:** 原「均衡 / 仅未看 / 仅收藏」三种模式改为一套硬过滤条件：观看状态（探索=只抽没看过的 / 不限 / 重温=只抽看过的）、仅收藏、整片时长上限（0 不限，有上限时排除未知时长）。`RandomPlayRequest` 字段为 `watch_state`/`favorites_only`/`max_duration_seconds`/`exclude_ids`，原 `mode` 删除。工具栏只留拆分按钮：主键「随机播放 · 生效条件」立即播放一部，▾ 里是「今晚看什么…」「随机 10 部」与条件开关（时长只在弹窗里设、菜单里可取消）。
- **条件与排除表持久化（2026-09-30 D-PC44，2026-10-11 改键）:** 随机条件与「最近 12 次」排除表存在 `localStorage`（`library-random-conditions`、`library-random-recent`，只存条件与 ID 数组，读写包 try/catch），重启应用后仍然生效；旧键 `library-random-mode` 在新键缺失时迁移读入。
- **「换一个」与延迟记账（2026-09-29/30，D-PC43/44）:** `PlayRandomVideoWithFilter` 启动播放器成功后不立即写统计，而是登记全应用唯一的未决项并返回 `reroll_token`；30 秒后、下一次随机之前、进入恢复/切换维护模式之前、应用关闭时，才在同一事务里写 `random_play_count`、`last_played_at`（只前进）与 `desktop_random` 事件。30 秒内在结果条点「换一个」调 `RerollRandom(token)`：丢弃这次统计，用原筛选加上被换掉的那一部作排除再抽；令牌已提交或失效时返回 `reason_code=reroll_expired`，前端改为普通的再随机一次。全库随机 `PlayRandomVideo` 仍是启动即记账（前端未调用）。

### 2.5 预览优先浏览 (Preview-First Browsing)
- **抽屉预览:** 视频列表项支持通过右侧抽屉进行内嵌预览。
- **抽屉动作条（2026-09-30，D-PC47，PLAY-14）:** 抽屉顶部常驻「播放 / 收藏 / 点赞 / 已看」与 0.5 步进的星级评分；评分点一下即保存（`UpdateVideoRating(id, rating|null)`），不经「保存作品信息」。窄行变体（抽屉打开时的列表行）也提供「已看」切换。
- **观看闭环:** 主片库视频记录收藏、已看、观看位置和更新时间；内嵌预览每 10 秒及暂停/关闭时保存进度，播放结束标记已看。字幕命中跳转优先于断点续播位置。进度上报为 `UpdateVideoWatchProgress(id, position, duration, completed, origin)`（2026-09-29/30，D-PC42）：`origin ∈ {resume, start, jump}` 表示本次起播来源（从断点、从片头、从字幕命中或手动指定时间）；`jump` 会话只允许把断点往前推（`NOT resumable OR 位置 <= 新位置` 时才写），看完后留下的旧断点不挡重看；`duration` 只在库内时长未知时采用。
- **断点有效（D-PC42，PLAY-06 / PLAY-10）:** `resumable(v) = 位置 > 0 且（未看完，或 watched_at 为空，或这次断点写于最近一次标已看之后）`，Go 的 `resumable` / `resumableSQL` 与前端 `utils/watchState.js` 各一份、共用样例。「继续观看」、抽屉续播、IINA 起播与 Jellyfin 的 `PlaybackPositionTicks` / `IsResumable` 都按它判定，三端断点因此互通。
- **有效观看事件（2026-09-29/30，D-PC43，PLAY-07）:** 内嵌播放器在同一次播放累计播放时长首次越过 `viewThreshold(duration) = min(60 秒, 时长 × 0.5)`（时长未知取 60 秒），或判定看完时，调 `RecordViewEvent(videoID, "inline_view", sessionID)` 记一条 `inline_view` 事件（按会话在内存 LRU 去重，只追加 `play_events`）；拖动、循环回片头不算播放。它不改播放计数，也不参与随机算法。
- **「算看完」的现行口径（2026-09-29/30，R6 / D-PC41 / D-PC42；推翻上一条的 1 秒容差、「断点文件消失不判已看」、「已看直接跳过」与「只前进不后退」守卫）:**
  - **判定式:** 片尾区间 `watchCompletionTail(d) = min(d × 5%, 180 秒)`，`isWatchCompleted(position, d) = d > 0 且 position > 0 且 position ≥ d − tail`。Go 端唯一定义在 `services/library_service.go`，前端在 `utils/watchState.js`（`VideoListPage` 与 `PreviewDrawer` 共用，含 `resumePosition`），两边用同一组样例对齐。内嵌播放器、Jellyfin、IINA 三条上报路径都只调它。判定成立时照旧标已看并把断点清零，`watched_at` 只记第一次看完；手动 `SetVideoWatched(true)` 仍不动断点；历史遗留行仍不回填（下一条）。
  - **IINA 起播:** 正式播放续播时，若断点有效且找得到 `iina-cli`，以 `iina-cli --mpv-start=<秒，1 位小数>` 起播（断点可能来自内嵌预览或 Jellyfin，IINA 自己并不知道）；设置为「从头播」时走 `--mpv-resume-playback=no`；IINA 不在时退回系统默认打开方式。
  - **IINA 删除事件:** 应用发起的正式播放成功后经 `onPlaybackLaunched` 钩子登记会话（内存，12 小时过期）。watch_later 文件被删除、且对应已登记会话时，取最后已知位置 `max(库内断点, 起播位置 + (删除时间 − 启动时间))`，满足 `isWatchCompleted` 或达到时长 90% 即判看完，并发既有的 `iina-progress-synced`（`changes[].watched=true`）。两道保护：距启动的墙钟时间短于 `max(10 秒, min(60 秒, 0.5 × (时长 − 起播位置)))` 时不结算也不消耗会话（mpv 续播加载断点后可能立刻删文件）；会话期间观察到本次播放之后的写入即结束会话。未登记的删除事件照旧忽略。
  - **IINA 同步:** 先做修改时间陈旧检查——文件修改时间新于库内 `watch_progress_updated_at` 才采用，采用时进度时间写为文件修改时间——再做完成判定；完成判定之前不再有按位置幅度的守卫。已看、断点不可续且 `watched_at` 与进度时间都为空的行无法判断新旧，照旧跳过。
  - **普通 IINA 断点路径的已知限制:** 从片头连续看完但没有watch_later写入/删除，或短片不到10秒时，原断点观察可能无法结算；该默认路径未被静默替换。2026-10-22已另行提供显式选择的IINA精确同步，见下一条。
- **IINA精确同步（2026-10-22，D-F05）:** `settings.desktop_player`空/system保留原派发，iina_controlled才启动本应用私有进程。`controlled_iina.go`不持业务表，VideoService与队列各自拥有token/run，普通播放不写或清空队列；与全部队列播放器共享占用，不能抢占。实际位置累计和可信EOF驱动有效观看，暂停/seek/窗口关闭/IPC失败不冒充结束；原生重播开新cycle，正式起播计数不重复。`desktop_controlled_view`经既有会话去重和日记事务写入，公开RecordViewEvent仍只允许inline_view；私有watch_later不交旧观察器。关闭成功前保留进程、run和占用；失败显示「操作未完成/重试停止」，维护中止，迟到事实被拒绝。队列失败同样保留清理对象，用独立cleanup token重试，不能用旧Stop停止新实例。
- **历史遗留记录不回填（2026-09-13 裁决）:** 库里存在 `watch_position_seconds >= duration-1 且 is_watched=false` 的老记录（旧 IINA 夹紧、或旧代码「看完后手动标未看」留下的）。用户裁定**不做一次性回填**，让它们在下一次进度上报时自愈。理由是这两类记录在数据上无法区分，回填会把用户显式标过未看的片子又标回已看。代价是更新后这些行仍会显示「看到 X / Y」，直到再播一次。
- **直接播 + 自动代理（用户 2026-10-13 裁决，同日按评审修订，[设计](../../docs/loopx/design/2026-10-13-preview-formats/需求设计文档.md)）:** 没有有效代理时，桌面预览按实际编码判定能否直放（`services/preview_direct_play.go` 的 `decideDesktopPreview`）：.mp4 / .m4v / .mov 且容器确是 ISO-BMFF、视频 h264（8 位 4:2:0）/ hevc（标签不是 hev1）/ prores、音频 aac / mp3 / alac / ac3 / eac3 / 常见 LPCM 或无音频 → `inline` 直放源文件（mov 报 `video/quicktime`）；.webm / .ogv / .ogg 照旧；其余要代理。快照缺失时限时 5 秒补探一次（新增 `media_streams.codec_tag`），判不出就按扩展名沿用旧行为，失败按「视频 + 源指纹」记在内存里不再重探。要代理时：没有 ffmpeg 按旧行为；预计产物超过 min(10 GiB, 代理上限 × 20%) 为 `proxy-manual`（「文件较大（约 X GB）…」，只给手动生成）；否则 `proxy-preparing`，由预览宿主按 owner 自动请求代理（见 2.23「自动代理」），显示排位 / 生成中与「用系统播放器预览」，就绪后切到内嵌。直放源解码失败同样自动请求。手机端与 Jellyfin 的白名单、正式播放打开源文件都不变。
- **降级策略:** 判不出编码（探测失败）的非白名单文件，以及等代理期间与代理失败后，都可用统计中立的系统播放器预览，不污染正式播放统计。
- **资源路由:** 预览媒体通过 `preview_asset_handler.go` 暴露受控资源路径，由前端 `<video>` 使用；列表缩略图通过 `/preview/thumbnail/{videoID}` 按需生成并缓存，源文件更新后自动失效，生成失败只显示占位图。

### 2.6 播放可靠性与失效纠偏
- **统计保护:** 正式播放只在播放器成功启动之后才更新统计：`launchPlayback` 用 `open`（或 `iina-cli`）启动外部播放器，进程启动成功（`cmd.Start` 返回 nil）即算成功，结果为 `PlaybackAttemptResult.dispatch_succeeded=true`；它不代表文件真的播起来了，更不代表看了多久（因此洞察页把这类事件叫「启动播放」，见 2.18）。启动失败不会污染 `play_count` / `random_play_count` / `last_played_at`。筛选内随机在启动成功后还要等 30 秒延迟提交（见 2.1）。（旧写法把这一步叫作「dispatch success」，指的就是上述进程启动成功，PLAY-15，2026-09-30 按代码更正。）
- **明确错误:** 播放失败返回带文件名的中文错误，**不含绝对路径**（系统错误里的路径擦成 `<path>`，G-3，2026-09-30）；`PlaybackAttemptResult.reason` 归为 `offline_root`（所在磁盘未连接，提示「所在磁盘未连接，请连接后重试」）/ `missing_file` / `error`（D-PC11）。
- **失效标记:** 记录支持 `is_stale` 状态，用于表示当前路径失效/待纠偏；2026-09-29/30 起同时写 `stale_reason`（见 2.7）。
- **局部纠偏（D-PC11，PLAY-12 / LIB-13）:** 播放失败后返回窄 `reconcile result`：根离线时只标 `offline_root`、不做重定位；根在线而文件不在时标 `missing_file` 并立即返回，重定位（`findRelocatedVideoCandidate`）改在后台 goroutine 里全局串行执行，找到后调 `RelocateVideo` 并发 `video-relocated {video_id, new_path}`。前端就地把该行改为失效态（不再整页重载），提示里带「重新定位 / 查看路径失效」。
- **统计事务:** 正式播放成功后，计数递增（`play_count` / `random_play_count` / `last_played_at`）与 `play_events` 插入在同一个数据库事务内完成；事务失败只记一行日志，`PlaybackAttemptResult` 仍为成功，计数与事件都不写，两者永远一致。
- **事件产生点:** 正式派发记desktop_play，随机派发按30秒窗口延迟记desktop_random；inline_view、queue_view、desktop_controlled_view、mobile_feed、jellyfin_view是各自owner确认的有效观看。普通观看进度更新和旧IINA断点回读不产生事件；精确同步由独立owner写desktop_controlled_view，不混作inline_view。

### 2.10.1 今晚看什么（2026-10-10，2026-10-11 与随机播放合并）
- 入口在随机拆分按钮的 ▾ 菜单与命令面板（原独立按钮已移除），继承打开时的完整LibraryFilter；语义搜索、迁移、增量扫描期间不可打开。弹窗编辑的就是随机播放共用的随机条件（整片时长、探索/不限/重温、仅收藏），条件一变即重抽（分钟数300ms合并）并回写片库页；非法分钟数报错且不回写。「换一批」再排除当前这一批，抽不出新的则保留当前批并提示；「随机播放一部」关闭弹窗走工具栏主键的随机播放（结果条、换一个、延迟记账）。
- `VideoService.SuggestTonight(ctx, RandomPlayRequest, limit)`在维护闸门内用随机播放的同一套候选与均衡加权不放回抽取（与`PickRandomVideos`共用`sampleRandomVideosFrom`），排除最近12次随机结果；纯读，不写计数/事件。理由只引用真实字段（预算/未知时长、收藏、观看状态、已有评分、播放次数）。播放候选仍是普通PlayVideo(ID)。前端代次隔离旧输入响应，错误与零命中分开。

### 2.10.2 观看笔记（2026-10-10）

- 已确认的inline_view/jellyfin_view/queue_view/desktop_controlled_view及带可选view_session_id的mobile_feed，与播放事件在同一事务创建日记；持久会话摘要唯一键涵盖删除占位，LRU淘汰后仍不重复计账。自然结束后重新播放、手机重新进入是新会话，自动loop/暂停/seek不是；Jellyfin复用同一会话ID时不猜测重看，允许手动补记。旧移动请求和外部启动保留旧统计，单列播放记录。自动条目初始评分为空，手工日记不自动合并，不同步文件级评分或已看。

- 日记/书签界面50条一页，过期请求隔离；只在最新成功响应时同时提交内容、游标和历史。核对新原片时挂起编辑并保留草稿，保存中锁定字段；页面首次挂载后保留，返回刷新列表，隐藏页Escape不丢草稿。年度回顾按WatchedOn统计实际记录数，不推算观看小时。

### 2.10.3 下一集与待播队列（2026-10-10）
- 全局一条持久队列（`playback_queue_states` 固定ID=1 + `playback_queue_entries`），条目可重复、冻结加入时的作品集顺序；结构/选择/设置修改带`expected_revision`做CAS，读取按`(position,id)`游标并在Revision变化时返回`queue_changed`。容量1万项、单次显式加入≤1000个ID，超限整次拒绝。重启把运行态标interrupted并保持暂停，不自行起播。
- 播放器：系统默认（只支持手动下一项）、应用内`QueueInlinePlayer`（`/preview/queue/{32位hex token}`，以租用的文件描述符按Range服务并逐次复核源size/mtime，不暴露路径）、专用IINA进程（私有mpv IPC，keep-open=yes的`eof-reached`为结束事实，观察者每个进程只注册一次，复用进程时先读当前playlist entry再loadfile）。自动连播默认关，只有当前token/entry的可靠自然结束推进一次；暂停、停止、关闭、崩溃、加载失败、重复结束都不推进。**拖动到末尾不算自然结束**（seek后必须观察到越过落点的实际播放），返回`queue_end_ignored`且不记有效观看；迟到/重挂载的旧序号返回`queue_stale_event`，播放器暂停并提示重新播放。IINA的time-pos事件按最新值合并，其他事件保序，超过128条积压才停止控制。
- 「加入待播」按钮（`QueueActionButton`，2026-10-13）：只针对一部视频（不替换队列）时是开关——这部已在队列里显示「移除待播」（`aria-pressed`），点了按同一 revision 读完整个队列、把它的每一条依次 `remove`（revision 逐条加一，中途 `queue_changed` 就按最新队列重来，最多 3 次）；不在就「加入待播」。打开时读一次，`playback-queue-state` 事件再读，晚到的旧结果丢掉；读不到时按钮保持原样。助手在 `utils/playbackQueue.js`（`findQueueEntriesForVideo` / `removeVideoFromPlaybackQueue`）。作品集、「从本集播放」「下一集」等整批或替换队列的按钮照旧只加。
- 正式统计、有效观看与日记复用VideoService/viewEvents的context核心；维护与退出先关闭队列准入再立围栏。合同见[播放队列合同](../../docs/loopx/design/2026-10-10-media-workbench/播放队列合同.md)。真实IINA集成测试需`CINEINSIGHT_TEST_IINA=1`。
- **缩略图（2026-10-14）:** 待播队列列表的每一项与主窗口底部的当前项都显示该视频的缩略图（`/preview/thumbnail/{video_id}`，`PlaybackQueuePanel.vue`）；按 `video_id` 记取图失败（同一部片可排进队列多次），失败留一块底色占位。缩略图与片名是一个按钮（`.btn-plain`）：列表里点它发 `open-video(video_id)` 并关掉队列列表，主窗口底部的当前项点它也发 `open-video`；App 按 from=`playback-queue` 进整页详情，视频已不在片库时提示「这部视频已不在片库中，可能已删除或不在扫描目录内。」（`openVideoByID` 新增可选 `missingMessage`）。原「原片详情」按钮保留。

### 2.18 播放历史账本
- **表:** `play_events(id, video_id → videos ON DELETE CASCADE, played_at, source, created_at)`，索引 `(video_id, played_at)` 与 `(played_at)`。只追加，应用层没有任何 UPDATE / DELETE 路径；视频软删除时事件保留并继续进聚合，永久删除时级联清除。
- **迁移:** `ApplySchema` 内的 `backfillLegacyPlayEvents` 对 `last_played_at` 非空的视频各回填一条 `legacy` 事件，`NOT EXISTS` 保证幂等，两后端共用同一条 SQL；不按 `play_count` 合成多条（库里没有那些时间点）。实际插入行数大于 0 时打一行启动日志。
- **洞察改读:** `libraryWatchHeatmap` 改查 `play_events.played_at >= now-1y`，仍在 Go 侧按 `time.Local` 归并（SQLite 无 DATE 类型的老教训不变）。热力图口径由「每日有多少部片的最后播放落在这天」变成「每日播放次数」，同一部片一天播两次现在计两次。`services.LibraryStats` 新增 `total_play_events` 与 `plays_by_source`（不限一年窗口），洞察页在观看热力图旁展示，并说明累计流水包含重复播放和已软删除影片。
- **事件来源与洞察页（更新于2026-10-22）:** desktop_play/desktop_random是正式或随机派发；inline_view、queue_view、desktop_controlled_view、mobile_feed、jellyfin_view是对应owner确认的有效观看；legacy是历史补记，共八种。有效观看按实际累计阈值或可靠结束、会话去重；暂停与seek不产生额外派发。洞察、回顾、日记和序列化保留精确同步的独立来源与中文标签。两张来源列长度为32，旧数据保留；不增加controlled历史回填。
- **观看覆盖率（2026-09-11）:** 原「已看比例」仅统计 `is_watched`，与播放事件放在同卡会误导用户。主卡改为 `viewed_count / video_count`：非软删除视频中，已标记、正式播放计数 >0、最后播放时间非空、观看位置 >0 或有播放账本事件者，每部只计一次（EXISTS 避免重复事件放大；2026-09-29/30 起不再单列 `random_play_count > 0`）。仅零秒进度回报不算；分子分母 2026-09-29/30 起改为默认视图的可见范围（扫描根 + 黑名单 + 非失效）。`watched_count / watched_percent` 保持完成/手动标记口径，另显示「标记已看」。统计只读，不回填或覆盖人物/媒体观看标记；小于 0.1% 的正比例显示 `<0.1%`，避免显示为 0.0%。
- **与算法的关系:** 账本不参与随机算法，打分仍只读 `videos` 的三列（`ALGORITHM.md` 已注明）；`services/random_score_order_test.go` 用固定夹具把分数序钉死。

### 2.23 兼容性转封装代理（播放代理）
- **表:** `video_playback_proxies(id, video_id → videos ON DELETE CASCADE 唯一, source_size, source_mod_time_ns, strategy, status, output_size, last_used_at, last_error, …)`，索引 `uniq(video_id)` 与 `(last_used_at)`。**不存路径**：文件名由 `<videoID>-<sha256("size:mtimeNS") 前 16 位>.mp4` 推导。只有终态落表（ready / failed）；`failed` 行只为详情抽屉显示上次原因，不算有效代理、不计占用、不进 LRU。
- **文件位置:** 唯一位置 `~/.CineInsight/proxies/`，临时目录 `proxies/.tmp/`；产物先写临时目录，校验通过后同卷 `os.Rename` 发布。代理**不进 `videos` 表**、不写用户媒体目录、淘汰只删自己的文件。
- **策略（`playback_proxy_encode.go`，参数数组集中一处）:** 读技术快照首个非封面视频流与首个音频流：`h264|hevc` × (`aac|mp3` 或无音频) → remux（2026-10-13 起 H.264 须为 8 位 4:2:0——yuv420p / yuvj420p / nv12 或像素格式未知——否则转码） `-v error -y -i <src> -map 0:v:0 -map 0:a:0? -c copy [-tag:v hvc1] -movflags +faststart <tmp>`；否则 transcode `… -c:v h264_videotoolbox -b:v min(源码率,8000000) -vf scale='if(gt(iw,ih),min(1920,iw),-2)':'if(gt(iw,ih),-2,min(1920,ih))' -c:a aac -b:a 160k -movflags +faststart <tmp>`（按**长边** ≤1920 约束，竖屏同样不高于 1080p，永不放大）。HEVC 一律打 `hvc1`；两条路都用快照解析出的**绝对流序号** `-map 0:<v> -map 0:<a>` 只保留一路正片视频一路音频（避开封面图流与字幕流，无音频时不留空映射）。快照缺失或不新鲜先探测一次，仍不可用报 `probe_failed`。
- **八步流程与错误码:** 入队（自动路径先过 `IdleGate.Run`）→ 每项 `MediaWorkSlot.Acquire` → stat 源得指纹 A、已有有效代理报 `already_exists` → 取快照选策略 → ffmpeg 写临时 → 再 stat 得 B，A≠B 报 `source_changed` 并删临时 → ffprobe 读产物且时长与源相差 ≤2% → rename 落位、upsert `ready` 行、`enforceLimit()`。错误码：`already_exists` / `in_progress` / `source_changed` / `encode_failed`（带 stderr 尾部 2 KB，**绝对路径经 `scrubPlaybackProxyPaths` 擦成 `<path>`** 后再落表与回前端）/ `disk_full`（不触发淘汰）/ `file_missing`（顺带标 `is_stale`）/ `probe_failed` / `cancelled`（取消时正在跑与未轮到的项都记结果，计入 Skipped）。任何失败路径都清临时文件。取消后 worker 退出前再触发报 `ErrPlaybackProxyStopping`。手机端抽中视频后校验代理指纹，失效即清理并重抽；`ResolveMedia` 对白名单不命中且无可用代理的视频返回 `ErrShortFeedNoEligibleVideos`（路由 404），绝不回落源文件 MIME。
- **消费（D-004；顺序已被 2026-09-29/30 产品完善度批次改为「先查代理」，D-PC26，PLAY-05）:** `GetPreviewSession` ~~在 `inlinePreviewMIME` **不命中之后**才查代理~~ 现在**先**查有效代理、有就用（白名单命中的 mp4 也一样：扩展名是 mp4 不代表内嵌 `<video>` 解得了，用户专门生成的代理不该永远用不上），没有代理才判能否直放（2026-10-13 起按实际编码，见 2.5「直接播 + 自动代理」；此前是 `inlinePreviewMIME`）；手机端 `ResolveMedia` 仍是白名单优先（见 `docs/short-feed-lan.md`）。命中则 `mode=inline`、`LocatorValue` 仍是 `previewMediaPath(id)`、MIME `video/mp4`，并新增可选字段 `proxy: {strategy, size}`。`ResolvePreviewMedia` 解析到代理路径。手机端三个 MIME 门（`collectCandidates`、`videoDTO`、`ResolveMedia`）全部接上。**`inlinePreviewMIMEs` 一个字都没改**（`TestInlinePreviewMIMEsUnchanged`）。正式播放永远打开源文件（`TestPlayVideoNeverOpensProxy`）；内嵌预览不计播放。
- **失效与级联（D-002）:** 预览与手机端命中代理前先 `os.Stat` 源比对，不一致或产物被外部删掉就同步删文件与表行，本次按无代理处理——不做后台巡检。`VideoService.deleteVideo` 成功后调 `DeleteForVideo(id)`：软删除（回收站）与扫描对账删除都走这条；回收站恢复后要用得再次触发。
- **LRU（D-005）:** `settings.proxy_cache_limit_bytes` 默认 50 GiB（`database.DefaultProxyCacheLimitBytes`），**0 = 不限**，因此**不带 gorm default 标签**（默认非零数值列同此规则），默认值由 `ApplySchema` 新库显式行 + `migrateProxyCacheLimitSetting` 保证，负数归一化为默认。每次成功写入后与「立即整理」都跑 `EnforcePlaybackProxyLimit()`：只看 ready 行，按 `last_used_at ASC` 删到不超限，跳过保护窗口（120 s = 2 × 节流窗口）内用过的行。`last_used_at` 由预览会话与手机端媒体请求刷新，内存 map 每视频节流 60 秒，但表里的值已老过保护窗口时绕过节流强制刷新（否则「一直在播但每次被节流」的代理会被淘汰）。`GetPlaybackProxyUsage` 另扫目录统计孤儿文件（匹配命名规则但无表行）与非本应用文件数，「清空全部代理」只删匹配 `^\d+-[0-9a-f]{16}\.mp4$` 的文件并连带孤儿。`appdata` 解析失败（数据目录不可用）时代理服务的删除入口一律返回 `ErrPlaybackProxyDirUnavailable`，不在相对路径上动手。
- **触发与并发:** `CreatePlaybackProxy` / `BatchCreatePlaybackProxies` / `BatchCreatePlaybackProxiesForFilter`（服务端解析筛选成 ID）；单 worker + FIFO，批量内去重、已在处理的报 `in_progress`；「队列取空」与「翻 Running」同锁判定。登记表 key `proxy`；一轮跑完经 `DesktopNotifier` 发一条（只有成功/失败条数）。`settings.auto_compatibility_proxy` 默认 false，开启时 `runPostScanAutomation` 经 `runGatedAutoTask("proxy", …)` 对 `ScanSyncResult.AddedVideoIDs` 里不在白名单的视频入队；代理任务没有项间检查点（只在 `Run` 层过门）。
- **手机端直连上限（用户裁决 2026-09-07，`short_feed_mobile_fit.go`）:** 内嵌白名单只看扩展名，4K / 高码率 mp4 原样发给手机就会卡。现在 `ResolveMedia` 对白名单命中的源文件再过一道"手机能不能吃"的门：长边 >1920 **或** 总码率 >8 Mbps（快照总码率优先，缺快照按 大小×8/时长 估）即"重"，与代理产物规格刻意一致。重文件有有效代理就发代理字节；没有则照发源文件（总比放不了强），并在 `auto_compatibility_proxy` 打开时经 `EnqueueMobileFitCandidates`（跳过白名单筛选、只确认活跃）非阻塞排队生成，每视频十分钟最多提一次；判定结果按源指纹缓存十分钟（Safari 一次播放发很多 Range 请求）。扫描后的自动候选 `filterPlaybackProxyCandidates` 同步纳入"白名单命中但超标"的新视频，设置页开关文案随之改写。桌面端预览不受影响。同批前端修复：Feed 预取的下一条 `<video>` 从 `preload="auto"` 改为宿主控制的 `prefetchPreload`——换到新一条先 `metadata`，当前条 `canplaythrough` 后才升到 `auto`（图片为当前项时直接 `auto`），不再与正在播的视频抢带宽。
- **自动代理（2026-10-13「直接播 + 自动代理」，D-PF02..D-PF04，同日按评审修订）:** `GetPreviewSession` 只返回 `proxy-preparing` / `proxy-manual`，本身不入队。宿主（内嵌播放器、字幕工作台、版本对比每一侧；后两者经 `utils/previewProxy.js`）每次请求带一个新的 owner 令牌（实例 id + 序号，撤销只撤自己那一次；别的宿主已排的一部也照样登记）调 `RequestPreviewProxy(id, owner)` → `PlaybackProxyService.EnqueueAuto`（`services/playback_proxy_auto.go`；用户发起，不过空闲门，与手动项同一条 FIFO、不插队，策略照旧——H.264 非 8 位 4:2:0 改为转码）。服务按视频记 owner 集合：`CancelPreviewProxy(id, owner)` 移除 owner，最后一个 owner 走了才取消（排队中摘掉记 `cancelled`，处理中只取消这一项的 ctx）；要新建任务时服务端再过一次与 `GetPreviewSession` 同一个判定 `autoProxyGuard`（直放解码失败后的请求也受约束）：没有 ffmpeg 报 `auto_proxy_unavailable`、预计太大报 `auto_proxy_too_large`，都不排任务、不落记录；同时在等的自动代理最多 2 部，第三部报 `auto_proxy_limit` 拒绝；处理中刚被取消、结果未落时又被请求（自动或手动）的，结果落下后重排；做好的代理保留交给 LRU；手动入口从不被取消，手动再点一次即转成手动项。只有自动项的一轮状态带 `auto_only`：不发桌面通知，片库页不弹汇总，手动入口不因它置灰。直放源 `<video>` 解码失败时同样自动请求（经代理播放时不再请求）。用户在本次预览里删掉代理后不当场重建。待播队列播放器不用预览会话，不在此列。
- **抽屉反馈（2026-09-30，D-PC26，PLAY-04 / PLAY-05）:** 详情抽屉订阅 `playback-proxy-state`：当前视频在队列中显示「排队中（第 N 个）」、处理中显示「生成中」（`in_progress` 不再走失败文案）；本项结果为可用时自动重取预览会话、切到内嵌播放。内嵌 `<video>` 出错时显示「无法内嵌播放此文件」，给「用系统播放器预览」「生成播放代理」两个动作（2026-10-13 起同时自动请求代理）。
- **入口:** 详情抽屉技术信息区块（生成/删除此代理/状态/「经代理播放」）、行 ⋯ 菜单「增强」组、批量操作栏「为选中生成代理」、管理菜单「补全」组「为当前筛选生成代理」、设置页「播放兼容缓存」分区（2026-09-30 由「播放代理」改名，与在线资料源的「资料源出网代理」区分，D-PC59；占用/数量/上限 GiB/清空全部/立即整理/任务状态与取消）、「自动化与扫描」分区的自动开关。文案集中在 `frontend/src/utils/playbackProxy.js`。VideoToolbox 转码仅 macOS，其他平台只有 remux（有意不做软件编码回退）。

### 2.34 观看回顾（2026-10-11）
- **数据:** 视频复用只追加的`play_events`（2.18）。图片新增`image_view_events(id, image_id→images 级联, viewed_at, source, created_at)`，索引`(image_id, viewed_at)`、`(viewed_at)`；`images.view_count`（默认0）/`last_viewed_at`与事件同事务推进（`recordImageViewTx`，last_viewed_at只前进，`UpdateColumn`不碰updated_at）。来源`desktop_viewer`（照片页查看器同一张图连续显示满1.5秒且原图未加载失败，切图/关闭/离开页面取消计时）与`mobile_feed`（`ShortFeedService.recordImageView`同事务追加；互动表浏览次数仍每次+1）。同图同来源30分钟内只记一次，以库里最近事件判定（`viewed_at > at-30min`，整30分钟会再记）。软删保留事件、软删图片不再记；永久删除级联。迁移不回填，手机端旧`view_count`不合成事件。片库行与详情抽屉显示“播放 N 次”=`videos.play_count`（口径不变），查看器显示“查看 N 次”。
- **不展示无预览的媒体（2026-10-11 用户裁定）:** 已删除（回收站）或已移除（路径失效）的视频与图片没有预览图，最爱、排行、相关、新鲜度的视频与图片样本（新发现/重温/新收藏）、每月之最、实时流水与正在播放只取仍可用的媒体；总数、习惯分布与新发现/重温计数照常统计它们（新收藏计数含已移除、不含回收站）。
- **计算:** `RecapService.GetRecap({period: live|month|year, year, month})`（`services/recap_*.go`，App `GetRecap`）按`time.Local`取自然边界`[start,end)`；进行中的期次与上一期同样长的一段比（“上月同期/昨天同一时段/去年同期”），上一期为0时百分比为null。事件按窗一次读三列、Go侧归并（SQLite无DATE类型的老教训）；标签/人物/作品集Top在SQL里`JOIN`分组取前N（标签排除`COALESCE(automatic_kind,'')<>''`与软删标签），视频/图片排行与“本期最爱”同口径：次数降序→最近一次更晚→ID升序；只水合要显示的行（Unscoped，`available`标回收站/失效）。相关视频=与最爱共享非自动标签+人物+作品集个数（UNION ALL计数），只取默认视图可见、本期没播过、非自身，按共享数→评分（未评分后）→入库时间→ID，最多6；相关图片同理（标签+人物）。新发现/重温只看期内有非legacy事件的视频：本期前有任意事件（含legacy）为重温，期内首条是legacy的不算新发现；新收藏按`favorited_at`落在期内且仍收藏；评分没有时间戳，改报期内带评分的观影日记条数。称号阈值含边界（夜猫子0–5点≥30%、周末≥60%、重温/探索≥50%、连续≥7天、标签专一≥40%、图片控看图≥播放），占比类分母≥3，最多3个，全不满足给只陈述条数的“记录者”，空期不出称号。实时附加今日流水30条、近7天、正在播放（队列`starting/playing/dispatched`当前项，否则2小时内最后一条播放）。不推算时长。
- **新鲜度单选（2026-10-13）:** 新鲜度四张卡（新发现/重温/新收藏/观影日记评分）是单选（`role=radiogroup`，卡片是`.btn-plain`按钮，`aria-checked`，←/→/↑/↓循环、Home/End，焦点跟着选中项；钩子`recap-fresh-new|rewatched|favorites|diary`，横排`recap-fresh-samples`，空行`recap-fresh-empty`），默认新发现，换期次保留选择；只有选中那张用强调色，下面横排换成这一类的样本（副标题本期新发现/本期重温/本期新收藏/本期日记评分，横排统一16:9裁切）。`RecapFreshness`只增不改地加了`rewatched_samples`（`RecapVideo`）、`new_favorite_samples`（`RecapNewFavorite{kind: video|image, id, title, favorited_at, available}`）、`diary_rated_samples`（`RecapDiaryRated{id, title, rating, watched_on, video_id|null, video_available}`），与`new_samples`一样最多6个、永远是数组（空期也是`[]`）。样本与计数同口径：重温只取仍可展示的视频，按期内最后一次播放从近到远（并列ID小的在前）；新收藏只取未失效的（计数含失效、两边都不含回收站），视频与图片各按`favorited_at DESC, id DESC`取6再合并（同一时刻视频在前）；日记按`watched_on DESC, id DESC`（走`idx_diary_day`），日记本身不过滤，`video_available`=关联视频未删除且未失效。`new_samples`顺序不变（排行顺序）。点击：视频进整页详情（`open-video-id`），收藏里的图片开查看器（`open-image`，同今日流水的`openFeedItem`），日记有仍可用的关联视频进详情，否则`navigate('viewing-notes')`去片单「观看笔记」（默认就是观影日记；「观影记录」是榜单已看，不是日记）。计数为0仍可选中，下面一行「这一期没有{类别}。」；有计数但样本为空（都已不在库中）给一行「这 N 部都已不在库中，记录仍然保留。」。新鲜度只在空期之外计算，实时分段页面不展示新鲜度（后端照样给）。
- **刷新:** 所有播放事件写入点（正式/随机延迟提交/内嵌与Jellyfin/队列观看/手机端）与图片查看在提交后调用`notifyRecapActivity`，App把它转成事件`recap-activity`；回顾页仅在实时分段且页面可见时防抖600ms刷新，另每60秒兜底。
- **页面:** 顶栏“片单”组“回顾”（`RecapPage.vue`+`components/recap/*`，首次进入才挂载）。实时/月度/年度分段，月度年度可前后翻期（不越过当前期），请求代次丢弃晚到响应。最爱大图用`/preview/frame/{id}?ms=&w=960`在时长10/30/50/70/90%取帧逐张预载、交叉淡入+Ken Burns，失败退缩略图；数字滚动、进入视口淡入（`v-reveal`）；称号卡、相关视频横排、Top10海报墙、标签云、人物/作品集、图片马赛克、24小时径向钟、日历热力、新鲜度、年度“每月之最”胶片条与每季标签。`prefers-reduced-motion`下全部静止。点视频开详情抽屉，点标签回片库只按该标签筛选（`VideoListPage.applyTagFilterCommand`），点图片去图片页定位并开查看器（`PhotoLibraryPage.locateImage`，不在已加载结果里时清筛选按文件名搜），点人物/作品集走命令面板的实体入口；年度附“查看观影日记”，观看笔记的日记年度回顾口径不变。设计与实现记录见[观看回顾概要设计](../../docs/loopx/design/2026-10-11-viewing-recap/概要设计.md)。
- **查看全部（2026-10-14）:** 页面上的数字比列出来的多时给「查看全部 N 部/张/条/个」（只在 total > 列出数时出），打开 `components/recap/RecapListDialog.vue`（`DialogShell`，每页 60 +「加载更多」，请求代次丢弃晚到响应）：新鲜度四类（选中那张卡的横排下面；样本全不在库时也出）、Top 10（「看过的视频」）、最常看的图片、今日流水、标签、人物、作品集。后端 `ListRecapItems({period, year, month, kind, offset, limit})`（`services/recap_list*.go`；limit 默认 60、上限 200；kind = `new|rewatched|favorites|diary|videos|images|feed|tags|people|collections`，未知报 `recap_list_kind_invalid`，负 offset 报 `recap_list_offset_invalid`）返回 `{kind, total, offset, has_more, videos, video_ranks, image_ranks, favorites, diary, feed, tags, entities}`（各数组恒非空）。全量列表与页面数字同口径：**含已不在库中的项**（`available:false`，弹窗里置灰写「已不在库中」、不可点），顺序同样本/排行；分类、流水、收藏、日记与三类排行和 `GetRecap` 共用同一套代码（排行查询改为带 offset/limit 并回总数）。`RecapResult` 加性新增 `top_tags_total` / `top_people_total` / `top_collections_total`；流水总数即 `overview.plays + overview.image_views`。期内看过的视频（图片）全都不在库中时 Top 区块（图片区块）照样出，写「这 N 部（张）都已不在库中，记录仍然保留。」并留「查看全部」。空期 `ListRecapItems` 对新收藏/日记仍回真实数（页面空期不显示新鲜度，看不到差异）。「相关视频还有」「相似的图片还有」是推荐、不写数量，仍最多 6 个。

### 2026-10-29 播放与删除体验补正
- 用户反馈刚打开内嵌播放就片尾：普通续播现在按媒体实际duration复核现有片尾阈值，尾部/超时长断点从0起播，显式字幕/书签跳转仍保留原规则；队列同样复核，外部播放器不变。
- 先前用controlslist/CSS隐藏原生全屏不能保证实际WebKit仅一个入口。详情/抽屉及队列改用PlaybackControls，video不启用原生controls；单一全屏入口提供应用内全屏（外壳HTML dialog.showModal）和系统全屏（内层surface Fullscreen API），保持同一video节点、source与位置，Esc只退出本层。控制区与字幕布局已由下节2026-10-30修订，进度条获焦后仍复用方向键/空格规则。
- 用户要求记住废纸篓选择，替代此前单媒体确认默认强制不勾。上次确认值写入既有delete_original_file；取消不写，读取每次重开刷新。RememberDeleteFileChoice专用方法只更新这一列，成功事件同步App现有设置快照，不用整份设置覆盖。偏好保存失败提示但按本次确认值执行删除。
- 单媒体删除确认Teleport每次准备完成后新挂到body末尾，撤销宿主独立保留；避免复用旧容器导致新图片大图覆盖确认框。确认保存偏好期间锁表单/取消/Esc，外部目标变化使旧确认失效，事件与片库宿主冻结IDs和names。
- 设计与接口见 docs/loopx/design/2026-10-29-player-delete-fixes/。

### 2026-10-30 播放器控制层与样式
