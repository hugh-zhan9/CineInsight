# 浏览器插件与桥接下载

浏览器扩展在 `browser-extension/`，装法与用法见那里的 `README.md`。这一篇讲桌面端这一侧：
桥接通道是什么、边界划在哪、下载的东西怎么进片库。

## 这条通道和手机端 feed 不是一回事

两条通道长得像，边界完全不同，不要照着其中一条去理解另一条。

| | 手机端 feed（`docs/short-feed-lan.md`） | 浏览器插件桥接 |
| --- | --- | --- |
| 监听地址 | `0.0.0.0`（局域网可达） | **只有 `127.0.0.1`** |
| 端口区间 | 18088..18108 | 18110..18130 |
| 鉴权 | 没有 | **每个请求都要令牌** |
| 能做什么 | 浏览、点赞、删除已有媒体 | **让桌面端去取任意地址并往磁盘写文件** |
| 默认状态 | 随应用启动 | **默认关闭**，用户显式打开 |

差别的根源在最后两行：feed 那条的边界是"同一 WiFi 下知道地址的人能看能删"，这是已知
且被接受的；桥接能让桌面端按外部请求去取任意 URL 并落盘，风险等级不同，所以它三道闸
一起上。

## 三道闸

1. **只绑环回地址**。局域网上根本连不到这个端口。代码里还留了一次 `RemoteAddr` 环回校验
   作为纵深防御——将来谁改了绑定地址，那一条会立刻把非本机来源挡住。
2. **令牌**。除 `GET /bridge/v1/ping` 外每个请求都要带 `X-CineInsight-Token`，用定长比较
   （按字节短路比较会把令牌的正确前缀长度泄露给能计时的调用方）。令牌为空时服务干脆不启动：
   没有闸门的桥接不如不开。
3. **Origin 白名单**。带 `Origin` 的请求只放行 `chrome-extension://` 与 `moz-extension://`。
   这一条专治"任意网页借环回地址驱使桌面端下载"：网页发不出带自定义头的简单请求，
   预检会先撞在这里。

`ping` 不要令牌是必须的——插件得先认出"这个端口后面是 CineInsight"才谈得上配对。也正因为
它不要令牌，回包里只有 `app` 与 `protocol` 两个字段，不带版本、路径、库信息。

## 令牌

由桌面端生成（24 字节随机数的 base64url），用户手工复制到插件。不做自动配对，也不做局域网
发现广播。

**令牌有意不走通用的设置保存**：`UpdateSettings` 不给 `browser_bridge_token` 赋值，它只由
`RegenerateBrowserBridgeToken` 写。否则前端任何一次漏带该字段的提交都会把令牌抹成空，
已经配好的插件会在用户毫不知情的情况下断开。重新生成时旧令牌立即失效，界面必须说明这件事。

## 接口

| 方法 | 路径 | 令牌 | 说明 |
| --- | --- | --- | --- |
| GET | `/bridge/v1/ping` | 否 | 回 `{"app":"cineinsight","protocol":1}` |
| GET | `/bridge/v1/downloads` | 是 | 任务列表 |
| POST | `/bridge/v1/downloads` | 是 | 建任务 |
| POST | `/bridge/v1/downloads/{id}/cancel` | 是 | 取消任务 |

请求体纪律与手机端 feed 同口径：必须 `application/json`、限 1 MiB、**拒绝未知字段**、
只能有一个 JSON 值。拒绝未知字段意味着插件与桌面端的载荷字段必须逐字对上，对不上会立刻
报错而不是静默丢字段。

## 传进来的东西一律不可信

外部请求最终会变成一条 ffmpeg 命令，所以入口校验是这条链路上最要紧的一段：

- **协议只认 http/https**。ffmpeg 认得 `file:`、`concat:`、`pipe:` 等一堆协议，放任协议
  等于把"读本机任意文件"的能力交出去。命令行上还带了 `-protocol_whitelist`，**其中不含
  `file`**：HLS 的分片与密钥地址都来自播放列表，一份恶意播放列表把分片 URI 写成
  `file:///…` 就能让 ffmpeg 去读本机文件、把内容混进产出的视频里，而那个产出还会被自动
  扫描入库。这个选项在 `-i` 之前，只作用于输入侧，不影响输出文件的写入（已实测）。
- **请求头值里不许有 CR/LF**。`-headers` 是一整段 CRLF 分隔的文本，值里带换行就能多塞
  任意请求头。
- **参数直接给 exec，不经 shell**。地址里的引号、分号、反引号都只是普通字符。
- **文件名清洗后只能落在下载目录里**。占名用的是 `.part` 临时文件而不是最终文件：下载目录
  通常就是扫描目录，预先建一个空的 `.mp4` 会被扫描当成一条 0 字节的视频记录入库，应用被强制
  退出时它还会永久留在那儿；`.part` 不在任何视频扩展名白名单里。改名那一刻再用 `O_EXCL` 抢
  最终名字，被别人占了就另起一个，任何情况下都不覆盖已有文件。

## 队列与入库

- 队列自成一档并发（1–4，默认 2），**不进空闲门也不占 `MediaWorkSlot`**。空闲门只挡自动
  触发的任务，而这些是用户在浏览器里点出来的；`-c copy` 是网络与 IO 密集而非 CPU 密集，
  排进重媒体槽会被超分、转封装那类长任务饿死。
- 下载用 `ffmpeg -c copy` 无损转封装，HLS 落成 `.mp4`，直链保留原扩展名。进度从
  `-progress pipe:1` 的 `out_time_ms` 解析（这个字段名叫 ms、给的其实是微秒，是 ffmpeg 的
  历史遗留）。
- 落盘后调既有的 `SyncAffectedDirectories` 把下载目录追平进片库，缩略图与技术信息因此都走
  正常路径产生。**下载目录不会自动加进扫描目录列表**——那是用户的决定。目录不在扫描范围内
  时，任务会如实报「文件已保存，但没有入库」，而不是把它说成下载失败。
- 下载失败与入库失败在任务上是两个不同的字段。文件已经在盘上了就不该被说成下载失败。

## 设置项

| 列 | 默认 | 说明 |
| --- | --- | --- |
| `browser_bridge_enabled` | false | 零值即默认，不需要迁移 |
| `browser_bridge_token` | `''` | 只由 `RegenerateBrowserBridgeToken` 写 |
| `browser_download_directory` | `''` | 为空时拒绝建任务 |
| `browser_download_concurrency` | 2 | 0 在这里是非法值而非"不限"，所以可以带 gorm default |

## Cookie 的去向

勾了「推送时附带 Cookie」之后，Cookie 会作为 `-headers` 的一部分进入 ffmpeg 进程的命令行
参数。同一台电脑上同一用户的其他程序能通过进程列表看到它（Linux 上还有
`/proc/<pid>/cmdline`）。ffmpeg 没有"从文件读请求头"的入口，这一点在桌面端这一侧消除不掉，
所以插件那边默认关闭这个开关，并在选项页写明了代价。

## 已知边界

- 直播流没有终点，桥接同样不接。
- DRM 保护的流（SAMPLE-AES、Widevine、FairPlay）在插件侧就被判为不可下载，不会推过来。
- 桥接下载的进度只有"已处理时长"，没有百分比：HLS 的总时长要额外探测一次才知道，
  当前没有做这一步。任务对象上因此**没有**总时长字段，界面也不会拿它算出一个假的百分比。
- 「入库中」的任务给不出取消：那一步是扫描，不接受取消。
- 桥接会去取插件推来的任何 http(s) 地址，其中包括私网与环回地址。这是"下载这条流"这件事
  本身的含义，也是本机媒体服务器能用的前提，因此没有加地址段限制；闸门在令牌与只绑环回
  这两条上。
