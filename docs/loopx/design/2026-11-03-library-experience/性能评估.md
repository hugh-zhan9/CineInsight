# 搜索性能评估（2026-11-04）

本轮保留现有查询和生产索引，不加入候选排序索引。SQLite 候选改善了稀有词和无匹配扫描，但使两个分组查询变慢；PostgreSQL 已有的 trigram GIN 能处理稀有词，新增排序索引没有形成足以抵偿体积和写入成本的整体收益。此结论仅针对下述合成负载。

## 环境与测量边界

- 同一台 Mac17,2，16 GiB 内存，macOS 27.2（26B123），darwin/arm64，Go 1.24.9，desktop,production 标签。agent-go 串行锁，GOMAXPROCS=2、包并发1、测试并发2、nice10、GOMEMLIMIT=2GiB。
- SQLite 使用项目实际 go-sqlite3 驱动与 SQLiteDSN；PostgreSQL 18.3 为本机 Docker 隔离实例，CPU2、内存1GiB、数据 tmpfs768MiB、shared_buffers32MiB。两者存储介质不同，不能据此宣称 PostgreSQL 比 SQLite 快多少。
- 0、100、1万、10万、100万字幕段，每片1000段；有效影片按原筛选排除每29片的失效项和每37片的软删除项。共同文本含“人生”；每10段含“海边日落”，每7段 MiXeD，每11段中文标点，每13段含 `% _ \`，每100003段含稀有词。人物、标签、收藏、未看、时长组合按确定性规则生成，源码可复现。
- 每后端5规模 × 2索引配置 × 13查询组 × 2连接温度 × 30样本，共7800个计时样本。warm 预热一次；connection_cold 每次关闭空闲连接并建立新独占连接，包含连接建立成本。没有清理操作系统页缓存、SQLite文件缓存或 PostgreSQL shared buffers，故不是物理冷盘测试。
- 计时覆盖生产 dialogueMatches 共享条件生成与 SQL 执行，采用分组21行、平面51条和片内31条的第一页形态；不包含字幕文件核对/重建、每组二次取命中、覆盖率查询、源指纹、Wails传输和UI渲染。不能把结果当作页面端到端延迟。
- p50/p95 采用排序样本下标 floor((n−1)×p)；样本完整保留。内存是查询 TotalAlloc 中位数及批次末 Go heap/RSS 快照，不是峰值；PG服务端内存不包含在Go RSS中。每配置在测量后写入/删除30批×100段，表中为单批中位数。

## 候选与语义核对

current 为现有模型索引；PostgreSQL 同时包含生产已有的 `GIN (LOWER(text) gin_trgm_ops)`。ordered_candidate 只在临时库加 `(video_id DESC, start_time_ms ASC, id ASC)`，不改应用生产迁移。

两种配置、全部规模与查询组都逐条取完整结果，与独立字面子串匹配参考结果比较 ID、video_id、起止毫秒的 SHA-256 和条数；全通过。另核对改词、段删除/恢复、影片软删除/恢复，结果无幽灵命中，位置不变。空库只验证空结果，不伪称做过行变更。

实际打包相同的 Go 标签下，SQLite compile_options 没有 FTS5，CREATE VIRTUAL TABLE ... USING fts5(... trigram ...) 失败，故本轮没有可运行的 FTS5 候选。也不通过增加编译标志改变发布构建。即便启用，trigram MATCH 对少于3个Unicode字符不匹配，带 ESCAPE 的 LIKE 不能利用其索引，不能直接替换本项目字面子串语义。[SQLite FTS5 官方说明](https://sqlite.org/fts5.html#the_trigram_tokenizer)。PostgreSQL现有GIN对LIKE的支持见 [pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html)。

## 查询计划与取舍

- SQLite 当前按 video_id 索引定位，再做 LOWER(text) LIKE，部分排序用临时B树。候选减少部分排序/读取成本，百万段稀有词p95约185.54→127.56ms、无匹配181.50→110.57ms；但常见词分组2.88→4.47ms，组合分组2.81→4.61ms。没有一致收益，不把新索引加入每个安装。
- PostgreSQL 稀有词实际走现有GIN Bitmap Index Scan；常见词分组走video_id索引与Merge Join，组合分组走可见视频/标签/人物筛选后Nested Loop。候选的稀有词/无匹配没有改善，组合查询也基本不变；增加索引体积与写入维护不划算。
- 固定先current后candidate的顺序可能产生缓存或负载偏差；合成文本长度短且重复性高，不能代表任意长字幕或真实片库分布。未测试深页、多个并发用户或磁盘冷启动。结论是本轮证据不足以采用候选，不是永久证明所有优化无效。

## 复现

在仓库根目录执行；仅用于临时 SQLite 或专用 PostgreSQL 测试库；dbtest 创建隔离 PG schema，ANALYZE 会刷新该测试库的统计。PG DSN应指向专用测试实例，不能填真实片库连接。

```sh
bash scripts/search_performance.sh /tmp/cineinsight-perf-sqlite.json
CINEINSIGHT_TEST_PG_DSN='<专用测试库 DSN>' bash scripts/search_performance.sh /tmp/cineinsight-perf-postgres.json
# 快速核对空库与小库：
CINEINSIGHT_SEARCH_PERF_ROWS=0,100 bash scripts/search_performance.sh /tmp/cineinsight-perf-smoke.json
```

普通 go test 默认跳过评估。显式运行必须给输出路径，规模超出0..1000000拒绝。原始数据：[SQLite](performance-data/sqlite.json)、[PostgreSQL](performance-data/postgres.json)；实现：[合成评估测试](../../../../services/search_performance_test.go)、[运行入口](../../../../scripts/search_performance.sh)。

本轮完整命令退出0：SQLite services64.801s；PostgreSQL services56.265s。两个后端各260组统计、10组状态完整性记录，全部结果一致。
