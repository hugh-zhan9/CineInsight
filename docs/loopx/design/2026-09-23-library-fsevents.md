# macOS 目录监听改用 FSEvents

## 问题与实现

fsnotify 在 macOS 上使用 kqueue，注册目录时为其文件逐一打开句柄。G-DRIVE 上的大量图片使应用报 `too many open files`；报错文件只是触及限制的那一项。

macOS 现在使用原生 CoreServices FSEvents，每个扫描根一个递归事件流。注册不遍历目录树，不打开媒体文件，无新增 Go 依赖。Windows/Linux 保持 fsnotify；macOS 必须启用 CGO，不提供 kqueue 回退。

沿用现有增量对账、750ms 合并窗口、稳定探测及排除规则。FSEvents 回调本身不访问磁盘，事件在应用层按扫描根、黑名单、隐藏路径过滤。新目录天然包含在事件流里；根改名或卸载后显示不可用，由用户重试。系统真实路径映射回配置路径，覆盖 macOS 的 `/var` 与 `/private/var` 差异。

系统 `MustScanSubDirs` 触发子树补扫，系统丢事件或本地有界队列溢出触发有效根补扫，不把事件遗漏当作成功。原生回调不阻塞投递；关闭先停止并排空 dispatch 队列，随后释放 Go handle 和通道。CoreServices 的内部句柄可能异步回收，循环关闭测试等待其完成后核对数量。

黑名单的保存、移除、根被完全排除、嵌套扫描根与失败后重试均保留。`watch_count` 是实际注册数；页面只展示「实时同步中（含子目录）」，避免将一个递归根误报为只覆盖一个目录。

## 验证

- macOS 真实事件：多层新目录、文件创建/改写/重命名/删除、根改名、移除/重注册、关闭后拒绝添加。
- 12,000 个真实文件和失效符号链接：进程描述符由 6 增至 18（增长 12，含 CoreServices 初始资源）；完成 20 次启动/关闭后回到预热基线 17，无按文件数量增长。
- 满事件通道下的原生回调与关闭：无阻塞，溢出触发补扫。
- G-DRIVE 实盘只读注册：一个递归事件流，约 42–47ms；不遍历、不修改原盘文件。可用 `CINEINSIGHT_TEST_FSEVENTS_ROOT` 指定其他挂载根复测。
- 定向 Go race 回归覆盖监听、黑名单、应用设置接线及新增 FSEvents 测试；设置页组件测试 58 项。
- Wails `darwin/universal` 构建覆盖 arm64/x86_64；Windows 服务包交叉编译覆盖原 fsnotify 路径。

未主动卸载用户硬盘；卸载标志映射与根改名事件有覆盖，不将其表述为已完成物理拔盘验收。
