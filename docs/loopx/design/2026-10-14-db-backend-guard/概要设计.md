# 数据库后端回落保护 · 设计

状态：已实施（2026-10-14）。Accepted——用户 2026-10-14「需要增加保护」（同意此前的提议：记下上次用的后端，读不到 PostgreSQL 配置时停下来，而不是悄悄建一个空的本机库）。
来源：用户 2026-10-13「拉取最新代码打包之后数据都没了，全变成 sqlite 数据库了？我之前是 pg 呀」。排查结论：选库规则多版本未变；PostgreSQL 配置（PG_HOST 等）放在旧应用包或别处，安装脚本替换应用包后没再读到，于是按规则走到默认的 SQLite，打开了一个新的空库。
相关：选库规则 `database.ResolveBackend`（D-001）、应用内切换后端（[产品完善度 D-PC55](../2026-09-29-product-completeness/概要设计.md)）、配置文件加载顺序 `envConfigPaths`。

## 问题

`ResolveBackend`：DB_BACKEND 显式给出就用它；否则有 PG_HOST 就用 PostgreSQL，再否则用 SQLite。PostgreSQL 用户只要某次启动没读到 PG_HOST（配置文件随应用包被替换、换了启动方式、环境变量没带上），就会静默落到 SQLite，`openBackend` 顺手建出一个空库。用户看到空片库，以为数据丢了。

## 决定

<a id="D-DBG-01"></a>
**D-DBG-01 · Data Contract · Accepted**：每次数据库成功打开并建好表之后，把这次的后端记在数据目录下的 `backend-state.json`：`{ "backend": "postgres"|"sqlite", "location": "…", "updated_at": "RFC3339" }`。location：PostgreSQL 写 `user@host:port/dbname`（不含密码），SQLite 写库文件路径。原子写（临时文件 + rename）；写失败只记日志，不影响启动。

<a id="D-DBG-02"></a>
**D-DBG-02 · Behavior Contract · Accepted**：启动时拦下「隐式回落」。同时满足以下三条时，不打开、也不创建 SQLite 库文件，启动以原因码 `backend_fallback_blocked` 失败：
1. 本次解析结果是 SQLite；
2. 不是显式选择：加载完所有配置文件后 `DB_BACKEND` 仍为空（走的是「没有 PG_HOST 就用 SQLite」这条默认）；
3. `backend-state.json` 记的上次后端是 postgres。

不拦：`DB_BACKEND=sqlite` 显式给出（含应用内切换写下的配置）；没有记录（新装、旧版本升级后的第一次）；PostgreSQL 连不上（本来就是启动错误，不回落）；SQLite → PostgreSQL（新出现 PG_HOST 是配置 PostgreSQL 的标准做法）；恢复备份后的重连（沿用启动时的解析结果）。

<a id="D-DBG-03"></a>
**D-DBG-03 · Behavior Contract · Accepted**：启动出错页对这个原因码给专门的说明与出口：
- 说清发生了什么：「上次用的是 PostgreSQL（user@host:port/dbname），这次没有读到 PostgreSQL 配置，为了不打开一个空的本机库，已经停下。数据还在 PostgreSQL 里。」
- 列出这次读过的配置文件位置（按优先级，标明哪个存在），指明推荐放配置的位置是数据目录下的 `.env`（如 `~/.CineInsight/.env`），写好后「重新打开」。
- 另一个出口「这次改用本机 SQLite」：二次确认（写明会打开本机库、可能是空的，PostgreSQL 里的数据不受影响，之后想回去把配置放回并重启即可）→ 把记录改成 sqlite → 重启应用。不写任何 `.env`。
- 文案按统一设计用语；按钮与对话框用公共组件。

<a id="D-DBG-04"></a>
**D-DBG-04 · Interface Contract · Accepted**：
- `database`：判定函数（纯函数，输入：解析结果、DB_BACKEND 是否非空、记录）与记录的读写；`Init` 在打开之前判定、在 `ApplySchema` 成功后写记录；拦截返回可识别的错误（原因码前缀 `backend_fallback_blocked:`，与现有 `backend_env_locked:` 同一写法）。
- 绑定：`GetStartupBackendGuard()` 返回 `{ blocked, previous_location, config_files: [{ path, exists }], data_dir_config }`；`AcceptSQLiteAfterFallbackBlock()` 只在 blocked 时可用：写记录为 sqlite 后走现有 `RelaunchApp`。
- 前端：`App.vue` 启动出错页按 `GetStartupBackendGuard().blocked` 显示专门内容。

## 实施备注（2026-10-14）

- **待裁决**：数据目录下的 `.env` 只有带 `PREVIOUS_BACKEND` 才会被启动加载（APP-02 M-1，`database.BackendConfigAdoptable`；为的是不采用 09-01 旧版本写下、当年从未生效的 `DB_BACKEND`）。按 D-DBG-03 的推荐只往里写 `PG_*`，这份文件整份被跳过，重开后仍读不到 PostgreSQL 配置、仍会被拦。出错页按本设计实现，加载规则未改，等裁决。
- 「写好后『重新打开』」做成出错页上的「重新打开」按钮，调现有 `RelaunchApp`；「这次改用本机 SQLite…」用 `confirmAction` 二次确认。读到回落保护结果之前出错页的两张卡片都不画，被拦下时不先闪一下通用的「数据库连接失败」。
- 记录读不出（坏文件、权限）时按没有记录处理并记日志；「这次改用本机 SQLite」写记录失败时不重启，把错误交回出错页。
