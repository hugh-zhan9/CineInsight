# 数据库后端回落保护 · 设计

状态：已实施（2026-10-14）。Accepted——用户 2026-10-14「需要增加保护」（同意此前的提议：记下上次用的后端，读不到 PostgreSQL 配置时停下来，而不是悄悄建一个空的本机库）。
来源：用户 2026-10-13「拉取最新代码打包之后数据都没了，全变成 sqlite 数据库了？我之前是 pg 呀」。排查结论：选库规则多版本未变；PostgreSQL 配置（PG_HOST 等）放在旧应用包或别处，安装脚本替换应用包后没再读到，于是按规则走到默认的 SQLite，打开了一个新的空库。
相关：选库规则 `database.ResolveBackend`（D-001）、应用内切换后端（[产品完善度 D-PC55](../2026-09-29-product-completeness/概要设计.md)）、配置文件加载顺序 `envConfigPaths`。

## 问题

`ResolveBackend`：DB_BACKEND 显式给出就用它；否则有 PG_HOST 就用 PostgreSQL，再否则用 SQLite。PostgreSQL 用户只要某次启动没读到 PG_HOST（配置文件随应用包被替换、换了启动方式、环境变量没带上），就会静默落到 SQLite，`openBackend` 顺手建出一个空库。用户看到空片库，以为数据丢了。

## 决定

<a id="D-DBG-01"></a>
**D-DBG-01 · Data Contract · Accepted**：每次数据库成功打开并建好表之后，把这次的后端记在数据目录下的 `backend-state.json`：`{ "backend": "postgres"|"sqlite", "location": "…", "updated_at": "RFC3339", "postgres": { "host", "port", "user", "dbname", "sslmode"?, "timezone"? } }`。location：PostgreSQL 写 `user@host:port/dbname`（不含密码），SQLite 写库文件路径。`postgres` 只在 PostgreSQL 记录里有（D-DBG-05 预填配置块用），永远不含密码，`sslmode`、`timezone` 只在 `PG_SSLMODE`、`PG_TIMEZONE` 显式给出时记；较早写下、没有 `postgres` 的记录照常读，按不知道处理。原子写（0600 临时文件 → fsync → rename → fsync 目录，目录 fsync 失败只记日志）；写失败只记日志，不影响启动；`ApplySchema` 失败时不写。

<a id="D-DBG-02"></a>
**D-DBG-02 · Behavior Contract · Accepted**：启动时拦下「隐式回落」。同时满足以下三条时，不打开、也不创建 SQLite 库文件，启动以原因码 `backend_fallback_blocked` 失败：
1. 本次解析结果是 SQLite；
2. 不是显式选择：加载完所有配置文件后 `DB_BACKEND` 仍为空（走的是「没有 PG_HOST 就用 SQLite」这条默认）；
3. `backend-state.json` 记的上次后端是 postgres。

不拦：`DB_BACKEND=sqlite` 显式给出（含应用内切换写下的配置）；没有记录的大多数情况（见下）；PostgreSQL 连不上（本来就是启动错误，不回落）；SQLite → PostgreSQL（新出现 PG_HOST 是配置 PostgreSQL 的标准做法）；恢复备份后的重连（沿用启动时的解析结果）。

首次运行缺口（集成方 2026-10-14 裁定，评审 Minor 1）：升级后的第一次启动还没有记录，恰好这次又丢了 PostgreSQL 配置时上面三条拦不住。所以没有记录时另加一条：本次是走默认得到的 SQLite（1、2 同上）、本次的 SQLite 库文件不存在、而数据目录里已经有只有数据库用起来之后才会出现的数据——`thumbnails`、`image-thumbnails`、`media-details`、`proxies`、`backups`（默认位置）、`faces` 任一目录里至少有一项——也拦，依据记为 `inferred_postgres`（记录拦下的记为 `previous_postgres`）。这些目录都是处理库里的记录时才建出来的；`database.Init` 之前应用只建出一个空的数据目录（`NewApp`，有测试守着），日志 `app.log`、用户放的 `.env`、记录本身、空目录都不算，所以全新安装永远不会被拦。库文件在、或显式 `DB_BACKEND=sqlite` 时不拦。有记录时只看记录，这一条不起作用。

<a id="D-DBG-03"></a>
**D-DBG-03 · Behavior Contract · Accepted**：启动出错页对这个原因码给专门的说明与出口：
- 说清发生了什么：「上次用的是 PostgreSQL（user@host:port/dbname），这次没有读到 PostgreSQL 配置，为了不打开一个空的本机库，已经停下。数据还在 PostgreSQL 里。」
- 按数据目录推断拦下的（`inferred_postgres`）说不出上次的位置：「数据目录里有之前使用留下的数据（缩略图、备份等），但本机 SQLite 库文件不存在，这次也没有读到 PostgreSQL 配置。看起来之前用的是 PostgreSQL……如果之前用的是放在别处的 SQLite 库，把 SQLITE_PATH 配置找回来后重新打开。」
- 列出这次读过的配置文件位置（按优先级，标明哪个存在），给出可以直接存成数据目录下 `.env`（显示绝对路径）的配置块（D-DBG-05），存好、填上密码后「重新打开」（调现有 `RelaunchApp`）。
- 启动环境（加载配置文件之前的进程环境）里有 `PG_HOST` 但为空时，单独说明是它挡住了所有配置文件里的 `PG_HOST`（配置文件不覆盖已有变量），先去掉再重新打开（评审 Minor 4）。
- 另一个出口「这次改用本机 SQLite」：二次确认（写明会打开本机库、可能是空的，PostgreSQL 里的数据不受影响，之后想回去把配置放回并重启即可）→ 把记录改成 sqlite → 重启应用。不写任何 `.env`。
- 文案按统一设计用语；按钮与对话框用公共组件。

<a id="D-DBG-04"></a>
**D-DBG-04 · Interface Contract · Accepted**：
- `database`：判定函数（纯函数，输入：解析结果、DB_BACKEND 是否非空、记录）与记录的读写；`Init` 在打开之前判定、在 `ApplySchema` 成功后写记录；拦截返回可识别的错误（原因码前缀 `backend_fallback_blocked:`，与现有 `backend_env_locked:` 同一写法）。
- 绑定：`GetStartupBackendGuard()` 返回 `{ blocked, reason, previous_location, config_files: [{ path, exists }], data_dir_config, data_dir_config_status, config_snippet, pg_host_empty_in_launch_env }`（`data_dir_config_status` 为 `missing` / `ignored`（存在但这次整份没有采用）/ `loaded`）（`reason` 为 `previous_postgres` / `inferred_postgres`）；`AcceptSQLiteAfterFallbackBlock()` 只在 blocked 时可用：写记录为 sqlite 后走现有 `RelaunchApp`。
- 前端：`App.vue` 启动出错页按 `GetStartupBackendGuard().blocked` 显示专门内容。

<a id="D-DBG-05"></a>
**D-DBG-05 · Behavior Contract · Accepted（集成方 2026-10-14 裁定）**：出错页的出口是一段可以直接复制的配置块，格式就是应用内切换写下的数据目录 `.env`（带 `PREVIOUS_BACKEND`，启动时整份采用），按记录预填：

```
DB_BACKEND=postgres
PREVIOUS_BACKEND=sqlite
PG_HOST=…
PG_PORT=…
PG_USER=…
PG_PASSWORD=（在这里填密码）
PG_DB=…
PG_SSLMODE=…（只在记录里有时才写）
PG_TIMEZONE=…（只在记录里有时才写）
```

记录里不知道的项留空（按数据目录推断拦下的全部留空），有空着的项时说明里加「补全空着的几项」；密码永远是占位。「复制」用 `navigator.clipboard`，写不进去（或没有这个接口）时选中整段、提示按 ⌘C，不加依赖。页面写明数据目录下 `.env` 的绝对路径：文件不存在时说「存成」；已经有了时说「用下面这段替换这份文件的全部内容」，这次整份没有采用的再加一句「这份文件里原有的内容现在都没有生效」——不能只把配置块贴进旧文件：配置块带了 `PREVIOUS_BACKEND`，文件会被采用，而旧文件后面的 `DB_BACKEND=sqlite` 会压过配置块（同名键取最后一个），结果是一个空的本机库，记录也随之改成 sqlite（第二轮评审 S-a）。配置块下面一行密码提示，按所用 godotenv v1.5.1 的规则写：不加引号时「空格 + #」后面算注释、`$NAME` 会被展开；用英文双引号括起来、其中的 `"`、`\`、`$` 前各加一个 `\` 就能原样读进来；以 `"` 或 `\` 结尾的密码这样写也读不对。数据目录下缺 `PREVIOUS_BACKEND` 的 `.env` 照旧整份不采用（APP-02 M-1 不变）。

存好之后应用在 PostgreSQL 上跑起来时，设置页「数据库」分区与一次正常的「迁移并切换」之后一样：当前与下次启动都是 postgres，不提示「待重启」（`nextBackend` 读到的 `DB_BACKEND=postgres` 与正在用的库一致）；「切回之前的后端」指向 sqlite——本机没有 SQLite 片库时检查目标库得到空库，按 `target_empty` 拒绝，不立围栏、不改配置；本机还留着以前的 SQLite 片库时可以照常切回去（它就是以前用过的那个库）。

历史：同日曾改为「缺 `PREVIOUS_BACKEND` 的数据目录 `.env` 只忽略 `DB_BACKEND` / `PREVIOUS_BACKEND`、其余键照常加载」（a0078a0），独立评审（Important）指出这会改变现有安装打开哪个库——以最高优先级读进一份从未生效过的文件，空的 `PG_HOST=` 会挡住低优先级文件里的真值，照抄 `.env.example` 的值会与真实配置逐键混在一起，`SQLITE_PATH` 会把本机库换到别处——已撤回（cff4769），改为本条。

## 实施备注（2026-10-14）

- 实施时发现「只往数据目录下的 `.env` 写 `PG_*`」走不通（缺 `PREVIOUS_BACKEND` 的文件整份不采用），先后由集成方裁定为 D-DBG-05 的两个版本，现行的是配置块。
- 「写好后『重新打开』」做成出错页上的「重新打开」按钮，调现有 `RelaunchApp`；「这次改用本机 SQLite…」用 `confirmAction` 二次确认。读到回落保护结果之前出错页的两张卡片都不画，被拦下时不先闪一下通用的「数据库连接失败」。
- 记录读不出（坏文件、权限）时按没有记录处理并记日志；「这次改用本机 SQLite」写记录失败时不重启，把错误交回出错页。
