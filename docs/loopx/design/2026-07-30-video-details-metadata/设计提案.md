# 用本地结构化实体与技术快照扩展视频详情

Author(s): Codex / CineInsight
Last updated: 2026-07-30
Status: Accepted
Discussion: 当前用户会话
Source requirements: `.loopx/intake/2026-07-30-video-details-metadata/requirements.md`
Support lenses: architecture-designer, sql-style, go-style

## Abstract / 摘要

本提案在现有 Go、Wails、Vue、PostgreSQL 和 FFmpeg/ffprobe 边界内，扩展右侧预览抽屉为单页视频详情，增加显示标题、原始标题和个人评分；把演员建模为可复用人物，把相关视频建模为有序作品集；把文件、视频流、音轨和字幕轨信息保存为本地只读技术快照。所有信息只来自本地文件、数据库或用户输入，不接入在线影视资料库；旧视频不在启动时自动回填，用户通过可取消、可续跑的后台任务显式补全。

## Background / 背景与动机

当前 `models.Video` 只保存文件名、路径、大小、时长、分辨率、观看状态和标签。主片库已经具备预览、收藏、已看、保存视图、字幕搜索和清理能力，但用户无法区分“磁盘文件名”和“作品显示标题”，无法维护演员或作品集，也看不到多音轨、编码、帧率、HDR、内封字幕等结构化技术信息。

项目已有三个可复用基础：

- `PreviewDrawer.vue` 保持片库上下文并承载播放器。
- `VideoService.getVideoMetadata` 已通过本地 `ffprobe` 获取基础时长和分辨率。
- PostgreSQL、GORM、软删除回收站和资源 Handler 已提供增量 schema、关系保留及受控本地资源读取能力。

问题不在于缺少另一个独立页面，而在于现有预览抽屉缺少持久、可编辑、可关联和可恢复的详情模型。

## Goals And Non-Goals / 目标与非目标

目标：

- 在不丢失当前筛选和滚动位置的情况下完成预览与详情维护。
- 区分显示标题、原始标题和磁盘文件名，并扩展本地搜索。
- 支持 0–10、0.5 步进且可区分未评分与 0 分的个人评分。
- 建立允许同名的人物实体及应用托管头像。
- 建立名称唯一、可多重归属、可排序的通用作品集及应用托管封面。
- 解析并持久化只读技术快照；探测失败不破坏上一份成功数据。
- 旧片库通过显式后台任务补全，启动不产生全库 IO。

非目标：

- 不接入 TMDB、豆瓣或任何在线资料源。
- 不建立导演、角色、生日、人物简介、季或集模型。
- 不把演员继续模拟为标签，也不自动合并同名人物。
- 不允许用户编辑技术信息。
- 不在升级或启动时自动回填全库。
- 不改变文件重命名、播放统计、标签、字幕、迁移和回收站的既有语义。

## Proposal / 设计方案

1. 扩展而非替换现有抽屉。视频抽屉采用单页连续布局：预览、描述信息、演员、作品集、技术信息。人物和作品集也在同一抽屉容器中展示独立详情，并提供返回栈。当前片库查询状态不因抽屉导航而重置。
2. 在 `videos` 上直接增加一对一且高频查询的 `display_title`、`original_title`、`personal_rating`。显示标题只改变 UI 展示，不改变 `name/path`，从而保持磁盘文件真源。
3. 新建 `people` 和 `video_people`。人物姓名不唯一；创建前查询相似候选，但用户可明确新建同名人物。关系只表达演员成员关系，不保存角色或顺序。
4. 新建 `media_collections` 和 `collection_videos`。活跃作品集以规范化名称唯一；成员关系保存稳定位置。视频可属于多个作品集，软删除视频不删除成员关系。
5. 新建一对一 `video_technical_metadata` 和一对多 `media_streams`。成功探测在一个数据库事务中替换整份流快照；失败只更新最后尝试错误，不删除成功快照。
6. 技术探测使用 `ffprobe -show_format -show_streams -print_format json`，探测前后校验文件大小和修改时间，文件在探测中变化时丢弃结果。
7. 新导入、手动刷新和增量扫描发现文件变化时更新快照。旧记录由单实例、串行、可取消的后台补全任务处理；成功结果即刻持久化，重新运行会跳过未过期快照。
8. 人物头像和作品集封面由应用复制到 `~/.video-master/media-details/` 下的托管目录。资源 URL 只包含实体 ID，Handler 从数据库解析受控路径，不接受调用方传入任意文件路径。
9. 主片库新增“视频 / 人物 / 作品集”视图。视频查询增加评分范围和评分排序；默认排序及旧 Wails 方法保持不变，新页面接口返回不透明的稳定游标。

## Boundary Scenarios / 边界场景

- 空标题：显示标题为空时回退文件名；原始标题为空只隐藏该字段。
- 评分边界：`null`、0、0.5、10 合法；负数、超过 10、非 0.5 步进拒绝。
- 同名人物：允许；创建前展示候选，但不自动复用或合并。
- 同名作品集：活跃名称按规范化值唯一，创建和改名冲突均拒绝；软删除旧作品集后可新建全新同名作品集。
- 图片失败：非支持格式、目录、过大文件或不可读文件拒绝；数据库更新失败时补偿新托管文件；替换成功后清理旧文件。
- ffprobe 缺失或失败：新视频仍按现有规则导入；记录错误但不伪造快照。已有成功快照继续展示，并标为旧快照。
- 探测时源文件变化：结果不入库，返回可重试错误。
- 重复启动补全：运行中再次启动返回当前状态，不创建第二个 worker；重启应用后再次运行会从未完成记录继续。
- 取消补全：取消当前探测并停止取新任务；此前成功结果保留。
- 视频软删除：人物和作品集关系保留但默认查询隐藏；恢复后按原位置出现。
- 显式移除最后一个人物关系：事务删除关系和人物，头像按托管文件补偿流程清理；软删除视频不触发该清理。
- 作品集重排与隐藏成员：锁定作品集；只在活跃成员已有的位置槽位中重排，软删除成员保留自己的位置，恢复后回到原槽位。
- 旧应用回滚：旧二进制忽略新增列和表，仍显示文件名；新数据保留。托管文件不因代码回滚自动删除。
- 权限：应用仍是本地单用户 Wails 进程，不新增远程接口；资源 Handler 只提供 GET/HEAD。
- 网络：不发生任何影视资料网络请求。

## Rationale / 理由与取舍

| Alternative | Why Not |
|---|---|
| 新建独立全屏详情路由 | 会丢失当前筛选和滚动上下文，也重复现有预览抽屉的媒体生命周期 |
| 把演员继续保存为标签或逗号文本 | 无法稳定复用头像、原始名称和关联视频，也无法正确处理同名人物 |
| 对人物姓名设置唯一约束 | 现实存在同名人物，唯一姓名会导致错误合并 |
| 让作品集等同文件夹或电视剧系列 | 无法表达多重归属，并错误引入未要求的季集语义 |
| 把全部技术数据保存为一个 JSONB | 写入简单，但约束、流级测试和后续局部读取较弱；规范化流表更符合当前结构化目标 |
| 每次打开详情都运行 ffprobe | 增加延迟和磁盘唤醒，且详情读取失败会变得不稳定 |
| 升级后自动全库回填 | 大库或外置硬盘会造成不可预期的启动 IO，违背用户明确选择 |
| ffprobe 失败时清空快照 | 短暂依赖故障会破坏最后已知有效信息 |
| 接入在线刮削 | 超出本期本地边界，并引入匹配、隐私、凭证和来源治理问题 |

## Compatibility / 兼容性

方案对现有数据库和 Wails 调用纯增量：

- `videos` 新列都有安全空值；旧记录无需 DML 回填。
- 现有 `SearchLibraryVideos`、`GetPreviewSession`、`RefreshVideoMetadata`、标签、字幕和回收站接口保留。
- 新前端使用新增详情和分页接口；旧调用者继续获得原有默认排序和字段。
- 保存视图新增评分和排序列均有默认值，旧视图按原行为加载。
- 软删除视频不删除新关系，现有恢复流程不需要重建演员或作品集。
- 回滚旧代码不会丢失新数据；旧 UI 只是不可见。数据库降级不删除新增列或表，采用前向修复。

## Operational And Security Impact / 运行与安全影响

- 本地磁盘新增头像、封面和技术快照；头像/封面数量受用户创建实体数量约束，不缓存远程内容。
- ffprobe 后台补全串行执行，避免并发打满磁盘；支持取消并记录失败统计。
- 日志记录实体 ID、视频 ID、阶段、耗时和错误，不记录完整 ffprobe JSON、用户备注或任意图片内容。
- 资源路由由实体 ID 间接解析托管路径，并验证真实路径位于应用根目录，防止目录穿越或任意文件读取。
- 本期不改变应用认证边界，也不新增 LAN 暴露。

## Implementation And Transition / 实现与过渡

落地顺序必须先扩展 schema 与只读查询，再接入编辑和托管资产，最后切换前端抽屉、实体视图和后台补全。任何阶段都保持现有视频列表和预览可用。新技术探测成功后同时更新现有 `videos.duration/resolution/width/height`，避免两个元数据来源产生分歧；失败则两个来源都不更新。
