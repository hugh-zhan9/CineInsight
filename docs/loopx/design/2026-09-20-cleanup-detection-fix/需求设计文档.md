## 二、哈希契约（D-CD01）

### 2.1 `differenceHash` 的新语义

位置不变：`services/ai_same_source_fingerprint.go:96`。签名不变
`differenceHash(src image.Image, region image.Rectangle) uint64`。位序不变
（`result |= 1 << (y*8+x)`），因此不影响任何既有的解析与比较代码。

把 9×8 网格的每个格子从「取一个像素」改为「取格子内像素亮度的算术平均」：

| 项 | 规则 |
|---|---|
| 列边界 | 第 `x` 列为 `[Min.X + x*Dx/9, Min.X + (x+1)*Dx/9)`，整数除法 |
| 行边界 | 第 `y` 行为 `[Min.Y + y*Dy/8, Min.Y + (y+1)*Dy/8)`，整数除法 |
| 空格保护 | 上界不大于下界时取 `下界+1`，并夹到 `region.Max`；`Dx<9` 或 `Dy<8` 的小图因此仍能出哈希 |
| 亮度 | 逐像素 `(299*r + 587*g + 114*b) / 1000`，`r/g/b` 取自 `At(x,y).RGBA()`（与现实现同源，16 位分量） |
| 聚合 | 格内亮度求和后除以计入的像素数；累加用 `uint64` |
| 采样上限 | 每轴最多取 64 个等距位置（`nx = min(64, x1-x0)`，位置 `x0 + i*(x1-x0)/nx`）。**这是防御性上限，两个调用点都不会触发**：缩略图长边 480 → 格子 ≤60 像素；AI 抽帧宽度上限 512（`aiTaggingFrameMaxWidth`）→ 格子 ≤57 像素。实测取 64 与全量均值在 480px 缩略图上结果一致 |
| 比较 | 仍是同一行内相邻两格 `left > right`，严格大于，相等判 0 |

`sampledLuma` 随之退役（无其他调用方）。

**不改**：`PerceptualHashService` 的 `ffmpeg scale=9:8:flags=lanczos`（
`services/perceptual_hash_service.go:84`）与 `FrameHashService` 的
`scale=9:8:flags=area`（D-026）。这两条本来就是正确的降采样。

### 2.2 同源指纹版本

由 `same-source-dhash-v1` 改为 `same-source-dhash-v2`。`ensureFingerprint` 的

## 三、图片近似重复分桶（D-CD03）

`buildNearDuplicateGroups`（`services/image_cleanup.go:466`）的 band key 生成改为：

```
for band := 0; band < 8; band++ {
    keys = append(keys, fmt.Sprintf("%d:%s", band, hash[band*2:band*2+2]))
}
```

与 `perceptualBandKeys` 的差别只在没有 frame 维度（图片只有一张）。候选收集照
视频侧的形态改成跨 8 个桶去重累积：

| 项 | 规则 |
|---|---|
| 候选集合 | `map[int]struct{}`，跨 8 个 band 累积，去重 |
| 候选上限 | `imageCleanupMaxCandidates = 256`，达到即停止继续收集（不变） |
| 桶内邻居上限 | `imageCleanupMaxBandNeighbors = 64`，超出保留最近的 64 个（不变，但现在是每段各自一个桶） |
| 入桶时机 | 与视频侧一致：先按当前 band 收候选，再把自己追加进该 band 的桶 |
| 判定 | `bits.OnesCount64(a^b) <= imageCleanupHammingThreshold`（8，不变） |
| 成组 | 连通分量、按索引升序 DFS（不变） |
| `MaxHammingDistance` | 仍是「与推荐保留项」的最大距离、采样上限 64（不变） |

常量 `imageCleanupBandPrefixLen` 退役。

**保留的既有行为**：`excluded` 排除集（精确重复对 + `image_near_duplicate_dismissals`）
在成边前检查，位置与语义不变。

## 四、指纹待补全计数（D-CD04）

### 4.1 图片侧

`buildNearDuplicateGroups` 里三个 `continue` 的计数口径改为：

| 情形 | 现状 | 改后 |
|---|---|---|
| `perceptual_hash == ''` | 静默跳过，不计数 | `staleCount++` |
| `hash_source_*` 与文件失配 | `staleCount++` | 不变 |
| 长度不是 16 或 `ParseUint` 失败 | 记日志跳过，不计数 | `staleCount++`，日志保留 |

判据的输入是 `states`（已通过 `os.Stat` 的活跃图片），因此「文件不在」不会混进这个计数。

### 4.2 视频侧

`loadCleanupNearDuplicateGroups`（`services/perceptual_hash_cleanup.go:21`）当前只
遍历 `video_perceptual_hashes` 的现有行，**没有行的视频根本进不来**。改为：

1. 现有循环里，`HashEarly/Middle/Late` 有空串的行由「静默 `continue`」改为 `staleCount++`。
2. 新增一次统计：扫描范围内（`cleanupPathScope.contains`）、`os.Stat` 成功且为普通
   文件、但 `video_perceptual_hashes` 无行的视频数，累加进 `staleCount`。

实现约束：这一步不得再把整库视频连同 `Preload("Video.Tags")` 读一遍。
`analyzeCleanupCandidates` 已经持有本轮在范围内且 `os.Stat` 成功的视频集合，
把「已确认存在的视频 ID 集合」传进来，与 `video_perceptual_hashes` 的 `video_id`
集合做差即可，不新增查询。

3. `stale_frame_hash_count` 同口径改造（2026-09-20 用户裁决追加）：
   `countVideosWithoutUsableFrameHash` 原本把扫描根内的视频整个查一遍、一个
   `os.Stat` 都不做，于是外置盘没插时同一面板并排出现「123 个没有感知哈希」和
   「1439 个没有帧哈希」。改为同样只数 `presentVideoIDs`，顺带省掉那次整表读。
   文件读不到由 `SkippedUnavailable` 负责报，不算指纹问题。

## 五、清理分析的元数据与跳过计数（D-CD05、D-CD06）

### 5.1 `analyzeCleanupCandidates` 主循环改写

`services/cleanup_service.go:255` 起的循环，判定顺序改为：

| 步骤 | 条件 | 动作 |
|---|---|---|
| 1 | `os.Stat` 失败或是目录 | `SkippedUnavailable++`，日志保留，`continue` |
| 2 | 库内记录新鲜 | 用 `video.Duration / Resolution / Width / Height`，不起 ffprobe |
| 3 | 不新鲜 → ffprobe 成功 | 用探测值覆盖 `workingVideo` 的四个字段 |
| 4a | 不新鲜 → ffprobe 失败 → **库里曾有元数据** | `SkippedMetadata++`；**不 `continue`**，继续进步骤 6 |
| 4b | 不新鲜 → ffprobe 失败 → **库里也从无元数据** | `SkippedMetadata++`，`continue` |
| 5 | 有可用元数据且触发阈值 | 追加到 `LowDuration` / `LowResolution` |
| 6 | 走到这里的都入桶 | `sizeBuckets[workingVideo.Size] = append(...)` |

步骤 4a 是本条的核心：精确重复只需要文件大小与采样哈希，一次 ffprobe 失败不该
让一个真视频从所有类别里消失。

步骤 4b 是**受保护行为**，不可省略：`services/cleanup_service_test.go`
`TestAnalyzeCleanupCandidatesSkipsNonVideoRecordsWithoutMetadata` 钉住「历史上误
入库的源码文件（`.ts` 之类）不得出现在删除候选里」。这类记录的特征正是「库里
从来没有过元数据，且探测不出来」。早先的实现靠「探测失败就整条丢弃」顺带实现了
这件事；拆开之后必须显式保留。

两个判据：

```
hasStoredMetadata := video.Duration > 0 && video.Resolution != "" && video.Width > 0 && video.Height > 0
fresh            := hasStoredMetadata && info.Size() == video.Size
```

`hasStoredMetadata` 取自扫描侧的 `needsTechnicalRefreshDuringScan`，额外多要
`Width > 0`——低清判定读宽高两项，而扫描那条只看 `Height`。

这里刻意**不**查 `video_technical_metadata`：那张表存的是容器格式与码率，没有
时长与分辨率；清理分析也不需要它的探测指纹。

`workingVideo.Size` 统一取 `info.Size()`（磁盘实测），与图片侧一致；库内 `Size`
只用于上面的新鲜度比较。

### 5.2 新增字段

| 结构 | 新字段 | 类型 | 含义 |
|---|---|---|---|
| `CleanupAnalysis` | `SkippedUnavailable` | `int` `json:"skipped_unavailable"` | `os.Stat` 失败或是目录的视频数 |
| `CleanupAnalysis` | `SkippedMetadata` | `int` `json:"skipped_metadata"` | 文件在、但时长/分辨率取不到的视频数（仍参与精确重复） |
| `ImageCleanupAnalysis` | `SkippedUnavailable` | `int` `json:"skipped_unavailable"` | `os.Stat` 失败或非普通文件的图片数 |

图片侧不设 `SkippedMetadata`：该路径没有 ffprobe 环节。

`cleanupDoneMessage` 与 `imageCleanupDoneMessage` 追加这两项，进度事件形状不变。

### 5.3 前端呈现

两个审阅界面各加一行提示，与既有 `cleanup-stale-hash-hint` 同区域、同样式，
仅在计数 > 0 时出现，**不带按钮**：

- 视频：`本轮跳过 N 个视频（文件不可访问，如外置盘未挂载）`；`SkippedMetadata > 0`

## 六、图片感知哈希批量补全服务（D-CD07）

### 6.1 服务形态

新文件 `services/image_perceptual_hash_backfill.go`。逐项镜像
`ImageEXIFBackfillService`，不复用它的 worker：

| 成员 | 形态 |
|---|---|
| `ImagePerceptualHashBackfillFailure` | `{ImageID uint, Name string, Error string}` |
| `ImagePerceptualHashBackfillStatus` | 与 `ImageEXIFBackfillStatus` 同字段：`Running/Cancelled/Completed/Total/Processed/Succeeded/Skipped/Failed/CurrentImageID/StartedAt/UpdatedAt/Failures/Gate` |
| 构造 | `NewImagePerceptualHashBackfillService()`，`Failures` 初始化为空切片 |
| 注入 | `SetEventEmitter(func(ImagePerceptualHashBackfillStatus))`、`SetBackgroundTaskRegistry(*BackgroundTaskRegistry)` |
| 启动 | `StartImagePerceptualHashBackfill(ctx)`（显式，hook=nil）/ `StartImagePerceptualHashBackfillWithPauseHook(ctx, hook)`（自动） |
| 其余 | `GetImagePerceptualHashBackfillStatus()` / `CancelImagePerceptualHashBackfill()` / `StopAndWait()` |
| 并发 | 单 worker；`mu` 保护状态，`stopMu` + `worker sync.WaitGroup` 保护停机 |

**空闲门约束（D-032，硬要求）**：装钩子与翻 `Running` 必须在同一把 `mu` 内完成；
服务已在跑时不补装钩子；显式 `Start` 在同一把锁内摘钩子并调用
`IdleGate.Release(BackgroundTaskImagePerceptualHash)`。`waitForPauseHook` 在锁外调用
`hook.Wait(ctx, s.setGateState)`。

### 6.2 目标集与游标

```
is_stale = false
AND 不在图片扫描黑名单目录下
AND (perceptual_hash = ''
     OR hash_source_size <> <磁盘 size>
     OR hash_source_mod_time_ns <> <磁盘 mtime>)
```

黑名单那一行是 2026-09-20 用户裁决加上的（原稿只写 `is_stale`）：唯一的消费方
`analyzeImageCleanupCandidates` 是排黑名单的，目标集不排就会让 `Total` 比真要干的活
大一截，并去解码用户明确排除掉的目录。判据与消费方同源——`imageScanExcludedPaths`
读设置（图片黑名单优先、空则回退通用黑名单），SQL 侧走 `applyImageExclusions`
（LIKE 前缀），循环里再按 `isScanPathExcluded` 兜一道（路径写法有出入时 LIKE 会漏），
兜到的记 `Skipped` 以保持 `Processed` 追得平 `Total`。整轮只读一次黑名单：中途改了
也应当下一轮才生效，免得同一轮前后半段按两套集合跑。

后两项无法在 SQL 里判定（要 `os.Stat`），因此：

| 阶段 | 做法 |
|---|---|
| `countActive` | SQL 数目标集（`is_stale = false` + 排黑名单）的图片数作为 `Total`。**不预筛指纹状态**：后两项判据要 `os.Stat`，预筛出来的数会比实际遍历量小，`Processed` 会超过 `Total` |
| `loadBatch` | 按 `id > afterID AND is_stale = false` + 排黑名单顺序取批，逐项 `os.Stat` 后判定 |
| 游标 | `afterID` 在处理之前就前进（与 EXIF 服务同理），失败项不重试、不死循环 |
| 记账 | 指纹已新鲜 → `Skipped++`，**不取缩略图**；重算并落库成功 → `Succeeded++`；`os.Stat`、取缩略图或回读失败 → `Failed++` 并记一条 `Failures`（上限 50 条，错误文本截断） |

进度条因此是「检查到第几张」而不是「补了第几张」。这是有意的取舍：`Total` 精确、
单调，代价是已经新鲜的图片也计入分母。

`ResolveImageThumbnail` 返回成功只代表缩略图可用——指纹回填在它内部是机会式的
（失败只记日志）。因此处理完必须**回读该行确认指纹真的落库**，否则会把没补上的
算成成功，用户下一轮还会看到同样的待补全数。

### 6.3 单项处理

```
media, err := thumbnails.ResolveImageThumbnail(ctx, image.ID)
```

`ResolveImageThumbnail` 内部已包含「生成缩略图 → `backfillImageMetadata` 回填
width/height 与 dHash」的完整链路，所以本服务**不自己算哈希、不自己写库**，只负责
驱动与记账。处理后重读该行判断是否已有新鲜指纹，据此记 `Succeeded` / `Failed`。

这样 HEIC/RAW 的 sips 分支、缩略图缓存淘汰、EXIF 方向全部沿用既有实现，不产生第二条
解码路径。

## 九、边界条件

| 场景 | 处理 | 用户感知 |
|---|---|---|
| 补全跑到一半取消 | `afterID` 游标不持久化；下次从头扫，已新鲜的项记 `Skipped` 快速跳过 | 重复启动不会重算 |

| 外置盘未挂载时补全 | 每项 `os.Stat` 失败 → `Failed++` 并记 `Failures` | 失败明细里能看出是整盘不可用 |

| 缩略图生成失败（格式不支持） | `Failed++`，指纹保持空，下轮重试 | 失败明细列出 |
| 极小图片（宽<9 或高<8） | §2.1 的空格保护保证仍出哈希 | 正常参与比对 |
| 迁移后立刻打开图片清理 | 全部图片无指纹 → `stale_hash_count` = 活跃图片数，近似重复为空 | 提示行给出数量与补全按钮 |
| 图片全部软删（当前库状态） | 分析读到 0 条，结果为空 | 范围外，本次不处理 |
| `video_perceptual_hashes` 仍为 0 行 | D-CD04 使 `stale_hash_count` = 范围内可访问视频数 | 「重算感知哈希」按钮终于出现 |
