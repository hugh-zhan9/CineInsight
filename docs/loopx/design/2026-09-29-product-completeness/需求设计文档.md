## 0. 全局约束（每个切片都适用）

<a id="G-1"></a>**G-1 迁移硬规则**（沿用仓库既有规则，违反即判不合格）
- 新表一律加入 `models/schema.go` 的 `AllModels()`，被引用的表排在引用方之前；`TestAllModelsIsTopologicallyOrdered` 必须通过。
- `database/migrator` 往返测试夹具里每张表至少一行，新表同样适用。
- 默认值为 true 的布尔列、默认值非零的数值列**不带** gorm `default` 标签，默认值由 `ApplySchema` 为新库写显式行，老库由一次性迁移函数补写。
- 随机标识一律为 32 位十六进制字符，禁止 `uuid.NewString()`。
- 触及 upsert、唯一索引、`varchar` 长度的切片必须跑 PG 腿（`CINEINSIGHT_TEST_PG_DSN`，`-timeout 1500s`）。PG 独有的三个陷阱：21000 批内重复、42702 未限定列、22001 超长。

**G-2 并发**：不引入 `SELECT … FOR UPDATE` 或任何数据库锁。状态转换用条件更新（`WHERE state = ?`），以影响行数判定竞争：输的一方重读后返回幂等结果，或报冲突。

**G-3 错误与文案**：面向用户的错误为中文，不含绝对路径（沿用 `scrubPlaybackProxyPaths` / `scrubFacePaths` 的做法）。新增错误码的格式为 `snake_case` 字符串，放在返回结构的 `code` 字段里。

**G-4 回归测试命名**：每条问题清单条目至少一条回归测试，**测试名或用例描述中包含问题 ID**：Go 写成 `LIB03`（无连字符），前端写成 `LIB-03`。最终用 grep 核对 88 个 ID 的覆盖情况（§V.2）。

**G-5 绑定**：新增或修改 App 方法后重新生成 `frontend/wailsjs`。签名有变的旧方法要同步改掉全部前端调用点，不保留死绑定。

**G-6 不做的事**：不加未经要求的重试、降级、兼容垫片。唯一例外是非 darwin 平台：由 [D-PC02](./概要设计.md#D-PC02) 明确规定为「不支持废纸篓」。

### 1.2a 实施修订（P-001，2026-09-29 主代理审查后接受）

- `dismiss_key` 与 `token_hash` 改用 `varchar(64)`，不用 `char(64)`。PG 的 `char(n)` 会把默认值空串补成 64 个空格，下游判断 `!= ""` 时会误判。64 位十六进制哈希同样不会触发 22001。
- `short_feed_enabled` 与三个清理阈值列不加 `not null`。给已有行的表加一个没有默认值的 NOT NULL 列，两个后端都会失败。这与既有的 `idle_scheduling_enabled`、`proxy_cache_limit_bytes` 做法一致：默认值由 `ApplySchema` 的显式行和迁移函数写入。`short_feed_enabled` 的迁移额外做了 NULL 自愈：新加的列在老行上一定是 NULL，而用户关闭开关写入的是 false，两者可以区分。
- 术语表新唯一索引换了名字（`idx_translation_glossary_entries_scope_lang_term`），先确认新索引已经就位，再删除旧索引，保证任何时刻都有唯一约束保护。
- 首次收藏时写入 `favorited_at`；已收藏时再次置 true 用 `COALESCE` 保留原时间，取消收藏后再收藏才重新计时。
- `collection_suggestions` 不加 `kind` 列。`kind=append` 等价于 `target_collection_id` 非空，由 P-017 据此推导。
- `Settings.ShortFeedPINHash`、`FavoritesUnifiedAt` 标 `json:"-"`，不下发前端。「是否已设置 PIN」由 P-021 的专用接口返回（`pin_set bool`）。
- 登记表 key 总数由 20 变为 21（新增 `image_cleanup`，紧跟 `cleanup`）。

### 2.1 系统废纸篓（[D-PC01](./概要设计.md#D-PC01)、[D-PC02](./概要设计.md#D-PC02)）

- 新文件 `services/system_trash_darwin.go`（cgo，`-framework Foundation`，沿用 `desktop_notify_darwin.go` 的构建写法）与 `system_trash_other.go`。
- 函数 `moveToSystemTrash(path string) (trashedPath string, err error)`，调用 `[[NSFileManager defaultManager] trashItemAtURL:resultingItemURL:error:]`。NSError 映射如下：

| NSError | 返回 |
|---|---|
| `NSFileNoSuchFileError`(4)、`NSFileReadNoSuchFileError`(260) | 包装 `os.ErrNotExist` |
| `NSFeatureUnsupportedError`(3328)，或 domain=`NSCocoaErrorDomain` 且底层 POSIX 为 `ENOTSUP` / `EXDEV` | `ErrTrashUnsupportedVolume` |
| `NSFileWriteNoPermissionError`(513) | `ErrTrashPermissionDenied` |
| 其他 | `fmt.Errorf("移到废纸篓失败: %s", localizedDescription)`，经路径擦除 |

- 非 darwin 平台一律返回 `ErrTrashUnsupportedVolume`。
- `TrashService.MoveToTrash` 改为调用 `moveToSystemTrash`；`TrashTargetPath`、`copyToExclusiveAndDelete` 及同目录 `trash/` 的创建逻辑删除，新删除路径上不再出现。

**删除入口的结果契约**（`DeleteVideo`、`BatchDeleteVideos`、`DeleteImage`、`BatchDeleteImages`、`BatchDeleteImagesInDirectory`）：

| 参数 `deleteFile` | 流程 | 单项结果 `code` |
|---|---|---|
| true | `pending_move` → 移入系统废纸篓 → 事务：软删 + `mode=trash` + `trash_path=返回路径` + `delete_batch_id` → `deleted` | `ok`；`trash_unsupported`（记录不动、条目回滚，前端弹 D-PC02 选择框）；`file_missing`；`permission_denied`；`volume_offline`（根离线，**不降级**，修复 LIB-04 补充场景）；`error` |
| false | 事务：软删 + 建条目（`mode=record_only`，记录身份）+ `delete_batch_id` | `ok` / `error` |

- 新增 `PermanentlyDeleteVideos(ids []uint) BatchResult` 与 `PermanentlyDeleteImages`，只用于 `trash_unsupported` 之后用户选择「永久删除」。流程：身份核对 → `os.Remove` → 硬删记录（`Unscoped().Delete`，级联生效）。二次确认在前端完成，后端不再弹。
- 返回结构统一新增 `batch_id` 字段（本次操作的 `delete_batch_id`）。
- **既有签名保持不变**：`VideoService.DeleteVideo(id, deleteFile) error` 与 `ImageService.DeleteImage` 保持原样，遇到不支持废纸篓时返回 `ErrTrashUnsupportedVolume`。带结果码与 `batch_id` 的是新增方法（例如 `DeleteVideosDetailed`），桌面 App 层改用新方法。远端客户端对 `ErrTrashUnsupportedVolume` 的处理：
  - 手机端：返回 409 `{code:"trash_unsupported"}`，文案「该磁盘不支持废纸篓，请在桌面端处理」；
  - Jellyfin：沿用删除失败的既有映射，日志只记视频 ID；
  - 两者都**不提供**永久删除。
  
  （计划评审 I1。）
- **崩溃恢复（`mode=trash`）**：废纸篓中的实际路径要等 `trashItemAtURL` 返回才知道。如果文件已移动、事务尚未提交时进程退出，条目会停在 `pending_move` 且 `trash_path` 为空。启动对账按以下顺序处理这类行：
  1. 原路径文件仍在，且身份与条目一致 → 回滚为活跃记录；
  2. 原路径已不在 → 在该卷的用户废纸篓顶层（`~/.Trash`，或 `<卷根>/.Trashes/<uid>`）按 `stableFileIdentity` 查找。同卷移动 inode 不变，找到即补写 `trash_path` 并置为 `deleted`；
  3. 都找不到 → 置 `state='deleted'`、`last_error='文件位置未知'`，回收站中只提供「移除记录」。
  
  `legacy_trash` 行及其 `pending_move` / `restoring` / `rollback` 状态，继续走既有的对账逻辑；`mode` 回填只看 `file_moved` 与 `deleted_by`，与 `state` 无关。（计划评审 I13。）

**回收站读写接口**（统一视频与图片，替换现有两套只列全部的方法；旧方法删除，调用点一并改掉）：

## 3. 可见性与扫描（D-PC06~11）

### 3.1 失效原因（[D-PC06](./概要设计.md#D-PC06)）

- 常量在 `models/video.go`：`StaleReasonOfflineRoot="offline_root"`、`MissingFile="missing_file"`、`RemovedRoot="removed_root"`、`OutsideRoots="outside_roots"`、`PlayFailed="play_failed"`、`ReadError="read_error"`、`WatcherMissing="watcher_missing"`。
- 所有写 `is_stale=true` 的地方都要同时写原因，包括扫描缺失候选、读取失败、离线根、`MarkVideosStaleUnderRemovedRoot`、`reconcileOrphanedVideos`、监听、播放失败。所有写 `is_stale=false` 的地方同时清空原因。
- 新增守卫测试：从源码扫出所有 `is_stale` 写入点，逐一断言都带了原因（LIB-10）。
- `applyLibraryFilter`：`SmartView == stale` 时**跳过** `applyScanRootScope` 的根裁剪，只保留黑名单排除；新增筛选字段 `stale_reason`（可选，精确匹配，传 `unknown` 表示空原因）。其他视图的行为不变，由受保护测试钉住。
- 新增接口：
  - `ListStaleReasonCounts() map[string]int`；
  - `RecheckVideos(ids []uint) LibraryReconcileSummary`：取这些视频的目录去重后，调 `SyncAffectedDirectories`；
  - `ReaddRemovedRoot(videoID)`：返回原根路径，供前端预填「添加扫描目录」。
- 前端「路径失效」视图按原因分组显示标题与计数，行菜单提供「重新定位文件…」「重新检查」「删除」。「重新定位」接入既有 `App.RelocateVideo`：原生文件选择 → 调用 → 成功后移出失效。
- `GetLibraryVideoCount` 与洞察页全部总数改为使用「默认视图」同一套可见条件（根 + 黑名单 + 非失效）。
- 图片扫描隐藏：
  - `ListHiddenImages(cursor, limit)`：`deleted_by='scanner'`，或带 `is_stale` 恢复标记的软删图片，附原因 `offline_root` / `missing_file` / `removed_root`，原因由路径与根的在线状态推算，不落库；
  - `RecheckImages(ids)`：触发全量 `SyncImageDirectories`（图片侧没有窄扫描，这是既有限制）。

### 3.2 编辑路径 = 重映射（[D-PC07](./概要设计.md#D-PC07)）

- 从 `RenameDirectory`（`file_migration.go:475-517`）抽出纯数据库部分：`rewriteLibraryPathPrefixTx(tx, oldPrefix, newPrefix) PathRewriteCounts`，覆盖视频（含软删）、回收站条目 `original_path`、`scan_exclude_paths`、字幕索引路径、扫描目录。`RenameDirectory`、`MoveDirectory`、重映射三处共用它。
- `UpdateDirectory(id, alias, newPath, mode)`，`mode ∈ {remap, replace}`：
  - `remap`：`newPath` 必须存在，且不能与其他根相同或互相嵌套；执行 `rewriteLibraryPathPrefixTx(oldPath, newPath)`，随后 `SyncAffectedDirectories(newPath)` 并重配监听。
  - `replace`：沿用现有行为；旧根下的记录经 `MarkVideosStaleUnderRemovedRoot` 标记为 `removed_root`。
- 前端编辑框改变路径时显示二选一；旧路径 `os.Stat` 失败时默认选中 `remap`。

### 3.3 离线与重连（[D-PC08](./概要设计.md#D-PC08)）

- 监听把某根判为 `unavailable`（卸载或根被移除）时，调用 `VideoService.MarkRootOffline(root)`：该根下 `is_stale=false`、且不属于其他可用根的活跃视频，置为 `is_stale=true, stale_reason='offline_root'`。
- 根从 `unavailable` 回到 `watching` 时，排队 `SyncAffectedDirectories(root)`，窄对账会清掉该根下 `offline_root` 失效行（文件存在即恢复）。三个触发来源：
  - `RetryRoot` 成功；
  - 监听自行恢复；
  - 新增的 60 秒巡检：对 `unavailable` 根做 `os.Stat` 加 `scanVolumeMounted` 检查，可用即 `RetryRoot`。
- 启动时和全量扫描时的离线判定改为写 `offline_root`，与运行时一致。

### 3.4 扫描回报（[D-PC09](./概要设计.md#D-PC09)）

- `ScanSyncResult` 与 `LibraryReconcileSummary` 新增 `skip_breakdown`，key 为 `existing`、`blocked_user_delete`、`recently_modified`、`temp_file`、`not_video`、`read_error`。旧的 `skipped` 保留，等于各项之和。
- 启动扫描与改目录触发的扫描完成后，发 `library-scan-summary` 事件，载荷为 `{trigger: startup|directory_change|manual, result}`。`VideoListPage` 用 `IncrementalScanBar` 展示；`added + removed + restored + stale_marked > 0` 时重载列表与头部计数。
- 新增 `ValidateScanDirectory(path) {exists, duplicate_of, nested_in, contains}`。`ScanDialog` 把所选目录加入扫描根之前先确认；有嵌套关系时给出提示，可选「仅扫描不加入」（手动目录扫描本来就支持）。
- `ScanDirectoriesSection.vue` 里被吞掉的错误（`catch (err) {}`）改为显示在分区内。

### 3.5 迁移（[D-PC10](./概要设计.md#D-PC10)）

- `MoveDirectory` 的事务改用 `rewriteLibraryPathPrefixTx`，结果字段 `TrashEntriesUpdated` / `ScanExclusionsUpdated` 如实填写；`app_video.go` 成功后调用 `reconfigureLibraryWatcher`。
- 新增 `CheckMoveTarget(targetDir) {in_scan_roots bool}`。前端迁移确认框在目标不在任何扫描根时显示警告，并提供复选框「同时把目标加入扫描目录」。

### 3.6 播放失败（[D-PC11](./概要设计.md#D-PC11)）

- `PlaybackAttemptResult` 新增 `reason`，取值 `offline_root` / `missing_file` / `error`。
- 源文件不存在时：
  - 根离线（`scanVolumeMounted` 为 false，或根 `os.Stat` 失败）：标 `offline_root`，**不做**重定位，直接返回；
  - 根在线：标 `missing_file` 并返回，重定位在 goroutine 里执行 `findRelocatedVideoCandidate`；找到后调 `RelocateVideo` 并发 `video-relocated` 事件 `{video_id, new_path}`。

## 4. 文件写入保护（D-PC12~17）

### 4.1 重命名（[D-PC12](./概要设计.md#D-PC12)）

`RenameVideo`：

```text
ext := filepath.Ext(newName)
if ext == "" || !isConfiguredVideoExtension(ext) { newName += oldExt }
```

规范化后的新名与当前文件名相同时直接返回 nil。前端 `RenameDialogs.vue` 在输入未改动时点确认只关闭对话框；显示的新文件名与后端规则一致。回归用例覆盖 `The.Matrix.1999.1080p`、`a.b.c`、显式改为 `.mp4` 三种情况。

### 4.2 字幕写入器（[D-PC13](./概要设计.md#D-PC13)）

新文件 `services/subtitle_file_writer.go`：

```go
type SubtitleWriteResult struct { BackupID string; Replaced bool }
func (w *SubtitleFileWriter) Replace(ctx context.Context, videoID uint, target string, content []byte) (SubtitleWriteResult, error)
func (w *SubtitleFileWriter) ListBackups(videoID uint) ([]SubtitleBackup, error) // {id, created_at, size}
func (w *SubtitleFileWriter) RestoreBackup(ctx context.Context, videoID uint, backupID string) (SubtitleWriteResult, error)
```

- `Replace` 流程：同目录临时文件 `.<名>.cineinsight-tmp-<hex>` → `fsync` → 目标存在则复制到 `<dataDir>/subtitle-backups/<videoID>/<unixNano>.srt`（只保留最新 5 份，超出按时间删）→ `atomicReplaceSubtitle`（既有 `subtitle_atomic_replace_*`）→ 恢复原文件权限（沿用 `mergeBilingualSRT` 修复时的做法）。
- 调用方在外层持有 `lockSubtitleFile(videoID)`，写入器不另外加锁。
- 字幕生成改为：`writeSRT` 写到临时路径 `outputPrefix + ".cineinsight-pending.srt"`，对临时文件做校验：
  - 通过 → `Replace`；
  - 失败 → `pendingSubtitleArtifact.SRTPath` 指向临时文件，原字幕不动；
  - 空结果 → 删除临时文件并报错；
  - 取消 → 删除临时文件。
  
  `ForceGenerateSubtitle` 复用临时文件执行 `Replace`；用户放弃时删除临时文件。
- 翻译（`subtitle_translate_file.go`）、工作台保存（`subtitle_workbench.go`）、编码转换（§4.3）都改用 `Replace`。
- 新 App 方法：
  - `ListSubtitleBackups(videoID)`、`RestoreSubtitleBackup(videoID, backupID)`；恢复前会先备份当前文件。
  - `GetSubtitleOverwriteInfo(videoID) {exists, shared_with []{id, name}}`，`shared_with` 列出同目录、同基本名、扩展名不同的其他活跃视频。
- `SubtitleGenerateDialog` 在 `exists` 为 true 时，确认文案写明「将覆盖现有字幕（会先备份，可恢复）」；`shared_with` 非空时列出受影响的视频。

### 4.3 编码（[D-PC14](./概要设计.md#D-PC14)）

- 新增 `subtitleparser.DecodeSubtitleBytes(b []byte) (text string, encoding string, err error)`：
  - UTF-8 BOM / UTF-16LE/BE BOM：解码；
  - `utf8.Valid`：原样；
  - 否则依次尝试 `simplifiedchinese.GB18030`、`traditionalchinese.Big5`，取第一个解码后无 `U+FFFD` 且可打印字符比例 ≥ 95% 的结果，`encoding` 返回 `gb18030` / `big5`；
  - 都不满足：返回 `ErrSubtitleEncodingUnknown`。
  
  `golang.org/x/text` 由 indirect 改为 direct 依赖，版本不变。
- 工作台打开与翻译读取：`encoding != "utf-8"` 时返回错误码 `subtitle_encoding_not_utf8`（附 `detected_encoding`），不解析、不写入。
- 新增 `ConvertSubtitleToUTF8(videoID, fromEncoding)`：解码后经 `Replace` 写回（会先备份）。
- 字幕搜索索引读取改用 `DecodeSubtitleBytes`。

### 4.4 工作台容错（[D-PC15](./概要设计.md#D-PC15)）

- `subtitleparser/editor.go` 的严格解析把 `end <= start` 从加载错误降为 issue，其余格式错误仍报错。文档新增 `issues: [{index, kind: zero_duration|end_before_start|overlap}]`。
- 保存前的校验不变（有 issue 时拒绝），但返回第一个 issue 的位置。前端提供「下一个问题」与「一键修复」：
  - 零时长：结束时间 = 开始 + 500ms，且不越过下一条的开始；
  - 重叠：前一条的结束 = 后一条的开始 − 1ms。
- 文件不存在时，`OpenSubtitleDocument` 返回错误码 `subtitle_missing`。前端显示「新建空白字幕」，工作台以空文档打开，保存经 `Replace` 创建文件。
- 工作台相关错误改为中文，并经路径擦除。

### 4.5 翻译一致性（[D-PC16](./概要设计.md#D-PC16)）

- 工作台重译请求新增 `mode ∈ {translation_line, whole_entry}`。检测到当前选区多数条目为双语两行时，前端默认 `translation_line`：只把第一行送去翻译，并只替换第二行。
- 空译文回退（译文为空时保留原文，并计入 `subtitleFallbackWarning`）抽成函数 `applyTranslationFallback`，生成、文件翻译、工作台重译三处共用。

### 4.6 字幕覆盖范围（[D-PC17](./概要设计.md#D-PC17)）

### 8.2 看完判定（[D-PC41](./概要设计.md#D-PC41)）

```go
func watchCompletionTail(duration float64) float64 { return math.Min(duration*0.05, 180) }
func isWatchCompleted(position, duration float64) bool {
  return duration > 0 && position > 0 && position >= duration-watchCompletionTail(duration)
}
```

- 替换 `library_service.go:371-389` 的容差实现。Jellyfin、内嵌、IINA 三条路径都只调用 `isWatchCompleted`。前端 `utils/mediaDetails.js` 的 `resumePositionFor` 与行组件的 `watchProgressPercent` 使用同一公式（JS 版本，测试用同一组样例对齐）。
- IINA 会话登记：`launchPlayback` 成功后调用 `iinaProgress.RegisterLaunchedSession(videoID, path, startPosition, time.Now())`，内存保存，12 小时过期。`startPosition` 是本次起播位置：续播时为库内断点，从头播为 0。
- `iina_progress_service.go` 的监听处理 `Remove` / `Rename` 事件：由 watch_later 文件名反查视频（沿用既有的 md5(path) 映射）。若该视频在已登记会话中，取
  `lastKnown = max(db.watch_position_seconds, session.lastParsedPosition, startPosition + (eventTime − launchTime))`，
  最后一项是按墙钟推算的位置：暂停只会让它偏大，而删除事件只在播到结尾时发生（`iina_progress_service.go:21-24` 注释）。满足 `isWatchCompleted(lastKnown, duration) || lastKnown >= 0.9*duration` 时，调用 `markWatchedFromCompletion`（标已看、清零断点），并发 `iina-progress-updated` 事件，`Watched=true`。
- 未登记的删除事件照旧忽略（用户自己清除记录的情况）。
- **前提修订（2026-09-29 独立评审 A-I-1）**：mpv 续播**加载** watch_later 后很可能立即删除该文件，「删除只在播到结尾时发生」不成立（待真机确认）。因此结算前有两道保护：墙钟经过时间短于 `min(60s, 0.5 × (duration − startPosition))` 时既不结算也不消耗会话；会话期间观察到 mtime 不早于 `launchedAt` 的写入（这次播放已退出）即结束会话。若真机确认加载即删，「续播后看完」可能收不到第二次删除事件，与「从头播完」同属真机缺口，候选方案同下。结算用的最后已知位置为 `max(库内断点, startPosition + (eventTime − launchTime))`（会话期间读到的位置在第二道保护下用不到，已移除）。
- **已知缺口（真机待办，不在本批闭合）**：从片头开始连续看完时，IINA 可能从未写过 watch_later，就没有删除事件。实测的 `iina-cli --keep-running` 要等整个 IINA 退出才返回，不能作为会话结束信号；本机也没有 IINA 播放历史文件（`history.plist`）。可以验证的候选是：应用发起的播放加上 `--mpv-keep-open=yes`，让 IINA 播到结尾后停在最后一帧，关闭时写出接近片尾的位置，从而命中既有的完成判定。该方案需要真机播放确认后，再经用户同意启用，本批不实现。
