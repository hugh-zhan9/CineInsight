## 1 失联数据治理

### 1.1 失联条目与分组

<a id="lost-sources"></a>
统计的来源：

| 存法 | 视频 | 图片 |
|---|---|---|
| 失效行 | `videos.is_stale = true`，原因取 `stale_reason` | `images.is_stale = true` 且未软删，原因按 `image_visibility.go` 现算 |
| 扫描器回收站 | 已软删且 `deleted_by = 'scanner'`，回收站条目 `mode = missing` | 已软删、`deleted_by = 'scanner'` 且 `is_stale = true` |

用户自己删进回收站的条目不算失联。

原因归类（[D-LD-02](概要设计.md#D-LD-02)）：

| 归类 | 来源原因 | 找回 | 清除 |
|---|---|---|---|
| 卷未挂载 | `offline_root` | 否 | 否 |
| 读取出错 | `read_error` | 否 | 否 |
| 文件不见 | `missing_file`、扫描器回收站 | 是 | 是 |
| 目录已移除 | `removed_root` | 是 | 是 |
| 不在扫描目录 | `outside_roots` | 是 | 是 |
| 原因未知 | 空（历史失效行） | 是 | 是 |

分组：
- 先按所属扫描根分组（含已移除的根，从路径前缀推断，推不出来的归入「其他位置」），再按 `directory` 分组。
- 根前缀在 SQL 里只做粗筛（SQLite 的 `LIKE` 对 ASCII 不区分大小写），以 Go 侧的 `videoBelongsToRoots` 为准。
- 分组只给计数、总大小和前 5 条示例；组内明细分页读取。

### 1.2 找回

<a id="lost-relink"></a>
两种配对（[D-LD-03](概要设计.md#D-LD-03)），都只读取候选、不写库：

- **目录搬家** `PreviewLostRelinkMove{Kind, OldDirectory, NewDirectory}`：
  - 取 `OldDirectory` 下（含子目录）所有可找回的条目，用相对路径拼出新路径；
  - 文件存在且大小与记录相同 → `exact`；
  - 存在但大小不同 → `size_mismatch`，不可勾选；
  - 不存在 → 不列出。
- **在文件夹里找** `PreviewLostRelinkSearch{Kind, Directory, ItemIDs?}`：递归列出文件夹里的媒体文件（扩展名白名单与扫描一致），对每个待找回条目：
  - 「文件名 + 大小」唯一命中 → `name_size`（默认勾选）；
  - 否则「大小 + 扩展名」唯一命中 → `size_only`（默认不勾）；
  - 多个候选 → `ambiguous`，列出候选、不配对；
  - 同一个文件被多条记录命中时，这几条都降为 `ambiguous`。

每个候选还带两个标记：
- `outside_roots`：新路径不在任何当前扫描根内，不可执行，界面提示先加扫描目录；
- `occupied`：新路径已被另一条活动记录占用，不可执行。

**执行** `ApplyLostRelink{Kind, Pairs: [{ID, NewPath}]}`：逐条在路径锁内复核候选条件，然后：
- 失效行：视频走 `relocateVideoFrom`（更新路径、目录、名称、大小，清除失效，重同步短视频标签，触发补探测），图片走 `relocateImage`；
- 扫描器回收站行：在同一事务里取消软删、按 `restoreTrashEntry` 的成功语义直接删除它的 `missing` 回收站条目、更新路径并清除失效；事务提交后视频再触发补探测。不用 `retireTrashEntryTx`：它对 `missing` 条目会连同媒体记录一起硬删，只适用于清除（实施时修订）。

两种情况都保持记录 id 不变。每条结果为 `relinked` / `skipped(reason)` / `failed`。

### 1.3 清除

<a id="lost-purge"></a>
**预览** `PreviewLostPurge{Kind, IDs}`：只统计可清除的条目，返回：
- 条目数与总大小；
- 连带删除的播放记录数（`play_events`）与图片查看记录数；
- 受影响的标签关联、人物关联、作品集关联数；
- 会解散或缩小的版本组数；
- 观看笔记数（保留，仅告知）；
- 预计删除的派生文件大小。

**执行** `ApplyLostPurge{Kind, IDs, Confirm}`，`Confirm` 必须等于 `清除记录`，否则返回 `lost_purge_unconfirmed`。逐条在路径锁内处理：

1. **复核**：条目仍属可清除归类；`mediaPathUnavailable(path)` 为空（卷已挂载）；`os.Stat(path)` 返回不存在；没有进行中的超分任务。任一不满足 → `skipped`，原因分别为 `no_longer_lost`、`volume_offline`、`file_present`、`enhancement_active`。
2. **事务内**：
   - 版本组：成员移除前先用 `bumpVersionGroupRevision` 做条件 +1；组剩不足两个成员时解散。
   - 删除下表「需手动」的引用行。
   - 把 `viewing_diary_entries.source_play_event_id` 置空（指向这条视频的播放记录的那些）。
   - 扫描器回收站行先 `retireTrashEntryTx`。
   - 最后 `hardDeleteVideoTx` / `hardDeleteImageTx`，由外键级联清掉其余关联。
3. **事务提交后**：删除派生文件，并按需清掉播放代理。文件删不掉不算失败，留给孤儿回收。

引用行处理（视频；图片同理，取各自对应的表）：

| 处理 | 表 |
|---|---|
| 外键级联（不动） | AI 打标各表、帧哈希、感知哈希、语义与场景索引、`media_streams`、技术信息、本地元数据状态、`video_people`、`collection_videos`、字幕各表、`play_events`、短视频互动、清理忽略、榜单关联、播放代理、`video_version_members`、自动标签覆盖 |
| `hardDeleteVideoTx` 已处理 | `video_tags`、已结束的超分任务 |
| 需手动删除 | `near_duplicate_dismissals`、`clip_dismissals`、`video_version_suggestion_dismissals`（任一端是该 id）；`face_observations` 与 `face_relation_writes`（`media_kind`、`media_id` 匹配）；`playback_queue_entries` |
| 保留 | `video_bookmarks`、`viewing_diary_entries`（按设计比视频活得久）；`video_edit_items.output_video_id`、`tag_person_conversions`、`migration_staged_sources`（历史记录，由体检报告其悬挂） |

派生文件：
- 视频：`thumbnails/<id>.jpg` 与 `thumbnails/<id>.seek.*`、`media-details/videos/<id>/`、`subtitle-backups/<id>/`、上一步删掉的人脸观测对应的 `faces/<observationID>.jpg`；
- 图片：`image-thumbnails/<id>.jpg`、`image-thumbnails/<id>.view.jpg`。

清除结果按条给出 `purged`、`skipped(reason)` 或 `failed`。清除后推送片库变更事件，片库与洞察会重载。

### 1.4 孤儿文件

<a id="lost-orphans"></a>
`GetOrphanFileReport()` 只读。按下表的位置列出文件名能解析出 id、而所属记录在 `Unscoped` 下也查不到的文件，按位置给出个数与大小：

| 位置 | 判定依据 |
|---|---|
| `thumbnails/` | `videos` |
| `image-thumbnails/` | `images` |
| `media-details/videos/<id>/` | `videos` |
| `media-details/people/<id>/` | `people` |
| `media-details/collections/<id>/` | `collections` |
| `media-details/watchlist/<id>/` | 想看条目表 |
| `subtitle-backups/<id>/` | `videos` |
| `faces/<id>.jpg` | `face_observations` |
| 播放代理 | 沿用 `playback_proxy_store.go` 的孤儿统计 |

`media-details/movie_chart` 自带淘汰机制，不在范围内。文件名解析不出 id 的一律不动。壁纸副本按内容哈希命名、库里没有「当前壁纸」记录可对照，无法判定孤儿，不纳入（实施时修订）。

`ReclaimOrphanFiles{Locations}` 删除前对每个文件重新做一次判定，删除失败只计数。

## 2 元数据完整度与批量编辑

### 2.1 年份字段

<a id="mc-year"></a>
[D-MC-01](概要设计.md#D-MC-01)：

**字段**
- `models.Video` 新增 `Year *int`，不加 `default`。合法范围 1870–2100 在服务层校验，不建 CHECK 约束：SQLite 老库的表无法补加 CHECK，新老库会不一致（实施时修订）。

**NFO 导入**
- `localMovieNFO` 读 `<year>`；没有或不可用时取 `<premiered>`，再取 `<releasedate>`；只认开头恰好 4 位数字且在合法范围内的值。
- 合并规则与其他字段一致：空就自动补；已有值时只标「有更新」，由用户确认后覆盖。
- `LocalMetadataDocument` 与差异预览同步增加年份。

**NFO 导出**
- 写 `<year>`。

**详情编辑**
- `VideoDetailsUpdate` 新增 `Year *int`。`UpdateVideoDetails` 是整体替换，所有调用方（预览抽屉的编辑表单，以及将来的整页详情）必须回传年份。漏传等于清空，所以前端测试要钉住这一点。

**Jellyfin**
- 条目输出 `ProductionYear`（有值时）。按年份排序仍按 D-02 忽略。

### 2.2 完整度统计

<a id="mc-stats"></a>
`GetMetadataCompleteness() (MetadataCompleteness, error)`：
- 视频在 `visibleVideoQuery` 范围内统计，图片在 `applyImageVisibility` 范围内统计；
- 用一条 `CASE WHEN` 聚合给出各项缺失数，写法参照 `LibraryStatsService.GetStats`；
- 各项判定如下表。

| 项 `field` | 媒体 | 缺失判定 |
|---|---|---|
| `title` | 视频 | `display_title = ''` |
| `year` | 视频 | `year IS NULL` |
| `description` | 视频 | `description = ''` |
| `poster` / `fanart` | 视频 | `poster_path = ''` / `fanart_path = ''` |
| `people` | 视频 / 图片 | 不存在 `video_people` / `image_people` 行 |
| `tags` | 视频 / 图片 | 不存在 `automatic_kind = ''` 的标签关联（与「未打标签」同口径） |
| `subtitles` | 视频 | `NOT (hasAnySubtitleSQL)` |
| `technical` | 视频 | 没有 `video_technical_metadata.probed_at`，也没有视频流 |
| `thumbnail` | 视频 | `thumbnails/<id>.jpg` 不存在（列一次目录、在 Go 侧求差，不进 SQL） |
| `nfo_update` / `nfo_error` | 视频 | 本地元数据状态为 `update_available` / `error`（这两项是「待处理」而不是「缺失」，单独展示） |
| `taken_at` | 图片 | `exif_parsed_at IS NOT NULL AND taken_at IS NULL` |
| `gps` | 图片 | `exif_parsed_at IS NOT NULL AND gps_latitude IS NULL` |

- 未解析过 EXIF 的图片不计入 `taken_at` 和 `gps` 的分母，另给一个「未解析」数。
- 「缺得最多的目录」：`GetMetadataCompletenessByDirectory(kind, field, limit)` 按 `directory` 分组，取前 `limit`（默认 10）个目录。

### 2.4 批量编辑与撤销

<a id="mc-batch"></a>
**请求**：

```
MetadataBatchEditRequest {
  Kind: "video" | "image"
  Target: { IDs: []uint } 或 { Filter: LibraryFilter | ImageFilter }   // 二选一
  Ops: []MetadataBatchOp
}
MetadataBatchOp { Field, Action, Value }
```

| `Field` | `Action` | `Value` | 媒体 |
|---|---|---|---|
| `year` | `set` / `clear` | 年份 | 视频 |
| `rating` | `set` / `clear` | 0–10，步长 0.5 | 视频 / 图片 |
| `tag` | `add` / `remove` | 标签 id 列表（不含自动标签） | 视频 / 图片 |
| `person` | `add` / `remove` | 人物 id 列表 | 视频 / 图片 |
| `collection` | `add` / `remove` | 作品集 id 列表 | 视频 |

**校验**：`Ops` 非空；同一 `Field` 的 `set` 与 `clear` 不能同时出现；同一目标 id 不能同时出现在 `add` 和 `remove` 中；引用的标签、人物、作品集必须存在。违反任一条返回 `invalid_batch_edit`。

**预览** `PreviewMetadataBatchEdit` 返回目标条目数，以及每个操作「实际会改变的条目数」。已经是目标值、已有或本来没有该关联的条目不算在内。

**执行** `ApplyMetadataBatchEdit`：
- `Target.Filter` 在执行时重新解析成 id。
- 每 500 条一个事务，只写真正改变的行：标量列用条件更新，关联用 `INSERT … ON CONFLICT DO NOTHING` 或按行删除。
- 加标签保持现有语义：作废对应的待审 AI 候选。
- 去人物关联不删除人物。
- 每批同时写入撤销明细。

**撤销数据**：

```
metadata_batch_edits(id, kind, summary_json, item_count, created_at, undone_at)
metadata_batch_edit_items(id, batch_id → metadata_batch_edits ON DELETE CASCADE,
                          media_id, field, before_json, after_json)
```

- 每个实际改变的（条目，字段）记一行。关联类字段记录本次真正加上或去掉的 id。
- 只保留最近 20 次，写入新批次时删除更早的批次。

**撤销** `UndoMetadataBatchEdit(batchID)`：
- 逐行比较当前值与 `after_json`，一致才恢复 `before_json`，否则计入 `changed_since`；
- 关联类只撤销本批次加上或去掉的那几个 id；
- 撤销后写 `undone_at`；已经撤销过的批次返回 `batch_already_undone`。

**列表** `ListMetadataBatchEdits()` 给出时间、摘要、条目数，以及是否可撤销。

**选择范围**：批量操作栏现有的选择只覆盖已加载的行。「当前筛选的全部结果」是另一个按钮：先显示预览中的条目总数，再执行。

### 2.5 App 接口

`GetMetadataCompleteness`、`GetMetadataCompletenessByDirectory`、`PreviewMetadataBatchEdit`、`ApplyMetadataBatchEdit`、`ListMetadataBatchEdits`、`UndoMetadataBatchEdit`。

批量编辑在 `metadata_batch_edit` 任务键下执行，同一时刻只允许一个，第二个请求返回 `batch_edit_busy`。完成后推送片库变更事件。

## 3 本地规则自动化

### 3.1 数据

<a id="ra-data"></a>
```
automation_rules(id, name, media_kind, enabled, position,
                 conditions_json, actions_json, disabled_reason,
                 last_run_at, created_at, updated_at)
automation_rule_writes(id, rule_id → automation_rules ON DELETE CASCADE,
                       media_kind, media_id, action, target_id, inserted, created_at,
                       UNIQUE(rule_id, media_kind, media_id, action, target_id))
```

各列说明：
- `automation_rules.media_kind`：`video` 或 `image`。
- `enabled`：不加 `default`，由创建时显式写入。
- `disabled_reason`：取值为空、`target_deleted` 或 `invalid_condition`。
- `automation_rule_writes.action`：`tag` 或 `collection`。
- `automation_rule_writes.inserted`：这次是否真的插入了关系（[D-RA-03](概要设计.md#D-RA-03)）。
- `automation_rule_writes.media_id`：不挂外键，与人脸记账一样是多态引用。媒体被硬删时由失联清除和体检清理。

### 3.2 条件与动作

<a id="ra-conditions"></a>
`conditions_json` 是一个条件数组，按 AND 组合：

| `type` | 参数 | 适用 | 求值 |
|---|---|---|---|
| `under_directory` | `path` | 都 | `filepath` 语义的前缀判断，按路径段比较 |
| `name_contains` | `text` | 都 | 不区分大小写 |
| `name_glob` | `pattern` | 都 | `path.Match`，只匹配文件名 |
| `name_regex` | `pattern`（≤ 200 字符） | 都 | Go RE2，保存时编译校验 |
| `extension_in` | `exts` | 都 | 小写比较 |
| `size_between` | `min` / `max` 字节 | 都 | 闭区间，任一端可省略 |
| `duration_between` | `min` / `max` 秒 | 视频 | 时长为 0 视为未知 |
| `height_between` | `min` / `max` | 视频 | 高度为 0 视为未知 |
| `video_codec_in` | `codecs` | 视频 | 取 `media_streams` 首个视频流；没有流视为未知 |
| `has_gps` | `value` | 图片 | 未解析过 EXIF 视为未知 |

- 条件结果为未知时，整条规则对这个条目视为不满足，也不写账本，所以补探测后还能再次评估。
- 条件为空的规则不允许保存（`invalid_rule`）。
- 条件在 Go 侧求值。手动运行时先用 SQL 粗筛（目录前缀、大小、高度、时长），再在 Go 侧精筛。

`actions_json`：`[{type: "add_tag", tag_id}, {type: "add_to_collection", collection_id}]`，至少一项；`add_to_collection` 只能用于视频。两个写死的自动标签不能作为目标（它们有自己的覆盖表与同步，会把规则写入撤掉）。已保存的规则不能改媒体类型（账本按媒体类型记账）。

### 3.3 评估

<a id="ra-eval"></a>
- **规则队列**：一个内存队列加一个工作协程，结构同下载查重队列，带独立的取消上下文，退出时由 `StopAutomationRules` 取消。入队方：
  - `addVideoOrRestorePutBack` 在本地元数据观察之后、只针对新建的行入队（恢复回放的行不入队）；
  - `addImage` 新建图片后入队；
  - `TechnicalBackfillService` 对某条视频补探测成功后入队。

  入队只记 id，不在扫描的路径读锁内做任何写。
- **评估一条媒体**：按 `position` 取启用中、同媒体类型的规则，对每条规则做三步：
  1. 求值条件；
  2. 对每个动作检查账本里有没有 `(rule, media, action, target)`，有就跳过；
  3. 没有就执行动作，并在同一事务里写账本。加标签用 `INSERT INTO video_tags … ON CONFLICT DO NOTHING`，`inserted` 记录影响的行数是否为 1，插入后作废对应的待审 AI 候选。加入作品集用同样的写法。
- **手动运行**：
  - 预览：`PreviewAutomationRule(ruleID)` 在可见范围内返回会执行的条目数，以及前 50 条示例（排除账本里已有的组合）。
  - 执行：`RunAutomationRules(ruleIDs)` 在 `automation_rules` 任务键下分批执行，可取消；同一时刻只允许一次手动运行。
- **目标失效**：
  - 标签或作品集被删除时，删除对应的账本行，并从规则动作中去掉；规则没剩下动作时置 `enabled=false`、`disabled_reason=target_deleted`。
  - 标签合并时，改写规则动作与账本里的 `target_id`；改写与账本唯一键冲突时保留一行。

### 3.4 与 AI 自动打标的关系

<a id="ra-ai"></a>
[D-RA-04](概要设计.md#D-RA-04)：「已有人工标签就跳过」只认非自动标签，涉及两处，即 `hasNonAutomaticTags` 与 `findUntaggedVideos` 的 SQL。两处都要额外排除 `automation_rule_writes` 里 `inserted = true` 的（视频，标签）组合。图片的 AI 打标若有同样的跳过判定，按同一口径处理。其他所有地方（「未打标签」视图、清理时保留哪份的评分、标签筛选）把规则标签当普通标签。

### 3.5 App 接口

`ListAutomationRules`、`SaveAutomationRule(rule)`（新建或更新，校验条件与动作）、`DeleteAutomationRule(id)`、`ReorderAutomationRules(ids)`、`SetAutomationRuleEnabled(id, bool)`、`PreviewAutomationRule(id)`、`RunAutomationRules(ids)`、`CancelAutomationRuleRun()`。

错误码：`invalid_rule`（附字段说明）、`rule_not_found`、`automation_run_busy`。

## 4 数据健康检查与备份校验

### 4.1 备份产物与清单

<a id="dh-manifest"></a>
[D-DH-01](概要设计.md#D-DH-01)、[D-DH-02](概要设计.md#D-DH-02)：一份备份由三个同名前缀的文件组成：

- `cineinsight-<时间>.sqlite` 或 `.dump`：快照，格式与现在相同。
- `cineinsight-<时间>.files.tar`：文件包，不压缩（内容多为已压缩的图片），收入数据目录下的：
  - `media-details/people`
  - `media-details/collections`
  - `media-details/videos`
  - `media-details/watchlist`
  - `wallpapers`
  - `subtitle-backups`

  包内路径相对数据目录，不跟随符号链接。
- `cineinsight-<时间>.manifest.json`：
  ```
  { format: 1, backend, created_at,
    snapshot: {name, size, sha256},
    files: {name, size, sha256, entries: [{path, size, sha256}]},
    schema: {tables: {<表>: [<列>…]}},          // SQLite 取自快照；Postgres 取 pg_restore --list 的表名，列为空
    rows: {<表>: <行数>},                         // 仅 SQLite
    quick_check: "ok" | "<首条问题>" }            // 仅 SQLite
  ```

创建流程：
1. 快照写入临时文件（现有逻辑）。
2. SQLite 只读打开临时快照，执行 `PRAGMA quick_check`，统计各表行数、读取表结构；`quick_check` 不是 `ok` 时删除临时文件，这次备份记为失败。
3. 检查可用空间不少于「文件包预计大小 + 快照大小」，不够则失败，原因为 `backup_insufficient_space`。
4. 写文件包到临时文件，同时计算哈希。
5. 写清单临时文件。
6. 依次发布快照、文件包、清单。快照发布沿用排他创建加改名；清单最后发布，没有清单的半成品在下次轮转时清理。

轮转以快照为单位，连同它的文件包与清单一起删除。

列表：`ListBackups` 有清单时直接读取清单里的大小与哈希，不再逐份全量计算哈希。没有清单的备份标为 `legacy`。恢复前的「文件确认后未被改动」检查（`copyVerifiedBackup`）保持现状。

### 4.2 校验与恢复

<a id="dh-verify"></a>
`VerifyDatabaseBackup(name) (BackupVerification, error)` 在 `backup` 任务键下运行，结果包含：

- `hash_ok`：快照与文件包哈希都与清单一致；
- `files_ok`：文件包能逐条读出，条目路径、大小与清单一致；
- `quick_check`：SQLite 快照只读打开后的结果；
- `rows_ok`：各表行数与清单一致；
- `schema_compatible`；
- `level`：`full`（SQLite）、`archive`（Postgres：哈希 + `pg_restore --list` 可读）或 `legacy`（没有清单：只检查快照能否打开）。

`schema_compatible`：清单里的表和列都能在「当前已知结构」中找到。已知结构 = `AllModels` + 连接表 + Postgres 语义表 + 迁移标记表，再并上当前库实际存在的表与列（AutoMigrate 不删列，老库遗留列不能让自家备份被判为来自新版本；实施时修订）。Postgres 备份只比表名。校验结果按备份名保存在数据目录的 `backup-verifications.json`，供列表与体检读取。

恢复（`RestoreBackupWithLifecycle` 不变）新增三点：
- 有清单且 `schema_compatible=false` 时返回 `backup_from_newer_version`，不进入维护。
- 恢复前的安全备份同样带文件包与清单。它在 `quick_check` 不通过时也照常发布（问题写进清单），否则库已损坏时无法从备份恢复（实施时修订）。
- 数据库替换成功后、应用退出前，在维护围栏内恢复文件：文件包先完整解到同目录的临时位置并逐条校验，然后对每个收录目录执行「原目录改名为 `.pre-restore-<时间>`，新目录改名就位」，最后删除改名留下的旧目录（安全备份里已经有它们）。

  文件恢复失败时数据库已经替换，所以不回滚数据库：记录失败、提示「数据库已恢复，整理过的文件未能还原，可从恢复前的安全备份中取回」，并保留 `.pre-restore-*` 目录不删。旧格式备份恢复时不动这些目录。

### 4.3 体检检查项

<a id="dh-checks"></a>
`RunDataHealthCheck()` 在 `data_health` 任务键下运行，只读、可取消，单项超时 60 秒（超时记 `timeout`，继续下一项）。结果写入 `data_health_reports(id, started_at, finished_at, summary_json)`，只保留最近 10 份。

| 检查 `check` | 后端 | 方法 | 修复 |
|---|---|---|---|
| `sqlite_integrity` | SQLite | `PRAGMA quick_check` | 无（建议从备份恢复） |
| `foreign_keys` | SQLite | `PRAGMA foreign_key_check` | 无（只报） |
| `dangling_refs` | 都 | 下列无外键引用做反连接，父记录在 `Unscoped` 下不存在才算：<br>• 三类忽略表<br>• `face_observations` / `face_relation_writes`<br>• `playback_queue_entries`<br>• `automation_rule_writes`<br>• `metadata_batch_edit_items`<br>• `video_edit_items.output_video_id`<br>• `migration_staged_sources` | 历史记录（`video_edit_items`、`migration_staged_sources`）只报；其余删除悬挂行 |
| `missing_unique_indexes` | 都 | 对照 `ensureCoreQueryIndexes`、`ensureAITaggingIndexes` 与活动路径部分唯一索引的清单查索引是否存在，缺失则列出重复组 | 无（只报） |
| `derived_counts` | 都 | 先确认为纯派生的计数：场景与字幕索引的 `segment_count`、`face_clusters.observation_count`、帧哈希 `frame_count` 与数据长度。实现时逐项核实来源；不能确认的不进检查 | 按明细重算 |
| `managed_paths` | 都 | `poster_path`、`fanart_path`、人物头像、作品集封面、榜单海报等路径列：位于数据目录内且文件不存在 | 置空该列 |
| `backups` | 都 | 最近一次成功备份距今时长；最近一次校验结果；没有清单的备份数 | 链接到设置·备份 |
| `orphan_files` | 都 | 汇总[孤儿文件](#lost-orphans)报告 | 链接到失联页签 |

明确不检查：`play_count`、`last_played_at`、`images.view_count`。这些不是由明细派生的；`play_count` 在播放账本建立之前就有累计值。

**修复**：`RepairDataHealth(check) (DataHealthRepairResult, error)` 只接受上表中有修复的项。每 500 条一批，写入条件与检查条件相同，所以期间新产生的正常行不会被误删。修复完成后重跑该项。

### 4.4 App 接口

`RunDataHealthCheck`、`CancelDataHealthCheck`、`GetLatestDataHealthReport`、`RepairDataHealth`、`VerifyDatabaseBackup`。

设置页「备份」分区：
- 列表每行多出「校验」按钮和结果标记；
- 旧格式备份显示说明；
- 恢复确认框说明会同时还原整理过的文件。
