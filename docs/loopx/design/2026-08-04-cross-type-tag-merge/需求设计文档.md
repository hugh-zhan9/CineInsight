# 跨类型标签合并设计文档

## 二、需求信息

### 2.1 需求背景

- 背景：当前标签管理器和 `TagService.MergeTags` 都限制普通标签与 AI 标签只能在各自类型内合并，用户无法消除跨类型的同义标签。
- 需求目的：允许普通标签与 AI 标签互相作为合并来源和保留目标。
- 目标用户/使用方：本地片库维护者。
- 需求来源：2026-08-04 用户明确反馈“不能把 AI 标签和普通标签合并”。
- 等价验收标准：
  - `AC-001`：选择任意非自动标签作为保留目标后，可以选择普通标签和 AI 标签作为来源。
  - `AC-002`：合并后保留目标标签的 ID、名称、颜色、命名空间和 `is_system` 身份；来源关联和历史引用转移到目标，来源软删除。
  - `AC-003`：自动标签仍不能作为目标或来源，既有去重、事务和确认行为保持不变。

### 2.2 需求范围

- 本期范围：标签管理器的目标/来源选择；服务端跨类型校验；相关前后端回归测试；项目上下文说明。
- 非目标：不改变 AI 标签库配置入口，不自动决定保留哪一类标签，不修改表结构，不允许自动标签参与合并。
- 决策边界：用户通过“保留目标”显式决定最终标签身份；来源标签的类型不改变目标类型。
- 依赖方：Vue 标签管理器、Wails `MergeTags` API、Go `TagService`、现有 GORM 事务。
- 约束条件：保持 `MergeTags(sourceTagIDs, targetTagID)` 接口签名和返回结构稳定。
- 触发的辅助 skills：go-style。

## 三、概要设计

### 3.1 方案总述

- 设计目标：解除人为的同类型限制，同时保留目标优先和自动标签保护语义。
- 总体思路：类型筛选仅用于缩小目标列表；目标确定后，来源列表展示所有其他非自动标签。服务端删除 `IsSystem` 相等校验，以目标记录作为最终身份权威。
- 核心模块：`TagManagerDialog.vue`、`TagService.MergeTags`。
- 主要难点：AI 历史引用、视频关联和偏好权重必须继续在一个事务内转移并去重。
- 技术指标：不新增数据库查询轮次和网络接口；合并仍为单事务操作。

### 3.6 专项设计检查

| 辅助 skill | 触发原因 | 检查内容 | 设计结论 |
|---|---|---|---|
| go-style | 修改 Go 服务与测试 | 本地风格、错误处理、表驱动边界、gofmt | 删除单一业务禁令，不引入新抽象或错误类型；以真实数据库测试固定行为。 |

## 四、详细设计

### 4.1 标签管理器详细设计

#### 4.1.1 需求内容

- 入口：标签管理 → 合并同义标签。
- 操作人/调用方：本地用户。
- 前置条件：至少存在两个非自动标签。
- 输出结果：可跨普通/AI 类型选择来源并提交既有 `MergeTags` API。

#### 4.1.2 方案设计

- **`D-001`（AC-001，behavior contract）**：普通/AI 切换只筛选保留目标；选定目标后，来源候选为除目标外的全部非自动标签，并显示各自类型。
- 目标切换时仍清理已经不合法的来源 ID；因为唯一不合法来源是目标自身或已不在数据中的标签，跨类型选择不会再被清除。
- 确认文案继续列出目标和来源，不增加隐式类型转换。

#### 4.1.3 流程步骤

1. 用户按类型缩小目标标签列表并选择保留目标。
2. 界面展示所有其他非自动标签，用户可搜索、多选。
3. 用户确认后调用既有 `MergeTags` API。

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 目标为普通、来源含 AI | 允许提交 | AI 来源标识清晰可见 | 复用现有 API 日志 |
| 目标为 AI、来源含普通 | 允许提交 | 普通来源标识清晰可见 | 复用现有 API 日志 |
| 自动标签 | 从目标和来源候选中排除 | 不可选择 | 不涉及 |
| 目标切换 | 移除新目标自身，保留仍合法的其他来源 | 已选数量同步变化 | 不涉及 |
| 重复点击/并发 | 复用加载态和服务端事务；来源已删除时返回既有错误 | 显示合并失败 | 复用现有日志 |

#### 4.1.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| 必须显式选择目标与至少一个来源 | 防止误操作 | 组件测试 |
| 合并前二次确认 | 操作不可自动撤销 | 组件测试 |
| 名称搜索、全选可见、清空选择 | 保持现有交互能力 | 前端测试套件 |

### 4.2 标签合并服务详细设计

#### 4.2.1 需求内容

- 入口：`TagService.MergeTags`。
- 操作人/调用方：Wails `App.MergeTags`。
- 前置条件：目标与来源均存在且均非自动标签。
- 输出结果：来源的所有关联迁移到目标并软删除来源。

#### 4.2.2 方案设计

- **`D-002`（AC-002，data contract）**：目标标签是合并后身份的唯一权威；跨类型来源不会覆盖目标的 `is_system`、命名空间、名称、颜色或其他目标字段。
- **`D-003`（AC-003，compatibility contract）**：移除普通/AI 类型相等校验，但保留自动标签校验、来源存在性校验、视频关联去重、候选引用更新、审批记录去重、偏好权重求和和事务软删除；AI 来源合并到普通目标时，仍处于待审状态的候选必须转为 `superseded`，避免保留指向非 AI 标签库目标的可批准候选。
- 接口、返回值、日志字段和数据库结构不变。

#### 4.2.3 流程步骤

1. 规范化并校验目标/来源 ID。
2. 在事务中加载目标和全部来源，拒绝自动标签。
3. 迁移视频、候选、审批和偏好引用。
4. 软删除来源并提交事务。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 普通来源合并到 AI 目标 | 迁移引用，保留目标 `is_system=true` | 成功 | API 合并日志 |
| AI 来源合并到普通目标 | 迁移引用，保留目标 `is_system=false` | 成功 | API 合并日志 |
| AI 来源仍有待审候选 | 候选引用迁移到目标并标记 `superseded` | 不再出现在待审列表 | API 合并日志 |
| 来源包含自动标签 | 整体事务拒绝 | 返回现有错误 | API 错误日志 |
| 来源重复或包含目标 | 继续按既有规则去重/忽略目标 | 无额外感知 | 不涉及 |
| 部分来源不存在 | 整体事务拒绝，不产生部分迁移 | 显示失败 | API 错误日志 |
| 遗留数据 | 不需要迁移；仅影响之后的显式合并 | 无升级操作 | 不涉及 |
| 回滚 | 任一步失败由数据库事务回滚 | 不出现部分成功 | API 错误日志 |

#### 4.2.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| Wails API 签名与返回结构 | 保持前端兼容 | Go 编译与前端构建 |
| 来源软删除而非硬删除 | 保持历史和唯一性语义 | 服务测试 |
| 全部关联迁移在单事务内完成 | 防止部分合并 | 服务测试 |

### 10.5 Planning Handoff

- `plan2exec` 可以决定：测试命名和最小代码组织方式。
- 必须返回 `spec` 的事项：改变目标身份保留规则、允许自动标签参与、修改 API 或表结构。
- 必须返回 `clarify` 的事项：要求系统自动选择普通/AI 身份，或对跨类型方向施加新的不对称限制。
- 推荐下一步：按 `D-001` 至 `D-003` 直接执行最小修复；范围较小，无需持久执行计划。
