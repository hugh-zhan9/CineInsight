## 二、需求信息

### 2.1 需求背景

- **背景**：应用当前强制依赖 PostgreSQL——`database.Init()` 只调用 `postgres.Open(dsn)`，`.env` 缺 `PG_HOST` 直接启动失败。用户需要在没有 Postgres 的机器上也能跑起来。
- **需求目的**：支持 SQLite 作为可选后端，并允许在两种后端之间切换、切换时把数据一并搬过去。
- **目标用户**：应用的唯一用户（本机单人使用）。
- **关联原始材料**：本次会话中用户的两项裁决——「切换时把数据一并搬过去」「SQLite 备份实现独立分支」。
- 本需求无 intake package；需求来源是用户在会话中的直接口述与选择。

### 2.2 需求范围

- **本期范围**：
  1. 连接层按配置选择 SQLite / PostgreSQL 驱动；
  2. 修掉在 SQLite 上会产出错误数据的方言写法；
  3. 双向全量数据迁移（36 张 GORM 表 + 2 张隐式关联表）；
  4. SQLite 的备份/恢复分支；
  5. 设置页的后端切换入口与迁移进度。
- **非目标**：
  - 不做「同时连两个库」或「读写分离」；任一时刻只有一个活动后端。
  - 不在 SQLite 上实现语义检索（依赖 pgvector，见 D-004）。
  - 不扩展或复用 `cmd/migrate_sqlite_to_pg`（见 D-006）。
  - 不改动任何业务语义：随机加权、清理判定、AI 打标闭集、软删除与回收站、文件迁移安全边界原样保留。
  - 不做运行时热切换数据库句柄（见 D-007）。
- **决策边界**：本文档确定后端选择规则、迁移语义与备份语义。表结构本身不变——两个后端共用同一份 `models.AllModels()`。
- **约束条件**：单机桌面应用，无灰度、无监控面、无多实例并发。
- **触发的辅助 skills**：`sql-style`（方言、迁移、索引）、`go-style`（连接层与迁移器实现）。

### 2.3 可行性分析

- **技术可行性：高，且比表面看上去近得多。** 实测证据：
  - `gorm.io/driver/sqlite` 已是**直接依赖**（`go.mod:13`，非 indirect）；**整套 Go 测试本来就跑在 SQLite 上**，建库走的是同一份 `db.AutoMigrate(models.AllModels()...)`。这说明 36 张表的模型定义早已双方言兼容。
  - 逐项实测（一次性探针，已删除）结果：

    | 写法 | 出现处 | SQLite 实测 |
    |---|---|---|
    | 部分索引 `WHERE deleted_at IS NULL` | `ensureCoreQueryIndexes` 等 | 正常 |
    | 部分唯一索引 + `status IN (...)` | `idx_enhancement_tasks_active_source` | 正常 |
    | `ORDER BY ... NULLS LAST` | 4 处 | 正常 |
    | `ON CONFLICT DO NOTHING` | 7 处 | 正常（SQLite 3.24+） |
    | `SELECT ... FOR UPDATE` | 21 处 | **静默忽略**，但安全，见 D-003 |
    | `CAST(x AS DATE)` | 2 处 | **返回 `2026` 而非 `2026-09-01`**，见 D-002 |

- **关键风险**：
  1. **静默错误数据**（`CAST AS DATE`）。不报错、不崩溃，观看热力图把一整年的播放塞进一个格子。这类 bug 最难在验收中发现，必须在实现前就定死修法。
  2. **Postgres 路径当前零测试覆盖**。测试全跑 SQLite，PG 分支靠生产使用验证。加了第二个后端之后，"改 A 坏 B" 的风险从零变成真实存在，验证策略必须同时覆盖两个后端（见 11.3）。
  3. **迁移的 ID 保持与序列重置**。见 D-006 边界。
- **替代方案**：见 3.1「被否决的做法」。

## 三、概要设计

### 3.1 方案总述

- **设计目标**：让应用在有/没有 PostgreSQL 的机器上都能完整运行；两种后端之间可以带数据切换；切换过程任何一步失败都不丢数据。
- **总体思路**：
  1. **表结构不分叉**。两个后端共用 `models.AllModels()`，靠 GORM 的 AutoMigrate 各自建表。不引入手写 DDL 的双份维护。
  2. **方言差异优先在 Go 侧消解，而不是写两套 SQL 分支。** 这是仓库既有惯例——`ListImageTimelineBuckets` 的注释已明确写道：「年月提取在 SQLite（strftime）与 PostgreSQL（EXTRACT/to_char）上写法不同，下推要写两套分支，而测试只跑得到 SQLite 那套」。同样的理由适用于本次的热力图分组。
  3. **迁移是复制而非移动。** 源库全程只读，迁移完成后仍然完整存在。这条性质是整个回滚方案的基础（见 8.4）。
  4. **切换需要重启。** 不热换句柄（见 D-007）。
- **核心模块**：连接层（`database`）、方言消解（`services` 两处聚合）、迁移器（新 `database/migrator`）、备份服务（`services/backup_service` 加分支）、设置页切换 UI。
- **主要难点**：迁移的 ID 保持与 Postgres 序列重置；pgvector 向量无法跨后端携带时索引状态的正确表达。
- **被否决的做法**：
  - *为两个后端写两套 SQL 分支*——测试只跑得到 SQLite 那套，PG 分支会长期无覆盖地腐化。仓库已有成文反对意见。
  - *扩展 `cmd/migrate_sqlite_to_pg`*——它只覆盖 7 类实体（Videos/Tags/Settings/ScanDirectories/ShortFeedInteractions/ShortFeedTagPreferences/VideoTags），是 schema 还很小时的历史工具，现有 36 张表。在它上面加，不如按 `AllModels()` 写一个通用的。
  - *迁移时移动数据（源库清空）*——一旦中途失败就两边都不完整，没有安全的回滚点。

### 3.3 核心流程设计

| 流程 | 触发条件 | 参与模块 | 主流程 | 异常/补偿 | 输出 |
|---|---|---|---|---|---|
| 启动选后端 | 应用启动 | `database.Init` | 读配置 → 决定后端 → 连接 → AutoMigrate → 建索引 → 语义向量能力探测 | 连接失败沿用现有 `GetStartupError` 界面 | 活动 `database.DB` |
| 带数据切换 | 用户在设置页确认 | 设置页 → 迁移器 | 预检（目标可连、目标为空）→ 逐表复制 → 校验行数 → 写完成标记 → 写配置 → 提示重启 | 任一步失败：保留源库、标记目标不完整、不改配置 | 新后端配置 + 提示重启 |
| SQLite 备份 | 定时或手动 | 备份服务 | `VACUUM INTO` 写快照 → 按保留份数清理 | 写失败沿用现有失败态展示 | `.sqlite` 快照文件 |
| SQLite 恢复 | 用户确认 | 备份服务 | 校验快照后端类型 → 替换库文件 → 提示重启 | 后端类型不符直接拒绝 | 提示重启 |

### 3.4 功能模块

| 模块 | 职责 | 关键功能 | 依赖 | 备注 |
|---|---|---|---|---|
| `database` 连接层 | 按配置开对应驱动 | 后端判定、DSN/路径解析、AutoMigrate、索引 | GORM 两个 driver | 现有 `Init()` 内联改造 |
| 方言消解 | 去掉会产出错误数据的 SQL | 热力图分组改 Go 侧归并 | - | 2 处 |

| 设置页 | 切换入口 | 后端选择、预检提示、迁移进度、重启提示 | 新 Wails 绑定 | 新分区 |

### 3.6 专项设计检查

| 辅助 skill | 触发原因 | 检查内容 | 设计结论 |
|---|---|---|---|
| `sql-style` | 方言差异、迁移、索引 | 部分索引/NULLS LAST/ON CONFLICT 可移植性；`CAST AS DATE` 语义；序列重置 | 索引与冲突写法均可移植；`CAST AS DATE` 必须改 Go 侧归并；PG 侧迁移后必须 `setval` 重置序列 |

## 四、详细设计

### 4.1 连接层与后端选择

#### 4.1.1 需求内容

- **入口**：`database.Init()`。
- **调用方**：应用启动（`app.go: startup`）。
- **前置条件**：无。
- **输出结果**：`database.DB` 指向活动后端。

#### 4.1.2 方案设计

**D-001｜后端选择规则（兼容性契约）**

配置项 `DB_BACKEND`（`.env`），取值 `sqlite` / `postgres`。未设置时按下述规则自动判定，**目的是让现有安装升级后行为完全不变**：

- `DB_BACKEND` 显式设置 → 用它；
- 未设置且 `PG_HOST` 非空 → `postgres`（现有安装走这条，库不变）；
- 未设置且 `PG_HOST` 为空 → `sqlite`（新机器开箱即用）。

SQLite 库路径：`~/.video-master/library.db`，可用 `SQLITE_PATH` 覆盖。

**刻意不复用历史路径**：`cmd/migrate_sqlite_to_pg` 里的历史 SQLite 路径是 `~/.video-master/video-master.db`。若机器上残留那份旧库，自动采纳会让用户看到一份很久以前的陈旧片库，且看不出发生了什么。新后端一律用新文件名；旧文件不读、不删、不提示。

#### 4.1.3 流程步骤

1. `loadEnvConfig()`（现有）。
2. 判定后端（D-001）。
3. SQLite：确保目录存在，`sqlite.Open(path)`；Postgres：沿用 `postgresDSNFromEnv()`。
4. 其余步骤（清理重复、AutoMigrate、各 `ensure*Indexes`、默认设置初始化）两后端共用，不分叉。

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户感知 | 备注 |
|---|---|---|---|
| `DB_BACKEND` 取值非法 | 启动失败并明确报出取值 | 现有启动错误页 | 不静默回退，回退会让用户以为连上了实际另一个库 |
| SQLite 路径不可写 | 启动失败，报出路径 | 现有启动错误页 | - |
| 现有安装升级 | `PG_HOST` 仍在 → 仍走 postgres | 无感 | **最重要的兼容性约束** |
| 残留历史 `video-master.db` | 不读不删不提示 | 无感 | 见 4.1.2 |
| 两个后端都配了 | `DB_BACKEND` 决定；未设则 postgres 优先 | 无感 | - |

#### 4.1.5 不变行为

| 行为 | 保持不变的原因 | 验证方式 |
|---|---|---|
| 已配置 `PG_HOST` 的安装继续连 Postgres | 升级不得让用户看起来丢库 | 新增测试：设 `PG_HOST` 不设 `DB_BACKEND` → 判定为 postgres |
| `AutoMigrate` + `ensure*Indexes` 的调用顺序 | 顺序本身承载了迁移依赖 | 现有启动路径不改 |
| 启动失败的错误展示 | 现有 `GetStartupError` 界面已覆盖 | 现有测试 |

### 4.2 方言差异消解

#### 4.2.1 需求内容

- **入口**：`LibraryStatsService.GetStats()` 的观看热力图分组。
- **输出结果**：与 Postgres 上完全一致的按日分组计数。

#### 4.2.2 方案设计

**D-002｜`CAST(x AS DATE)` 改为 Go 侧按本地日期归并**

现状：`services/library_stats_service.go` 用
`Select("CAST(last_played_at AS DATE) AS date, COUNT(*) AS count").Group("CAST(last_played_at AS DATE)")`。
SQLite 无 DATE 类型，`CAST` 走 NUMERIC 亲和性，实测返回 `2026`——**一年的播放全部落进一个格子，且不报错**。

改法：只取 `last_played_at` 列，在 Go 侧按 `time.Local` 归并成 `YYYY-MM-DD`。理由与 `ListImageTimelineBuckets` 完全相同，且顺带消除了 Postgres 侧 `timestamptz` 按会话时区取值与前端按本地日期渲染之间的潜在错位——前端 `heatmapDays` 本来就是按本地日期构建坐标轴的。

数据量可接受：只投影一列、只取近一年有播放记录的行。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 用户感知 |
|---|---|---|
| `last_played_at` 为 NULL | 现有查询已 `WHERE last_played_at >= ?` 排除 | 无 |
| 跨时区（用户改系统时区） | 按当前 `time.Local` 归并，与前端坐标轴同源 | 分组随系统时区一致变化 |
| 一年内无任何播放 | 返回空切片，前端渲染全灰热力图 | 现有行为 |

#### 4.2.5 不变行为

| 行为 | 原因 | 验证方式 |
|---|---|---|
| 热力图口径为「按最后播放日期计视频数」 | 不是本次要改的语义 | 新增双后端一致性测试（11.3） |

### 4.3 行锁语义

**D-003｜`SELECT FOR UPDATE` 在 SQLite 上被忽略，且这是安全的**

21 处 `clause.Locking{Strength: "UPDATE"}` 在 SQLite 上实测不报错也不生效。**不移除这些子句**——Postgres 上它们是必需的。

安全性论证：SQLite 的写事务在数据库级互斥（单写者），并发写事务被串行化，其保证强于行级锁，因此「读-改-写」的丢更新在 SQLite 上不可能发生。

这条结论必须由测试钉住而不是只写在文档里：并发跑同一条 upsert 路径，断言无丢更新（11.3）。

**不变行为**：所有现有 `clause.Locking` 调用点一个都不改。

### 4.4 语义检索能力

**D-004｜SQLite 下语义检索不可用，且必须显式说明而非搜出空结果**

现状已具备降级：`database.PrepareSemanticVectorStorage` 判断 `db.Dialector.Name() != "postgres"` 时返回 `pgvector_requires_postgres`，图片侧同理。本设计不新增降级逻辑。

前端需确认两处已有提示在 SQLite 模式下确实被触发：视频库的 `semanticSearchErrorText`、图片库的 `semanticNotice`（该处已有 `semanticAvailable` 控制「语义」按钮禁用）。**验收标准是「入口置灰并说明原因」，不是「搜索返回空」**。

### 4.5 双向数据迁移

#### 4.5.1 需求内容

- **入口**：设置页「切换数据库后端」。
- **前置条件**：目标后端可连接，且目标库为空。
- **输出结果**：目标库含与源库一致的全量数据；源库不变。

#### 4.5.2 方案设计

**D-006｜通用迁移器，复制而非移动**

- 表清单由 `models.AllModels()`（36 张）驱动，另加两张隐式多对多关联表 `video_tags`、`image_tags`（`VideoPerson` / `CollectionVideo` 是显式模型，已在 `AllModels()` 中）。
- 逐表分批读源、批量写目标，**保留主键**——否则所有外键与关联行全部失效。
- **Postgres 作为目标时必须重置序列**：显式带 ID 插入不会推进 `BIGSERIAL` 序列，迁移后第一次新建记录会主键冲突。每张表迁完执行
  `setval(pg_get_serial_sequence('<table>','id'), COALESCE((SELECT MAX(id) FROM <table>), 1))`。
  SQLite 作为目标无此问题（`AUTOINCREMENT`/rowid 取 max+1）。
- **软删除行一并迁移**：回收站与「否认后不得重复确认」等语义都依赖软删除行存在，`Unscoped()` 读取。
- **pgvector 向量不跨后端携带**：
  - PG → SQLite：`video_semantic_vectors` / `image_semantic_vectors` 不迁移；同时清空语义索引元数据行，使 UI 报「需要重建」而不是声称索引存在却搜不出东西。
  - SQLite → PG：目标向量表为空，用户在设置页重建索引。
- 每张表一个事务；全部完成后写入一条完成标记（复用 `Settings` 的一个新字段或独立小表，实现期定）。目标库存在但无完成标记 = 半迁移状态。

#### 4.5.3 流程步骤

1. 预检：目标可连接；目标为空（无完成标记且核心表无行）。
2. 在目标上 `AutoMigrate` 建表建索引。
3. 按依赖无关顺序逐表复制（保留 ID，故无需拓扑排序）。
4. 复制两张隐式关联表。
5. 目标为 Postgres 时逐表重置序列。
6. 逐表校验行数与源一致。
7. 写完成标记 → 写 `DB_BACKEND` 配置 → 提示重启。

#### 4.5.4 边界条件

| 场景 | 处理方式 | 用户感知 |
|---|---|---|
| 目标库非空 | 拒绝迁移 | 明确提示「目标库已有数据，请先清空或换一个库」 |
| 迁移中途失败 | 停止，保留源库，不写完成标记，不改配置 | 报出失败表名与原因；可重试 |
| 迁移中进程被杀 | 目标处于半迁移状态（无完成标记） | 下次迁移预检拒绝，要求显式清空目标 |
| 大库耗时 | 分批 + 进度上报（表名 + 已完成/总表数） | 进度可见，不假死 |
| 源库有软删除行 | `Unscoped()` 一并迁移 | 回收站内容保留 |
| PG→SQLite 且已建语义索引 | 丢弃向量并清空索引元数据 | 语义入口置灰并提示需重建 |
| SQLite→PG 后新建记录 | 已重置序列 | 无感（未重置则会主键冲突） |
| 迁移完成后不重启 | 配置已写但句柄未换 | 明确提示必须重启；未重启前仍用旧后端 |

#### 4.5.5 不变行为

| 行为 | 原因 | 验证方式 |
|---|---|---|
| 源库在迁移全程只读 | 回滚方案的基础 | 迁移后校验源库行数与迁移前一致 |
| `cmd/migrate_sqlite_to_pg` 保持原样 | 历史工具，不在本期范围 | 不改该目录 |
| 表结构由 `AllModels()` 单一来源定义 | 避免双份 DDL 维护 | 两后端都走 `AutoMigrate` |

### 4.6 备份与恢复

**D-005｜SQLite 备份走 `VACUUM INTO`**

- 备份：`VACUUM INTO '<backup_dir>/<timestamp>.sqlite'`——产出单文件一致性快照，不需要停写。
- 复用现有的备份目录、保留份数、定时间隔与恢复确认 UI，不新建一套配置。
- 恢复：替换库文件后必须重启（不能安全地换掉正在使用的句柄）。
- **跨后端误恢复必须拒绝**：PG 快照是 `pg_dump` 自定义格式，SQLite 快照是 `.sqlite` 文件。恢复前按当前后端与快照类型校验，不符直接拒绝并说明，不尝试。

#### 4.6.4 边界条件

| 场景 | 处理方式 | 用户感知 |
|---|---|---|
| 备份目录不可写 | 沿用现有失败态 | 现有备份状态展示 |
| 快照与当前后端不匹配 | 拒绝并说明 | 明确提示 |
| 恢复后未重启 | 提示必须重启 | 明确提示 |
| 磁盘空间不足 | `VACUUM INTO` 失败，保留原库 | 现有失败态 |

#### 4.6.5 不变行为

| 行为 | 原因 | 验证方式 |
|---|---|---|
| Postgres 下的备份/恢复路径 | 现有功能不得回归 | 现有 `backup_service_test.go` 全绿 |
| 保留份数与定时间隔的语义 | 两后端共用同一份设置 | 现有测试 |

### 4.7 外键约束一致性

**D-009｜SQLite 必须开启外键约束**

**发现过程**：P-002 建好双后端测试基座后，同一套测试在 Postgres 上首跑出现 3 处失败。
其中 2 处的根因是 SQLite 默认关闭外键约束（`mattn/go-sqlite3` 不加 `_foreign_keys=1`
时 FK 不生效），而 Postgres 强制执行——测试夹具里凭空写的关联 ID 在 SQLite 上插得进去，
在 Postgres 上被拒绝。

**为什么必须统一而不是各自保留**：这不只是"两边不一致"的洁癖问题。若 SQLite 侧不强制
外键，用户在 SQLite 模式下可能积累孤儿行；随后按 D-006 迁往 Postgres 时，迁移会在中途
因外键冲突失败。「带数据切换」是本需求的核心承诺，一个能让它中途失败的差异不能留着。

**结论**：SQLite 连接串统一附加 `_foreign_keys=1`（`database.SQLiteDSN`），生产与测试
走同一个构造函数。两个后端的数据完整性保证由此一致。

**对既有测试的影响**：开启后暴露出两处夹具在构造外键约束下不可达的状态。修法不是放宽
约束，而是改成构造真实可达的场景——例如「matched tag 缺失」的真实触发是标签被软删除
（行还在、外键成立，但按作用域查不到），而不是指向一个从不存在的 ID。改完的测试比原来
更贴近生产。

第 3 处失败与外键无关：测试断言写死了 `?` 占位符，而 Postgres 渲染成 `$1`。SQL 语义
相同，归一化占位符后比对即可。

#### 4.7.4 边界条件

| 场景 | 处理方式 | 用户感知 |
|---|---|---|
| 存量 SQLite 库已有孤儿行 | 本设计不提供清理；开启约束后既有孤儿行不会被自动删除，但新的写入会被拒绝 | 迁移预检会暴露问题 |
| 迁移时源库有孤儿行 | 迁移到 Postgres 会失败并报出表名 | 明确失败优于静默丢行 |

#### 4.7.5 不变行为

| 行为 | 原因 | 验证方式 |
|---|---|---|
| Postgres 侧外键行为 | 一直如此，不变 | 双后端全套测试 |

### 5.2 数据迁移/初始化

- **DDL**：无手写 DDL 变更。两后端都由 `AutoMigrate(models.AllModels()...)` 建表，`ensure*Indexes` 建索引（实测均可在 SQLite 执行）。

## 八、系统发布

### 8.4 回滚方案

- **回滚条件**：切换后发现新后端数据或性能不符预期。
- **回滚步骤**：把 `DB_BACKEND` 改回原值并重启。
- **数据回滚**：不需要——迁移是复制，源库全程只读且完整保留。这是选择「复制而非移动」的唯一理由。
- **风险**：回滚后，切换之后在新后端产生的改动不会回到旧库。需在切换确认时明确告知。

## 十、排期与规划

### 10.5 Planning Handoff

`plan2exec` 可以自行决定的：切片划分与顺序、迁移器的内部结构与批大小、完成标记的存放形式（Settings 字段或独立小表）、进度事件的具体字段名、设置页新分区的位置与文案。

必须回到 `spec` 或 `clarify` 的：
- 需要改变 D-001 的后端判定规则（影响现有安装的兼容性）；
- 需要让迁移变成「移动」而非「复制」（推翻 8.4 回滚方案的前提）；
- 需要在 SQLite 上提供语义检索（推翻 D-004）；
- 发现某处业务语义在两个后端下不一致且无法在 Go 侧消解（本设计假定除已列两处外不存在这种情况——若发现，是设计假设被证伪，须回来修订）。

### 11.3 Verification Strategy

本需求无 `TC-*` 编号（需求来源是口述裁决），下列为设计级验证策略：

1. **双后端跑同一套 Go 测试。**（已完成，见 P-002）当前测试只跑 SQLite，Postgres 分支零覆盖。新增按环境变量选择测试后端的能力，使 CI/本地可分别在两个后端上跑完整套件。**这是本设计最重要的验证投入**——没有它，「改 A 坏 B」无法被发现。
2. **后端判定规则测试**（D-001）：四种配置组合各断言一次，重点是「有 `PG_HOST` 无 `DB_BACKEND` → postgres」。
3. **热力图双后端一致性测试**（D-002）：同一批数据在两个后端产出相同的按日分组。这条测试如果只在 SQLite 上跑，恰好会掩盖本次要修的 bug，必须双跑。
4. **并发无丢更新测试**（D-003）：SQLite 上并发执行 upsert 路径，断言最终计数正确。
5. **迁移往返测试**（D-006）：SQLite → PG → SQLite，逐表比对行数与主键集合；含软删除行；断言源库前后不变。
6. **序列重置测试**（D-006）：迁移到 PG 后立即新建一条记录，断言不冲突。
7. **备份跨后端拒绝测试**（D-005）：用 PG 快照在 SQLite 模式下恢复，断言被拒绝且未改动库文件。
8. **现有 `backup_service_test.go` 全绿**，确认 Postgres 备份路径无回归。
