# 应用内预览支持 mov / mkv / avi 等格式 · 需求设计文档

状态：Accepted 并已实施（2026-10-13）；同日按独立评审修订（自动代理按宿主记账、大小上限、编码规则补全）。
来源：用户 2026-10-13 裁决「直接播 + 自动代理」；大小上限为集成方裁决（同日）。

## 裁决与规则

<a id="D-PF01"></a>
**D-PF01 · 直放按实际编码判定。** 没有有效代理时（「先查代理」不变），桌面预览查判定表 `decideDesktopPreview`（`services/preview_direct_play.go`），与手机端 / Jellyfin 的 `inlinePreviewMIMEs` 分开（`TestInlinePreviewMIMEsUnchanged`）：

| 条件 | 结果 |
|---|---|
| .mp4 / .m4v / .mov，容器确是 ISO-BMFF（`format_name` 含 mov 或 mp4；缺失不否决）；视频 h264（像素格式 yuv420p / yuvj420p / nv12，未知不否决）、hevc（标签不是 hev1，未知不否决）或 prores；音频 aac / mp3 / alac / ac3 / eac3 / pcm_s16le / pcm_s16be / pcm_s24le / pcm_s24be / pcm_s32le / pcm_f32le 或无音频 | `inline` 直放源文件（MIME video/mp4 / video/x-m4v / video/quicktime） |
| .webm / .ogv / .ogg | 照旧按扩展名直放 |
| 其余（编码不符的上面三种扩展名、mkv、avi、wmv、flv、ts…） | 要代理，见 D-PF02 |
| 技术快照判不出 | 按扩展名沿用旧行为（mp4 / m4v 内嵌，其余外部预览） |

快照缺失或不新鲜时用播放代理同一套探测（`MediaProbeService.Refresh` + `loadPlaybackProxySnapshot`）补探一次，期限 5 秒；探测失败、超时或探出来没有视频流，按「视频 + 源指纹」记在内存里，本次运行内再打开同一份源直接走旧行为，源文件变了才再探。快照新增 `media_streams.codec_tag`（ffprobe `codec_tag_string`，mkv 的占位标签存空串），之前的快照为空串，按「未知」处理——这类 hev1 文件在 `<video>` 报错后由 D-PF03 兜住。代理策略同步收紧：H.264 不是 8 位 4:2:0 时不再 remux，改转码；HEVC 照旧 remux 并一律打 hvc1。正式播放（`PlayVideo`）照旧打开源文件。

<a id="D-PF02"></a>
**D-PF02 · 要代理时自动生成，太大的只给手动。** 本机没有 ffmpeg（或没有代理服务）时按旧行为，不尝试、不落失败记录。否则估算产物大小：remux 取源大小；转码按「转码实际用的目标视频码率 min(源码率, 8 Mbps) + 音频 160 kbps」× 时长，时长未知时取源大小。估算超过 min(10 GiB, 代理上限 × 20%)（上限为 0 即不限时取 10 GiB）时会话为 `proxy-manual`，说明「文件较大（约 X GB），生成播放代理会占用相同大小的空间」，只给手动「生成播放代理」与「用系统播放器预览」；手动生成行为不变。其余为 `proxy-preparing`：宿主自动请求代理，显示「排队中（第 N 个）」/「生成中」与系统播放器按钮，就绪后重取会话切到内嵌；失败显示既有失败文案，留着系统播放器与手动生成按钮。

<a id="D-PF03"></a>
**D-PF03 · 直放解码失败也自动代理。** 直放源在 `<video>` 报错时，内嵌播放器同样自动请求代理（两个按钮照留）；经代理播放时不再请求。

<a id="D-PF04"></a>
**D-PF04 · 自动代理按宿主记账。** 每个预览宿主实例带一个 owner（内嵌播放器、字幕工作台、版本对比的每一侧）。后端 `PlaybackProxyService.EnqueueAuto(video, owner)` / `CancelAuto(video, owner)`（App `RequestPreviewProxy` / `CancelPreviewProxy`）按视频记 owner 集合：
- 请求加入 owner，没在排队或处理就入队（用户发起，不过空闲门，与手动项同一条 FIFO、不插队）；取消移除 owner，最后一个 owner 走了才取消这一项——排队中当场摘掉，处理中只停这一项（每项一个可单独取消的 ctx，整轮照跑）。抽屉（片库页常驻挂载）与整页详情看同一部时互不取消；宿主换片只撤销自己的上一项请求。
- 同时在等的自动代理最多 2 部，第三部直接拒绝（`auto_proxy_limit`），宿主显示「已有 2 部视频在等自动生成的播放代理……」并给手动按钮。选拒绝而不是取消最旧的一项：被取消的那一项可能另有宿主正在等。
- 处理中的一项刚被取消、取消结果还没记下时又有人要它（快速 A→B→A，或手动入口）：先记下，结果落下后立刻重排，不会把这次请求吞掉。
- 做好的代理保留交给 LRU。手动入口（按钮、批量、按筛选、扫描后自动）从不被预览取消；手动再点一次自动项即转成手动项；已被手动排进去的视频请求自动代理时只跟着它走、不记 owner。
- 只有预览自动代理的一轮（状态 `auto_only`）跑完不发桌面通知，片库页也不弹「播放代理完成：…」；播放器自己显示进度与结果。

## 宿主

内嵌播放器（详情抽屉、整页详情）自己跟踪进度（它还管手动生成），框里进度与提示用 `role="status"`、失败用 `role="alert"` 两个元素；整页详情在框里已显示时不在框下重复。字幕工作台与版本对比经 `utils/previewProxy.js` 的跟随器做同样的事（`proxy-preparing` 自动请求、就绪后重取会话，`proxy-manual` 与失败后给手动按钮，关闭时撤销）；两者与播放器共用 `advanceProxyTracking` 推进跟踪。待播队列播放器不用预览会话，不在本次范围。用户在本次预览里删掉代理后播放器不当场重建。

## 实施中的取舍

- 入队由宿主发起，不在 `GetPreviewSession` 里：读会话的地方不止预览（版本对比一次读两个），读会话不该有副作用。
- 转码估算按转码实际用的目标码率而不是一律按 8 Mbps：低码率的长片转出来本来就小，一律按上限会把它们误挡成「只能手动」。
- mkv 等也补探快照：估算大小要知道走 remux 还是转码；探不出来的文件代理任务同样会探不出来，因此按旧行为而不是排一项注定失败的任务。
- 不插队、只显示排位与「生成中」（代理服务没有逐项百分比）；失败后重开同一预览会再试一次。

## 验证

- Go：判定表逐行（含 PCM、hev1、H.264 像素格式、各扩展名、判不出）；补探一次、失败记忆与源变更后重探、卡住的探测被期限停下；大小上限（10 GiB、20%、边界、remux 与转码估算）；没有 ffmpeg；owner 记账（同一部两个宿主、不同两部与上限、乱序请求与取消、快速 A→B→A、处理中取消只停一项、手动从不被取消、窗口内手动重排）；`auto_only` 与通知。
- 前端：播放器（owner、proxy-manual、上限提示、status / alert 分离、换片与关闭撤销自己的请求）、片库页不弹 auto_only 汇总、字幕工作台与版本对比的自动请求 / 手动按钮 / 关闭撤销。
- 真机（ffmpeg 9.0.1）：`TestPreviewFormatsEndToEndWithRealFFmpeg` 合成 mov(h264)、mov(ProRes + LPCM)、mp4(HEVC hvc1) 直放，mkv(h264)、mp4(HEVC hev1) remux（产物标签 hvc1）、mov(10 位 H.264)、avi(xvid) 转码，并经代理上限走一次 proxy-manual；`TestPreviewProxyCancelStopsRealTranscode` 在真实转码中撤销请求。
