## 二、需求信息

### 2.1 需求背景

- 背景：想看片单 av 类型的自动补全当前实际不可用。`registry.go:62` 把 av 链排成
  `{fanza, javbus}`，`chain.go:76` 只在 `not_found` 时才问下一跳，而 `fanza.go:271`
  在凭证为空时返回 `credential_missing` 并当场早退（`chain_test.go:96` 钉住该行为）。
  DMM 联盟凭证要求日本地址与收款方式，对单机用户是结构性拿不到，于是零认证的
  JavBus 永远不会被询问。
- 需求目的：让 av 补全在零凭证下可用，并填满今天恒为空的字段
  （`javbus.go:177-178` 写死 `Overview: ""`、`Rating: 0`）。
- 目标用户/使用方：CineInsight 单机用户。
- 需求链接：不涉及。
- 关联原始材料：
  - 已接受的方案与取舍：[设计提案.md](./设计提案.md)（D-AVM01～D-AVM10 的决定正文在此）
  - 参考实现：`sqzw-x/amane` 的 `crawlers/`（多源择优策略，不移植代码）
- Intake package contract：
  `.loopx/intake/2026-09-13-watchlist-online-source-reduction/requirements.md`
  （canonical `AC-01`～`AC-09` / `TC-01`～`TC-08`）；
  `clarification.md`（supporting evidence，按需引用）

### 2.2 需求范围

- 本期范围：av 类型的自动补全改为 JavBus + jav321 + airav 三源并问、逐字段择优；
  FANZA 适配器与两项凭证退场；新增字段级归属存储。
- 非目标：**日文原题**（`OriginalTitle` 无落点，本期不加列）；TMDB / Bangumi 与其类型路由；javdb 与 r18dev；本地 NFO 优先；
  文件监控/重命名/归档；演员资料库；**给 `WatchlistMetadataDetail` 新增字段**。
- 决策边界：择优表为静态代码常量，不做用户可配（无需求提出）。
- 依赖方：`WatchlistService` 补全链路；设置页在线资料源分区；连接探测。
- 约束条件：所有出网必须经 `NewWatchlistMetadataHTTPClient`；沿用六个失败分类，
  不新增第七类；番号归一化不做源专有编码换算。
- 触发的辅助 skills：architecture-designer、sql-style

### 3.1 方案总述

- 概要层权威：架构、核心流程与模块划分见《[概要设计.md](./概要设计.md)》；
  方案取舍与被否方案见《[设计提案.md](./设计提案.md)》。本文件只拥有字段级契约。

  字段级可追溯（AC-04）。

  取第一个非空值；`lookupWatchlistDetail` 按类型分流，其余类型走链不变。

  复用 JavBus 适配器（仅一处年龄门 cookie 修复，其余零改动）。

## 四、详细设计

### 4.1 聚合器详细设计

#### 4.1.1 需求内容

- 入口：`AggregateWatchlistMetadataDetail(ctx, sources, kind, query)`
- 调用方：`lookupWatchlistDetail`（`watchlist_enrichment.go:550`），仅当 `kind == av`
- 前置条件：`sources` 非空；`query` 为用户手输番号（可含空白与大小写差异）
- 输出结果：`(*WatchlistMetadataDetail, map[string]string, error)`——
  详情、字段名→源名的归属表、错误

#### 4.1.2 方案设计

- **核心逻辑**：归一化番号 → 对每个源并发执行 `watchlistSourceDetail` →
  收集 `(源名, 详情, 错误)` → 按 D-AVM03 逐字段择优 → 产出详情与归属表。
- **择优规则**（D-AVM03，可复现）：每个字段按固定源顺序取**第一个非空值**；
  表中未列字段用全局兜底序 `javbus → jav321 → airav`。

  | 字段 | 落到哪一列 | 顺序 | 实际生效（本期两源） |
  |---|---|---|---|
  | `Title` | **`source_title`**（D-AVM11 新列） | airav → jav321 → javbus | jav321 → javbus |
  | `Overview` / `Genres` | `overview` / `genres` | airav → jav321 → javbus | jav321 → javbus |
  | `PosterURL` | `poster_path`（下载后） | javbus → jav321 → airav | javbus → jav321 |
  | `Year` / `Cast` | `year` / `credits` | jav321 → airav → javbus | jav321 → javbus |
  | `Directors` | `credits` | javbus → jav321 → airav | javbus → jav321 |
  | `Rating` | `rating` | jav321 → airav → javbus | jav321 → javbus |
  | `OriginalTitle` | **无落点，丢弃** | —— | —— |

  表里保留 airav 的位置：它只是**本期未能接入**（Cloudflare，见设计提案 Open Questions），
  不是被否决。哪天能接上，加一个适配器文件、在路由表加一行即可，这张表不用动。

  **表中只列真正能落库的字段。** `Title` 早先直接列在这里是错的：补全写回从不写
  `title`（见 4.1.2 下方「与 `Title` 的关系」），必须经由 D-AVM11 的新列才落得下去。

  「非空」判定：字符串 `strings.TrimSpace(v) != ""`；切片 `len(v) > 0`；`Year != 0`。
- **`SourceName` / `SourceItemID`**（D-AVM04/D-AVM05）：
  `SourceName = "aggregate"`；`SourceItemID = 归一化后的番号`。
- **与 `Title` 的关系**（D-AVM11）：条目的 `Title` 是用户手输的番号，
  补全**一律不写它**——`settleEnrichmentSuccess`（`watchlist_enrichment.go:460-473`）
  的字段表里没有 `title`，这是 D-WM06「用户输入优先」的既有实现。
  择优出来的片名写进**新列 `source_title`**，界面并列展示，两者互不覆盖。
- **并发控制**（D-AVM09）：并发度 = 源数量，共用调用方传入的 client；
  `ctx` 统一取消；单源 panic 必须被 recover 并归为 `source_error`，不得带倒其余源。
- **幂等设计**：纯函数，同样输入产生同样输出（择优表是常量）。无副作用。
- **并发持久化状态**：**不涉及**。聚合器不碰数据库；写回仍由
  `settleEnrichmentSuccess` 的既有 CAS 完成，不变量与 ABA 防护不变。
- **异常处理**（D-AVM10）：只要有一个源成功即整体成功。全部失败时按
  `proxy_unreachable > network_unreachable > credential_invalid > credential_missing
  > source_error > not_found` 选一个上报；**仅当全部为 `not_found` 才报 `not_found`**。
- **日志**：每源一行，记源名、成败、失败分类与耗时。三源并发出问题时，
  没有这行日志无法定位是哪一源慢或挂。**不得记录完整 URL**（沿用既有约定）。

#### 4.1.3 流程步骤

1. 归一化 `query` 为标准番号形态
2. 对每个源起一个 goroutine，调用 `watchlistSourceDetail(ctx, source, kind, 番号)`
3. 等全部返回（或 ctx 取消）
4. 若成功集为空 → 按 D-AVM10 选分类，返回错误
5. 否则按字段优先级表合并，同时记录每个被采纳字段的源名
6. 填 `SourceName='aggregate'`、`SourceItemID=归一化番号`
7. 返回详情与归属表

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 三源全成功 | 正常合并 | 条目补全，简介有值 | 日志三行成功 |
| 一源 500、两源正常 | 产出合并结果，缺字段由存活源补 | 补全成功 | 日志一行 `source_error` |
| 三源全 `not_found` | 报 `not_found` | 「查无此片」 | 日志三行 not_found |
| 两源 not_found + 一源 proxy 不通 | 报 `proxy_unreachable` | 「去看代理配置」 | 日志含 proxy 行 |
| 某源超时 | 归 `network_unreachable`，其余照常 | 若他源成功则无感 | 日志记耗时 |
| 番号为空 | 各适配器各自返回 `not_found`，聚合后仍 `not_found` | 「查无此片」 | —— |
| 某源 panic | recover 归 `source_error`，不影响其余源 | 若他源成功则无感 | 日志记 panic |
| `sources` 为空 | 返回 `ErrWatchlistMetadataKindUnsupported` | 「该类型尚无在线资料源」 | —— |
| 合并后 `SourceItemID` 超 64 字节 | 由既有 `enrichClaimedEntry` 判 `source_error` | 补全失败 | 沿用既有日志 |
| 补全期间用户编辑/删除条目 | **不变**：写回撞 `status+claim` 守卫被丢弃 | 用户输入优先 | 沿用既有日志 |

#### 4.1.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| movie/tv/show/anime 走链补全 | 不在本期范围 | `go test ./services -run Chain` 全绿 |
| 认领与写回的 CAS 守卫 | 聚合不引入新并发面 | `go test ./services -run Enrich` 全绿 |
| 六个失败分类码的字面量 | 存进 `enrichment_error`（size:32），是数据合同 | 现有分类测试 |
| 出网必经代理客户端 | AC-06 | TC-04 |
| `ListCandidates` / `ApplyCandidate` 单源语义 | D-AVM08 | 现有候选测试 |

### 4.2 jav321 适配器详细设计

#### 4.2.1 需求内容

- 入口：`NewJav321WatchlistMetadataSource(client)`，实现 `WatchlistMetadataSource`
- 前置条件：无凭证
- 输出：`WatchlistMetadataCandidate` / `WatchlistMetadataDetail`

#### 4.2.2 方案设计

- **核心逻辑**：`GET https://www.jav321.com/video/{归一化番号}`，单跳直达，
  搜索与详情打同一页面（与 `javbus.go:109` 同理：番号是主键，命中即唯一一条）。
- **字段抽取**：标题、番号、演员、厂商、发行日期、时长、标签、封面、简介。
  其中**时长与厂商当前结构装不下，直接丢弃**（2.2 非目标）。
- **not_found 判定**：只有 HTTP 404 才是「没有这个番号」。
  **选择器失效不得报 `not_found`**——沿用 `javbus.go:24` 的既有约定，
  否则会把用户支去核对番号，而真正该做的是修适配器。
- **异常处理**：非 2xx 走 `classifyWatchlistMetadataHTTPStatus`；
  传输错误走 `classifyWatchlistMetadataTransportError`。
- **日志**：只记路径与耗时，不记完整 URL。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 感知 |
|---|---|---|
| HTTP 404 | `not_found` | 「查无此片」 |
| 200 但页面结构变了（关键选择器全失效） | `source_error`，**不是** not_found | 「源返回了无法解析的内容」 |
| 200 且部分字段缺失 | 缺的留零值，不猜 | 该字段由他源补 |
| 番号含空白/小写 | 由聚合器统一归一化后传入 | 无感 |

#### 4.2.5 不变行为

| 行为 | 原因 | 验证 |
|---|---|---|
| 适配器不碰数据库、不下海报 | `watchlist_metadata_source.go` 开头声明的边界 | 代码审查 + 单测用桩替身 |
| 出网只用注入的 client | 代理必须生效 | TC-04 |

### 4.3 airav 适配器详细设计

结构同 4.2，差异如下：

- **两跳**：`GET https://airav.io/search?keyword={番号}` → 取首个结果的详情页 URL → 取详情
- **中文字段**：按 `演員` / `廠商` / `日期` / `時長` 等中文标签定位，
  产出**中文标题与简介**——这是引入本源的主要理由
- **not_found 判定**：搜索结果为空即 `not_found`；详情页 404 亦然。
  同样地，**选择器失效归 `source_error`**
- **边界补充**：搜索命中多条时**取第一条**，不重排（与 `watchlistSourceDetail`
  「源给的就是匹配度顺序」一致）

## 五、存储类设计

### 5.1 库表设计

#### 5.1.2 表结构

| 表名 | 用途 | 变化 |
|---|---|---|
| `watchlist_entries` | 想看条目 | **加两列** `source_fields`、`source_title` |
| `settings` | 全局设置 | **无 DDL 变化**（两个 FANZA 列保留，仅程序不再读写） |

`watchlist_entries` 字段明细（仅新增列）：

| 字段 | 类型 | 必填 | 默认值 | 含义 | 来源/取值逻辑 | 备注 |
|---|---|---|---|---|---|---|
| `source_fields` | `text` | 是 | `''` | 字段级归属：被采纳字段 → 源名。**键名以本表的列名为准**（`source_title` / `overview` / `genres` / `year` / `credits` / `rating` / `poster_path`），不是适配器结构体的字段名 | 仅 av 聚合补全写入；JSON 对象如 `{"source_title":"airav","poster_path":"javbus"}` | 非 av 与手动重选恒为空串 |
| `source_title` | `text` | 是 | `''` | 源站片名（中文优先），**只读补充**，不覆盖用户手输的 `Title` | **仅 kind==av** 写入：聚合补全按择优表写；手动重选写所选源给的片名 | 其余类型与取不到时恒为空串，界面只显示 `Title` |

gorm 标签：`gorm:"type:text;not null;default:''" json:"source_fields"`。
字符串列的 `default:''` 不触犯 2026-09-02 的 `gorm default` 禁令——
该禁令管的是默认 true 的布尔列与默认非零的数值列
（`models/watchlist.go:33` 已有同类说明）。

### 5.2 数据迁移/初始化

- **DDL**：无需手写。`database.go:336` 的 `db.AutoMigrate(models.AllModels()...)`
  会自动补 `source_fields` 与 `source_title` 两列；`not null default ''` 让存量行得到空串。
- **DML**：无。
- **数据回填**：**不做**（D-AVM06）。存量 av 条目的 `source_name` 保留历史值
  `fanza` / `javbus`，`source_fields` 留空串。回填意味着重新出网补全所有历史条目，
  既无需求也有风险。
- **老数据兼容**：存量已补全内容（标题/年份/简介/海报）全部不动（AC-08 / TC-06）。
- **删列决策**（D-AVM07）：`settings` 的 `fanza_api_id` / `fanza_affiliate_id`
  **不删**。`AutoMigrate` 本就不删列，删列需要单独写迁移函数，且会破坏降级
  （旧版本二进制读不到列）。留列的成本是两个静置的空列。
- **可重入**：`AutoMigrate` 重复执行安全。
- **双后端**：SQLite 与 PostgreSQL 均由 `AutoMigrate` 处理，无方言分支。

## 八、系统发布

### 8.2 降级方案

- 触发条件：新 av 链路出网大面积失败（站点改版或被封）
- 降级行为：**无自动降级**。沿用仓库既有原则：不加任何需求未命名的
  fallback / 降级模式，失败就如实报分类码
- 用户影响：av 条目补全失败并显示具体分类，其余类型不受影响
- 恢复方式：修适配器并发版

### 8.4 回滚方案

- 回滚条件：本次变更导致 av 或其他类型补全回归
- 回滚步骤：回退二进制即可
- **数据回滚：不需要**。`source_fields` 与 `source_title` 都是加性列，旧版本忽略；
  `settings` 两个 FANZA 列从未删除，旧版本照常读写
- 风险：回滚后用新版本补全过的 av 条目，其 `source_name='aggregate'`
  在旧前端会显示成裸字符串 `aggregate`（不崩，仅显示不美观）

## 九、系统监控与维护

### 9.1 监控与告警

单机应用，无告警渠道。以日志为准：

- 每源一行：源名、成败、失败分类、耗时。**三源并发时缺这行日志无法定位慢源**
- 合并结果一行：条目 ID、各字段采纳来源
- 一律**不记完整 URL**（沿用既有约定）

### 9.3 可靠性与兜底

- **抓取脆弱性**：jav321 与 airav 都是 HTML 抓取，站点改版即失效。
  这是接受的维护成本，与既有 JavBus 适配器同类。
  缓解手段只有一条且是硬约定：**选择器失效必须归 `source_error`，不得归 `not_found`**
  ——否则用户会去核对番号，而真正该做的是修适配器
- **字段兜底**：任一字段取不到就留零值，不猜、不合成
- **新老数据兼容**：见 5.2
