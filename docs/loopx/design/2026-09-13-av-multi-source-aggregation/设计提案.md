# AV 补全改为三源并问、逐字段择优；FANZA 退场，JavBus 复用

Author(s): CineInsight
Last updated: 2026-09-13（V2：新增 D-AVM11 源站片名列）
Status: Accepted（2026-09-13 实施期修订：airav 不接入，见 Open Questions）
Discussion: 不涉及
Source requirements: `.loopx/intake/2026-09-13-watchlist-online-source-reduction/requirements.md`
Support lenses: architecture-designer, sql-style

## Abstract / 摘要

想看片单 **av** 类型的自动补全，从「FANZA 首选 → JavBus 兜底、整条记录归属单一源」
改为「**JavBus + jav321 + airav 三源并问，逐字段按静态优先级表择优**」。FANZA 适配器
与两项凭证整体退场；JavBus 适配器复用，但要修掉它的年龄门缺陷。

最重要的承诺：**改完之后 AV 补全不需要任何凭证**，三个源都是零认证；并且今天恒为空的
「简介」字段会有值。

作用范围只有 av。TMDB（movie/tv/show）与 Bangumi（anime）一行不改；
走链策略 `chain.go` 保留给它们，不删。

## Background / 背景与动机

### 今天 AV 补全实际上是死的

`registry.go:62` 把 av 链排成 `{fanza, javbus}`，`chain.go:76` 只在 `not_found`
时才问下一跳，而 `fanza.go:271` 在凭证为空时返回的是 `credential_missing` 并且
**不发请求**。`chain_test.go:96` 用 `{CredentialMissing, false}` 钉死了这个行为。

后果具体而确定：**用户没有 DMM 凭证，每一次 av 补全都停在第一跳，零认证、可用的
JavBus 一次都不会被询问。**

而 DMM 凭证的获取门槛是日本地址与收款方式（联盟注册要求），对本项目的单机用户不是
「暂时没配」，是**结构性拿不到**。

### 即便 JavBus 可达，单源也填不满

`javbus.go:177-178` 写死 `Overview: ""`、`Rating: 0`——JavBus 的详情页没有简介。
所以哪怕修好链路顺序，av 条目的简介也永远是空的。

jav321 与 airav 都提供 plot/简介，airav 还提供**中文**标题与简介
（其解析器按 `演員` / `廠商` / `日期` / `時長` 取字段）。而本项目界面是中文的。

这就是「逐字段择优」的直接理由：不是为了架构好看，是因为**没有任何单一源能填满这张表**。

### 参考来源

`sqzw-x/amane` 的 `crawlers/` 采用「多源择优：聚合多个数据源的元数据，逐字段择优」，
`site_roles.py` 以「列表顺序即优先级」表达。本提案借鉴该策略，不移植其代码、
不移植其文件监控工作流（本项目的匹配键由用户手输番号提供，不需要扫盘）。

## Goals And Non-Goals / 目标与非目标

**目标**

1. av 自动补全在零凭证下可用（AC-01）
2. 三源并问，单源失败不阻断其余（AC-02）
3. 逐字段择优，缺字段由他源补齐（AC-03）
4. 补全结果可追溯到字段级来源（AC-04）
5. FANZA 从设置页、探测表、配置载荷中消失（AC-07）
6. 存量 av 条目不丢数据（AC-08）

**非目标**

- 不改 TMDB / Bangumi 与它们的类型路由
- 不做 javdb（需 cookies，与「摆脱凭证」的动机冲突）与 r18dev（需自备离线 PG dump）
- 不做本地 NFO 优先、不做文件监控/重命名/归档
- 不做演员资料库
- **不给 `WatchlistMetadataDetail` 新增字段**（jav321/airav 提供的 runtime、studio
  当前结构装不下，本期直接丢弃；新增字段会牵动 TMDB/Bangumi 两条不在范围内的链路）

## Proposal / 设计方案

### 最小版本：一个只作用于 av 的聚合器

新增 `services/watchlist_metadata_aggregate.go`，提供一个函数：

```go
func AggregateWatchlistMetadataDetail(
    ctx context.Context,
    sources []WatchlistMetadataSource,
    kind WatchlistMetadataKind,
    query string,
) (*WatchlistMetadataDetail, map[string]string, error)
```

它并发地对每个源执行「搜索 → 取首个候选 → 取详情」（与现有
`watchlistSourceDetail` 同一套路，直接复用该函数），然后按字段优先级表合并。
第二个返回值是**字段名 → 源名**的归属表。

`lookupWatchlistDetail`（`watchlist_enrichment.go:550`）按类型分流：

- av → 走聚合器
- 其余 → 保持现在的 `walkWatchlistMetadataChain` 一字不改

**D-AVM01**：聚合与走链**并存**，不是取代。`chain.go` 仍是 movie/tv/show/anime 的
唯一策略；av 是唯一走聚合的类型。删掉 chain.go 会波及四个不在范围内的类型。

### 择优规则：静态按字段优先级表 + 非空优先

**D-AVM03**。规则只有两条，可复现（TC-07）：

1. 每个字段有一个**固定的源顺序**，按该顺序取**第一个非空值**
2. 表里没列到的字段，用全局兜底顺序 `javbus → jav321 → airav`

| 字段 | 落到哪一列 | 优先级顺序 | 理由 |
|---|---|---|---|
| `Title` | **新列 `source_title`**（D-AVM11） | airav → jav321 → javbus | 中文界面优先中文片名 |
| `Overview` | `overview` | airav → jav321 → javbus | JavBus 恒为空；airav 给中文简介 |
| `Genres` | `genres` | airav → jav321 → javbus | 同上，中文标签 |
| `PosterURL` | `poster_path`（下载后） | javbus → jav321 → airav | JavBus 封面已验证可用 |
| `Year` | `year` | jav321 → airav → javbus | 三源都给发行日期，取解析最稳的 |
| `Cast` / `Directors` | `credits` | jav321 → airav → javbus（Cast）；javbus 优先（Directors） | 三源都给演员；仅 JavBus 明确解析导演 |
| `Rating` | `rating` | jav321 → airav → javbus | jav321 的详情页有 `平均評価`（2026-09-13 真实页面侦察确认） |
| `OriginalTitle` | **无落点，本期丢弃** | —— | 本仓库没有存日文原题的列，本期不为它加列 |

**这张表只列真正能落库的字段。** 早先版本把 `Title` 与 `OriginalTitle` 直接列进来是错的：
补全写回（`watchlist_enrichment.go:460-473`）从不写 `title`，`WatchlistEntry` 也没有
`OriginalTitle` 列，那两行当时决定的是观察不到的事。

「非空」的判定：字符串取 `strings.TrimSpace(v) != ""`，切片取 `len(v) > 0`，
`Year` 取 `!= 0`。这与现有各适配器「取不到就留零值、不猜」的约定一致
（`tmdb.go` / `javbus.go` 均如此）。

**边界**：该表是**静态代码常量**，不做成用户可配。用户可配意味着要设计配置 UI、
校验、迁移与「配错了怎么办」，而本期没有任何需求提出过这件事。

### 源站片名另存一列，不覆盖用户手输的番号

**D-AVM11**。av 条目的 `Title` 是用户手输的番号（`ABC-123`），补全**从不写它**——
这是既有裁决 D-WM06「用户输入永远优先」的体现，全仓唯一写 watchlist 标题的地方是
`watchlist_service.go:152` 的用户手动改名。

于是 airav 抓到的中文片名原本无处安放。我们**新增一列 `source_title`** 存源站片名，
补全写入，用户手输的 `Title` 一字不动。界面在 `source_title` 非空且不等于 `Title` 时
并列展示（`ABC-123 · 中文片名`）。

这样 D-WM06 不受任何改动：用户输入仍然优先，只是多了一个只读的补充展示位。

**边界一**：只加这一列。日文原题（`OriginalTitle`）同样没有落点，本期**不**为它加列。

**边界二（承重）**：`settleEnrichmentSuccess` 与 `ApplyCandidate` 这两条写入路径
**全类型共用、没有 kind 分支**。因此新列必须**显式判 `kind==av` 才写**——
否则一条 movie 条目补全后会从「沙丘」变成「沙丘 · Dune」，那是红线禁止的
可观察变化，而且既有 movie 测试抓不到（新列不在任何断言里）。`source_fields` 同此边界。

### 字段级归属：SourceName 不变形，另开一列

**D-AVM04**。`WatchlistEntry.SourceName` 是 `size:16` 单值列。三条路：

- 塞逗号分隔的多源名 → 装不下，且破坏「一个源名」的既有语义
- 只记主源 → 满足不了 AC-04
- **保持单值，新开一列记字段级归属** ← 选这条

具体：

- `SourceName` 写入固定字面量 `aggregate`（9 字节，`size:16` 装得下），
  表示「本条来自多源合并，不归属任何单一源」
- 新增列 `WatchlistEntry.SourceFields string`（`type:text;not null;default:''`），
  存 JSON 对象 `{"source_title":"airav","overview":"airav","poster_path":"javbus",...}`，
  只记**实际被采纳**的字段
- `SourceItemID` 写入**归一化后的番号**（见 D-AVM05）

这样做的前提已核实：`SourceName` 今天**没有任何路由作用**。`ApplyCandidate`
（`watchlist_service.go:321`）是把 `sourceItemID` 丢给 `DetailWatchlistMetadataChain`
挨个源试，不看 `SourceName`；`SourceName` 的唯一消费者是前端展示
（`WatchlistPage.vue:139` 的 `SOURCE_LABELS`）与进度事件。

前端需加一条标签 `aggregate: '多源合并'`。`WatchlistPage.vue:365` 的兜底是
`SOURCE_LABELS[x] || x || '资料源'`，不加标签也不会崩，只是显示成裸字符串。

### 番号归一化：只做大小写与分隔符，不做源专有编码换算

**D-AVM05**。`fanza.go:88` 有一条既有裁决：**不做番号到 content_id 的换算**，
理由是「没有公开文档可依，凭猜写一个只会在用户看不见的地方悄悄查错片」。

FANZA 退场后，这条裁决针对的对象（`abc00123` 这种补零编码）随之消失。
JavBus、jav321、airav 三家用的都是同一种展示形态 `ABC-123`。

因此本期口径：**归一化 = `TrimSpace` + 转大写 + 把全角/下划线/空格分隔符统一成半角连字符**。
明确**不做**补零、去零、厂牌前缀补全这类源专有编码换算。

这是**收窄**既有裁决的适用范围，不是推翻它：凭猜换算依然禁止。

### 失败分类的聚合口径

**D-AVM10**。三源全部失败时，取**最值得用户处理**的那一类上报，顺序为：

```
proxy_unreachable > network_unreachable > credential_invalid
  > credential_missing > source_error > not_found
```

只有**三源全部 `not_found`** 时才上报 `not_found`（AC-05）。

理由与 `chain.go` 现有注释同源：把配置或网络问题伪装成「查无此片」，会让用户
照着「换个番号试试」排查，而真正该做的是去修代理。

只要**有一个源成功**，整体就是成功——哪怕另外两个全炸（AC-02）。

### 并发边界

**D-AVM09**。三个请求并发发出，共用 `sources.registry` 里那个**已经建好的**
`http.Client`（`registry.go:30` 的既有约定：建一次共用，自带连接池）。

- 并发度固定为源数量（3），不引入 worker pool
- 单次请求超时沿用 `watchlistEnrichRequestTimeout`，不改
- 整体用 `context` 统一取消；任一源 panic 不得带倒其余两个

出网并发是**新增的**，但数据库并发面**完全没有变化**——见下。

## Architecture Fit / 架构适配

| Concern | Evidence | Decision | Cost or boundary | D anchor |
|---|---|---|---|---|
| 单源「搜索+详情」逻辑 | `watchlist_enrichment.go:565` `watchlistSourceDetail` | **reuse** | 聚合器对每个源调用它，语义（同源搜索取首个候选再取详情）完全匹配 | D-AVM01 |
| JavBus 适配器 | `watchlist_metadata_javbus.go` | **reuse + 一处修复** | 零凭证、番号即路径；但缺年龄门 cookie 导致每次查询都落 source_error（2026-09-13 真实请求确认并已修复） | D-AVM02 |
| 出网客户端 | `watchlist_metadata_config.go:97` `NewWatchlistMetadataHTTPClient` | **reuse** | 新适配器一律从 registry 拿 client，不自建；否则代理只对部分源生效（AC-06） | D-AVM09 |
| 失败分类 | `watchlist_metadata_source.go` 六分类 | **reuse**，不扩张 | 聚合只**选**一个已有分类上报，不新增第七类 | D-AVM10 |
| 走链策略 | `watchlist_metadata_chain.go` | **保留**，不复用于 av | av 改走聚合；chain 仍是其余四类型的唯一策略。并存的代价是两套策略共存，边界由 `lookupWatchlistDetail` 一处 switch 承担 | D-AVM01 |
| 字段级归属存储 | `models/watchlist.go:57` `SourceName`（size:16） | **new column** | 最接近的候选是 `SourceName` 本身，但它是单值且语义已定；扩成多值会破坏前端展示与既有语义 | D-AVM04 |
| 并发持久化状态 | `watchlist_enrichment.go:368/409` claim + 写回守卫 | **unchanged** | 聚合全部发生在写回**之前**，写回仍是同一条带 `status + claim` 守卫的单条 UPDATE | D-AVM08 |

**隔离与故障半径**

| 模块 | 所有者 | 依赖方向 | 共享状态 | 故障半径 |
|---|---|---|---|---|
| 聚合器 `watchlist_metadata_aggregate.go` | services | 被 `watchlist_enrichment.go` 调用；只调适配器接口 | 无（纯函数，不碰 DB） | 仅 av 补全一条；抛错落到既有 `settleEnrichmentFailure` |
| 三个 av 适配器 | services | 只依赖注入的 `*http.Client` | 共用 client 的连接池 | 单源失败被聚合器吞掉并记录，不外溢 |

**数据库并发**：本方案**不引入任何新的并发持久化状态**。认领
（`claimEnrichment` 的条件 UPDATE）与写回（`writeBackEnrichment` 的
`status + claim` 双守卫 CAS）一字不改；新增的 `source_fields` 列与
`source_name` 在同一条 UPDATE 里写。不变量、ABA 防护、回滚边界全部沿用，
无新增锁、无 `SELECT ... FOR UPDATE`、无重试。

## Boundary Scenarios / 边界场景

| 类别 | 场景 | 本方案的处理 |
|---|---|---|
| 部分失败 | 三源中一个 500、两个正常 | **产出合并结果**，缺的字段由存活源补齐（AC-02/TC-02） |
| 部分失败 | 三源全 `not_found` | 上报 `not_found`（AC-05/TC-03） |
| 部分失败 | 两源 `not_found`、一源 `proxy_unreachable` | 上报 `proxy_unreachable`——用户要修的是代理，不是番号（D-AVM10） |
| 依赖超时 | 某源超时 | 归 `network_unreachable`，其余两源照常；整体仍可成功 |
| 非法输入 | 番号为空 | 沿用现有行为：适配器各自返回 `not_found`，聚合后仍是 `not_found` |
| 并发 | 补全期间用户编辑/删除条目 | **不变**：写回撞上 `status + claim` 守卫被丢弃，用户输入优先（D-WM06） |
| 并发 | 补全期间用户手动重选候选 → manual | **不变**：同上，守卫丢弃后台结果 |
| 遗留数据 | 存量 `source_name='fanza'` 的已补全条目 | **不动**（D-AVM06）。`source_fields` 为空串，前端按空处理；`SOURCE_LABELS` 保留 `fanza` 键以便正常显示历史值 |
| 遗留数据 | 存量 `source_name='javbus'` 的条目 | 同上，不动 |
| 迁移重叠 | 新列 `source_fields` 加列时机 | `AutoMigrate` 加列，`not null default ''`，存量行自动得空串；可重复执行 |
| 回滚/降级 | 回退到旧版本二进制 | FANZA 两列仍在表上（未删），旧版本读写照常；`source_fields` 列被旧版本忽略。**降级不丢数据** |
| 权限 | 不涉及 | 单机应用，无多租户/鉴权面 |
| 必须不变 | movie/tv/show/anime 的补全行为 | 完全不经过聚合器；`chain.go` 与 `tmdb.go`、`bangumi.go` 零改动（`javbus.go` 另有一处年龄门修复，它只服务 av） |
| 必须不变 | 手动重选候选（`ListCandidates` / `ApplyCandidate`） | **仍是单源语义**（D-AVM08）：列出的每条候选归属一个具体源，应用后 `SourceName` 写该源名、`source_fields` 清空。聚合只作用于自动补全 |
| 必须不变 | 资料源出网代理 | 三源全部经 `NewWatchlistMetadataHTTPClient`；无任何源绕过（AC-06/TC-04） |

## Rationale / 理由与取舍

| Alternative | Why Not |
|---|---|
| 只修链路顺序，让 JavBus 可达，不做聚合 | 修得了「查不到」，修不了「简介恒为空」——`javbus.go:177` 写死 `Overview: ""`。用户的诉求是「能力不足」，这条只解决一半 |
| 把 av 也留在 `chain.go`，只是把 FANZA 摘掉 | 走链是「第一个成功就停」，拿不到跨源合并。要合并就必须改走法，不如显式分流 |
| 用 `chain.go` 改造成「既能兜底又能合并」 | 会让四个不在范围内的类型跟着变。走链策略的注释明确说明其兜底语义是 D-WM07 的合同，不该为 av 一个类型改写 |
| `SourceName` 存逗号分隔多源 | `size:16` 装不下三个源名；且破坏 `SOURCE_LABELS` 查表与「一个源名」的既有语义 |
| 不记字段级归属，只记主源 | 违反 AC-04。且择优表一旦调整，用户无法判断某个字段为什么变了 |
| 择优用「质量启发式」（取最长简介、取分辨率最高的图） | 不可复现，违反 TC-07；且「更长」不等于「更好」 |
| 择优表做成用户可配 | 本期无任何需求提出；配置面要带 UI、校验、迁移与错配兜底，成本远超收益 |
| 删掉 FANZA 的两个 Settings 列 | `AutoMigrate` 不删列，删列需要单独写迁移；而删了会破坏降级（旧版本读不到列）。留列零成本 |
| 顺带接入 javdb | 需要 cookies 与会话维护，与本次「摆脱凭证配置」的核心动机直接冲突 |

## Operational And Security Impact / 运行与安全影响

- **凭证面缩小**：FANZA 两项凭证退场后，av 链不再持有任何密钥。三个源都是零认证，
  `redactWatchlistMetadataSecret` 对 av 链不再有可抹的对象（TMDB/Bangumi 仍需要，保留）。
- **出网请求量**：单条 av 补全从「最多 2 源串行」变为「3 源并发」，
  请求数上升，但都在一次补全的既有超时窗口内，且共用连接池。
- **可诊断性**：`source_fields` 让「这个简介哪来的」可直接回答。日志需记录
  每源的成败与耗时，否则三源并发出问题时无法定位是哪一源慢。
- **年龄验证门（2026-09-13 已确认并修复）**：`javbus.com` 对不带 `dv=1` 的请求回 302
  指向 `/doc/driver-verify`，Go 的 client 跟过去拿回一个 200 验证页，其中没有 `<h3>`
  也没有 `bigImage`，两条承重正则同时失效 → `source_error`。**修复前 JavBus 对每一次
  查询都返回 source_error，从未真正工作过。** 逐个试过 `age=verified` / `existmag=all`
  / `existmag=mag` 均无效，只有 `dv=1` 有效。已加 cookie 并用 `SSIS-001` 做真实请求
  端到端验证：番号、标题、年份、导演、类型、演员、封面全部落位，`Overview` 与 `Rating`
  确认为空——后者正好实证了「单源填不满、需要多源」这个立项理由。
- **抓取脆弱性**：jav321 与 airav 都是 HTML 抓取，站点改版即失效。这是接受的
  维护成本——与既有 JavBus 适配器同类（`javbus.go:24` 已记录该风险与「选择器
  失效不得报 not_found」的处理约定，新适配器沿用）。

## Implementation And Transition / 实现与过渡

顺序只在两处影响风险，其余自由：

1. **先**加聚合器与 `source_fields` 列，让 av 走「JavBus 单源 + 聚合器」
   —— 此时行为等价于今天的 JavBus，但链路已切换，可先验证不回退
2. **再**加 jav321、airav 两个适配器
3. **最后**摘 FANZA（适配器、凭证、设置页、探测表、白名单）

先摘 FANZA 再建聚合会留下一段 av 完全没有源的窗口。

## Open Questions / 待决问题

**实施期变更（2026-09-13）**：**airav 未能接入**。它全站（含 API 路径）返回 Cloudflare
的「Just a moment...」JS 挑战，普通 HTTP 客户端过不去——与本提案当初排除 javdb 的
理由同类，且更重（要执行 JS，不是一个 cookie 的事）。

候选替代经实测均不达标：`javlibrary` 同样是 CF 挑战；`freejavbt` 可达，但抽样 8 个番号
只有 3 个有中文标题，其中 SSIS-001 一条给的是**另一部片**（标题写三上悠亞、演员却是葵司）。
错误率 1/3，且失败模式很糟——用户看到一个像模像样的中文片名，无从判断它是错的，
比显示日文标题更差。故不采用。

**后果**：本期实际源清单为 **JavBus + jav321**。「中文片名与中文简介」这个立项理由
**未能达成**；中文只落在标签上（JavBus 的类别本就是中文）。但**简介从「恒为空」变成有值**
这一条达成了，逐字段择优的机制也完整落地，接第三个源时只需加一个适配器文件。

原列的两项已由用户于 2026-09-13 接受：

- D-AVM04 的 `SourceName = "aggregate"` 字面量 —— **已接受**
- D-AVM03 的 `Title` 优先中文（airav） —— **已接受**（改日文原题为主标题只需改一行常量）

## Detailed Design Handoff / 详细设计交接

应当现在写详细设计。必须作为固定约束的决定：

- D-AVM01 聚合与走链并存，av 是唯一走聚合的类型
- D-AVM02 源清单 = JavBus（复用 + 一处年龄门 cookie 修复）+ jav321 + airav，全零凭证
- D-AVM03 静态按字段优先级表 + 非空优先
- D-AVM04 `SourceName='aggregate'` + 新列 `source_fields`
- D-AVM05 番号归一化只做大小写与分隔符
- D-AVM08 手动重选候选保持单源语义
- D-AVM09 三源并发共用既有 client，不自建
- D-AVM10 失败分类按「最值得处理」排序上报
- D-AVM11 源站片名另存 `source_title` 列，不覆盖用户手输 `Title`；不存日文原题
