## 2 后端接口与数据

<a id="collection-progress"></a>
### 2.1 作品集进度（D-P2-02）

```go
// app_media_details.go
func (a *App) ListCollectionProgress(req services.CollectionProgressRequest) ([]services.CollectionProgress, error)

type CollectionProgressRequest struct {
    CollectionIDs []uint `json:"collection_ids"` // 非空：只算这些（作品集页、封面墙）；最多 200
    ContinueOnly  bool   `json:"continue_only"`  // true：「追到哪了」候选（见下），忽略 CollectionIDs
    Limit         int    `json:"limit"`          // ContinueOnly 时生效，默认 12，最大 50
}

type CollectionProgress struct {
    CollectionID    uint                    `json:"collection_id"`
    Name            string                  `json:"name"`
    HasCover        bool                    `json:"has_cover"`
    TotalWorks      int                     `json:"total_works"`
    WatchedWorks    int                     `json:"watched_works"`
    InProgressWorks int                     `json:"in_progress_works"`
    Complete        bool                    `json:"complete"`
    Next            *CollectionProgressNext `json:"next,omitempty"`
    LastActivityAt  *time.Time              `json:"last_activity_at" ts_type:"string"`
}

type CollectionProgressNext struct {
    VideoID              uint    `json:"video_id"` // 该部的代表视频（版本组取组代表）
    Title                string  `json:"title"`
    WorkIndex            int     `json:"work_index"` // 第几部，从 1 起
    Resume               bool    `json:"resume"`     // 有续播位置
    WatchPositionSeconds float64 `json:"watch_position_seconds"`
    Duration             float64 `json:"duration"`
}
```

- **计算**（`services/collection_progress.go` ✚，纯 Go 汇总，一次查询取成员）：
  - 查询：`collection_videos` 联 `videos`（活跃、未失效）左联 `video_version_members`，按 `(collection_id, position, video_id)` 排序。
  - 「一部」：同一 `group_id` 的成员合并，取它们中最小的 `position` 定位置；代表视频取该组代表（与 `CollapseVersions` 同一规则）。
  - 看过：组内任一成员 `is_watched`。在看：没看过且任一成员 `watch_position_seconds > 0`。
  - 活动时间：组内成员 `max(last_played_at, watch_progress_updated_at, watched_at)`。
  - 下一部：按概要设计 D-P2-02 的顺序选；`Resume` 为在看那一部。
- **`ContinueOnly` 候选**：至少一个成员有活动时间的作品集；算完后过滤「总部数 ≥ 2、看过或在看 ≥ 1、未完成」，按 `LastActivityAt` 倒序取 `Limit`。
- **逐部明细**（2026-10-13 增补，作品集页用）：请求加 `include_works`（只能配 `collection_ids`，最多 20 个），每个作品集多给 `works []{work_index, video_ids（该部在作品集里的活跃未失效成员，代表在前）, representative_video_id, state: watched|in_progress|unwatched, resume_video_id（在看时有断点的成员，否则 0）}` 与 `offline_video_ids`（失效成员，不计入任何一部）。
- **失败**：数据库不可用返回错误（前端该区块显示错误、不影响其他区块）；作品集 ID 不存在的跳过。
- **性能**：成员总数在几千量级，单次查询 + 内存汇总；不加缓存。

<a id="watchlist-links"></a>
### 2.2 想看条目与片库的关联（D-P2-03）

**数据**（2026-10-13 评审修订：关联只住一张表，见下方「修订记录」）：

```go
// models/watchlist.go ✚
// WatchlistVideoLink：想看条目与片库视频关联的唯一归处，按条目记、与条目来源无关。
type WatchlistVideoLink struct {
    ID               uint   `gorm:"primarykey"`
    WatchlistEntryID uint   `gorm:"not null;uniqueIndex:idx_watchlist_video_links_pair,priority:1"`
    VideoID          uint   `gorm:"not null;uniqueIndex:idx_watchlist_video_links_pair,priority:2;index"`
    Origin           string `gorm:"size:16;not null"` // auto | manual | dismissed；不设 gorm default，创建时显式赋值
    Entry            WatchlistEntry `gorm:"foreignKey:WatchlistEntryID;constraint:OnDelete:CASCADE;" json:"-"`
    Video            Video          `gorm:"constraint:OnDelete:CASCADE;" json:"-"`
    CreatedAt, UpdatedAt time.Time // 关联时间取 UpdatedAt：变成 manual 时刷新
}
```

- **一处一份**：想看的关联只存在 `watchlist_video_links`（`auto` / `manual` / `dismissed`），条目来源在豆瓣与其他之间切换（补全重试、改选候选、榜单复用、改名清来源）关联都不丢。`movie_video_links` 仍归榜单（榜单的已看双向同步只看它），表结构不变。
- **读取**一个条目的关联 = 它的 `auto` / `manual` 行 ∪（条目此刻是豆瓣来源 `source_name = douban` 且 `source_item_id` 非空时）`movie_video_links` 里它那个豆瓣 ID 的行（读作 `manual`），再减去**按作品**解除过的：同一版本组任一成员对这个条目有 `dismissed`，整部作品的关联都不算。只算活跃视频。
- 迁移：`WatchlistVideoLink` 经 `AllModels` 自动迁移（拓扑序：在 `WatchlistEntry`、`Video` 之后），`TestModelSchemaGolden` 更新。不回填。

**接口**：

```go
func (a *App) ListWatchlistLibraryState(entryIDs []uint) (map[uint]services.WatchlistLibraryState, error) // 最多 200
func (a *App) LinkWatchlistEntryVideo(entryID, videoID uint) error   // 手动确认：写 manual（关联时间为此刻），清掉这部作品的 dismissed；豆瓣条目另调 LinkMovieToVideo
func (a *App) UnlinkWatchlistEntryVideo(entryID, videoID uint) error // 解除：这一对写 dismissed（没有关联也记）；豆瓣条目另调 UnlinkMovieVideo
func (a *App) ListWatchlistInLibrary(limit int) ([]services.WatchlistInLibraryItem, error) // 首页：已关联且这部作品没看过，按关联时间倒序，默认 12、最大 50

type WatchlistLibraryState struct {
    Linked    []WatchlistLinkedVideo `json:"linked"`    // {video_id, title, origin: auto|manual, is_watched}
    Dismissed []uint                 `json:"dismissed"` // 解除过的视频 ID（含解除过的作品的全部版本），升序
}
```

- 「片库中可能已有」的建议继续用 `SuggestLibraryMatchesBatch`（按片名 + 年份查，与来源无关），前端用 `linked` 与 `dismissed` 过滤掉已关联与已解除的。
- `ListWatchlistInLibrary`：每个条目取最近一次关联的未失效视频，映射到所在版本组的代表；这部作品任一（活跃、未失效）版本看过就不列。
- 榜单页 `UnlinkMovieVideo` 在同一事务里给此刻以这个豆瓣 ID 为来源的每个想看条目记这一对 `dismissed`（作品级生效），想看的自动匹配不会再连回来；`LinkMovieToVideo` 对称地清掉这些条目对这部作品的 `dismissed`。
- 豆瓣条目在片单页关联 / 解除：先写片单一侧，再同步榜单；榜单服务不可用或同步失败时报「已在想看中…，但榜单没同步；稍后重试即可」，两步都幂等。
- 条目改名（片名变了）：删掉它的 `auto` 关联（`manual` 与 `dismissed` 留着），再按新片名做单条匹配。

**自动匹配**（`services/watchlist_library_match.go` ✚）：

- 输入：没有任何已关联（按上面的读取规则）、片名非空、年份 > 0 的条目。
- 规则：`normalizeLibraryTitle(条目片名)` 与视频 `display_title` / `original_title` / 去扩展名 `name` 的规范化结果**完全相等**（不接受前缀），且 `videos.year` 等于条目年份；命中的视频按版本组合并后**恰好一部**、且这部作品没有被这个条目解除过，才关联到代表视频。**只写** `watchlist_video_links(origin=auto)`，从不写 `movie_video_links`，因此不牵动榜单的已看同步（不会因为看完一部自动关联的视频而删掉榜单建的想看条目、改掉榜单标记）。
- 时机：
  - 条目新增、改名、在线补全成功（含用户选定候选）后（只算这一条，同步执行，不等后台全量轮）；
  - 扫描同步完成且新增了视频后（全部未关联条目，后台、空闲门外——与想看条数成正比）；
  - 视频的片名 / 原始片名 / 文件名 / 年份变了（元数据编辑、NFO 应用、批量改年份、重命名与重新定位）、回收站恢复后：防抖约 5 秒的后台全量轮；
  - 应用启动后一次（后台，数据库就绪后）。
- 并发：后台全量轮同一时刻只跑一轮（进行中再触发就记一次「再跑」）；自动写入用 (条目, 视频) 唯一键 `ON CONFLICT DO NOTHING`，已有的 `dismissed` / `manual` 行总是赢，所以手动关联 / 解除不用等匹配轮，与匹配轮交错时解除也不会被覆盖。

**修订记录**：2026-10-13 初稿让豆瓣条目的关联（含自动匹配）写 `movie_video_links` 并给它加 `origin` 列。评审发现三处问题：自动关联进了 `movie_video_links` 会驱动榜单的已看双向同步（看完一部自动关联的视频就删掉了榜单建的想看条目、把榜单标成已看）；榜单页解除不记 `dismissed`，下一轮又连回来；条目来源在豆瓣与其他之间切换时，按来源选表的读法让关联凭空消失。改为上面的「一张表」：`movie_video_links.origin` 撤回（该列没有发布过；留着这一列的库照常迁移），解除按作品生效。

### 2.3 片库新排序（D-P2-01）

| `sort_mode` ✚ | 排序 | 游标字段 ✚ |
|---|---|---|
| `added_desc` | `created_at DESC, id DESC` | `CreatedAt *time.Time` |
| `year_desc` | `year DESC NULLS LAST, id DESC` | `Year *int`、`YearIsNull bool` |
| `title_asc` | `title_sort_key ASC, id ASC` | `TitleKey string` |

- `validateLibraryVideoCursor` 按模式校验各自字段（其他模式的字段必须为空）。
- **排序键** `videos.title_sort_key`（`size:512;not null;default:''`，与 `id` 组成复合索引）：
  - 取值：`display_title`，为空时取去扩展名的 `name`；用 `golang.org/x/text/collate`（`language.Chinese`，忽略大小写与宽度）算出排序键，十六进制存储。两种数据库按字节序比较，顺序一致。
  - 维护：`models.Video` 的钩子（`BeforeCreate` 按结构体算；`BeforeUpdate` 处理 Save 与按已加载行的更新，键写在更新内容的副本里，不改调用方的 map；多行模型的标题更新拒绝）；不走钩子的批量更新（`Model(&Video{}).Where(...).Updates(map)` 改标题或文件名的路径）必须改为调用 `services.UpdateVideoTitleFields(...)` 统一写法。键带版本前缀（`1:` + 十六进制）；启动时后台对账全部行（分批 500），存的键与算出来的不一致（空键、并发写入错过、排序规则版本变了）就改正。
  - 守卫测试：列出所有写 `display_title` / `name` 的服务入口（重命名、NFO 应用、元数据编辑、批量编辑、扫描建档、迁移），每条写完后断言排序键正确。
- `LibraryFilter.SortMode` 的取值校验加入三种新模式；Jellyfin 与手机端不暴露新排序（它们不传 `sort_mode` 或只传既有值）。

### 3.11 观看侧照片流 `viewer/PhotoBrowsePage.vue`（D-P2-08，2026-10-14）

- **数据**：全部复用现有接口，不改后端。
  - 照片：`SearchImagePage({filter, cursor, limit})`，`filter.sort_mode` 固定为拍摄时间倒序（与图片管理时间线同一个排序值，键 `COALESCE(taken_at, created_at)`）；每批与图片管理相同。
  - 组头计数：`ListImageTimelineBuckets(filter)`，同一个 `filter`。
  - 筛选只用 `keyword`、`favorite_only`、`person_ids`、`directory`；其余字段保持空。人物选项沿用图片管理的人物筛选搜索；文件夹选项来自 `ListImageFolderGroups(filter)`（名称 + 张数）。
- **网格**：按月分组的窗口化网格，复用 `utils/photoGrid.js`（`buildPhotoLayout` 的按月分组、`calculatePhotoWindow`、`calculatePhotoAnchorScrollTop`）与滚动宿主解析（`resolveScrollOwnerDescriptor`），不另写一套。缩略图比图片管理大（观看向），卡片是 `.btn-plain`，只有图，悬停不出管理按钮；收藏的显示一个小标记。
- **看图**：新组件（如 `viewer/PhotoLightbox.vue`），全屏、影院表面、`BaseModal` 栈里的最上层（Esc 关闭）。
  - ← → 切换；到已加载末尾时续载下一批再前进；第一张 / 最后一张时对应方向的按钮禁用。
  - 打开一张时调 `RecordImageView`（与图片管理看图同口径，失败只记日志）；详情用 `GetImageDetail`（人物、EXIF）。
  - 收藏 `SetImageFavorite`、评分 `SetImageRating`：就地更新本页这一张；失败用 `AppBanner` 或提示报原因，状态回到原值。
  - 信息面板：拍摄时间、相机与参数、尺寸、文件夹；人物芯片点了进 `people` 观看页的这个人。
  - 设为壁纸复用 `WallpaperButton`；「在图片管理中打开」= 进 `photos-manage` 并定位这一张（`PhotoLibraryPage.locateImage`）。
  - 没有删除、打标签、AI、批量、目录操作。
- **进入方式**：
  - 顶栏「图片」与命令面板的「图片」进 `photos`。
  - 回顾、人物 / 作品集观看页的 `open-image`：进 `photos` 并打开那一张——先在已加载的列表里找；找不到就清空筛选、按文件名关键字定位（与 `PhotoLibraryPage.locateImage` 同口径）；仍找不到提示「这张图片已不在图片库中」。
  - 人物观看页「去图片」：`navigateTo('photos', { personId })`，`applyPageParams` 落成人物筛选。
  - 管理侧原本进 `photos` 的入口（若有）改进 `photos-manage`；`photos.*` 命令宿主页仍是 `photos-manage`。
- **刷新**：管理侧删除 / 收藏 / 清理等改了图片后，观看页下次显示时按同一条件原地重取、保持滚动位置（与视频海报墙的原地刷新同法）；条件变了才回顶。
- **状态**：加载中 `SkeletonBlock`；图片库为空 `EmptyState`（下一步「去图片管理添加目录」）；筛选无结果 `EmptyState`（「清空筛选」）；出错 `AppBanner` + 重试。筛选状态存在本页，切走再回来保留滚动位置。
- **挂载**：`PhotoLibraryPage` 只在 `photos-manage` 显示（`photoPageVisible` 去掉 `photos`）；它的宿主命令照旧。
